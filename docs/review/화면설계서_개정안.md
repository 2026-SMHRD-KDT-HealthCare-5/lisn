## SD-15. slide15 `MAIN_SETTING_01` — 화면설명 전면 교체 ⭐⭐

**현재 화면설명이 홈 대시보드(slide13) 복사본입니다.** 설정 화면인데 "오늘의 감정 이모지", "추천 콘텐츠 영상(3-4-1)" 이 적혀 있습니다.

**교체 — 화면설명**
> ❶ 웨어러블 연동 상태: 연동된 기기명과 연동 여부를 표시하고, 항목별(활동량·수면·체성분) 수집 동의 상태를 개별 토글로 제공
> ❷ 연동 관리 버튼: OS 헬스 플랫폼 권한 설정 화면으로 연결. 권한 변경이 필요한 경우 안내 문구 노출
> ❸ 알림 설정: 맞춤 케어 알림 수신 여부 토글. 해제 시 콘텐츠 추천 푸시가 발송되지 않음

> ❻ 로그아웃 버튼: 세션(JWT) 무효화 후 로그인 화면(MAIN_LOGIN_01)으로 복귀

**교체 — 화면개요**
> 웨어러블 연동 상태와 항목별 수집 동의, 알림 수신, 페르소나 설정을 관리하고 계정 관련 기능으로 진입하는 화면

> ❻ 로그아웃이 `MLCM_101` 의 유일한 진입점입니다. 현재 설계서 어디에도 없습니다.

## SD-10. slide10 `MAIN_JOIN_03` — 화면설명 전면 교체 ⭐⭐

**화면개요는 "웨어러블 기기를 연동할 수 있는 페이지" 인데 화면설명은 `MAIN_JOIN_02` 복사본입니다.** 연동 관련 설명이 한 줄도 없습니다.

**교체 — 화면설명**

> ❷ 수집 항목 안내: 필수(활동량 - 걸음 수·이동 거리·소모 칼로리, 수면 패턴 - 수면 단계별 시간)와 선택(체성분 - 체중·골격근량 등)을 구분해 표시
> ❸ 항목별 동의 체크박스: 필수·선택 항목에 대해 개별 동의를 받음
> ❹ 연동하기 버튼: OS 헬스 플랫폼(Health Connect) 권한 요청 창을 호출. 승인 결과에 따라 연동 상태를 저장
> ❺ 건너뛰기: 연동 없이 홈 화면(MAIN_HOME_01)으로 이동. 이후 설정(MAIN_SETTING_01)에서 연동 가능
> ❻ (예외) 권한 승인을 거부하거나 취소한 경우 서비스 이용에 제한이 있을 수 있다는 경고 팝업을 노출하고 재시도 버튼을 제공

**교체 — 화면이름**
> 웨어러블 연동 설정 화면

**교체 — 화면개요**
> 회원가입 완료 후 스마트워치·체성분계 데이터 수집 항목에 동의하고 OS 헬스 플랫폼 연동 권한을 설정하는 화면

**교체 — 관련 유스케이스 ID**
> MLCM_110

**교체 — 메뉴경로**
> 로그인/약관동의/회원가입 정보 입력/웨어러블 연동

> ❺ 를 넣는 이유는 `MLCM_110` 의 선행조건이 "회원가입 및 로그인을 완료하여 메인/초기 설정 화면에 진입한 상태" 이고, **연동을 나중에 할 수 있어야** 마이페이지 재진입 분기가 성립하기 때문입니다.

> ❷ 비밀번호 입력창: 비밀번호 입력용 마스킹 인풋 박스

> ⚠ **「로그인 유지」는 복원하지 않습니다.** 12장 시절에는 있었으나, 그 항목은 **refresh token 을 전제**합니다. 이 프로젝트는 처음부터 단일 JWT 설계(`refresh` 가 산출물 어디에도 0건)라 복원하면 설계 공백이 되살아납니다. 복원 근거가 "예전에 있었으니까" 뿐이라 채택하지 않았습니다. → [`API설계_사전결정.md`](API설계_사전결정.md) 1절
>
> 「계정 찾기」만 복원합니다. 이건 `MLCM_102`(비밀번호 재설정)의 **유일한 진입점**이라 없으면 유스케이스가 도달 불가능해집니다.

## SD-12. slide12 `MAIN_CHAT_02` — 대화 기록 기능 복원 ⭐

**화면개요에는 "대화 기록 조회/삭제 가능" 이라 되어 있고 메뉴 구성도에도 「대화 기록 / 상세보기 / 삭제」가 있는데, 화면설명에서만 빠졌습니다.**

> ❸ 대화 입력: 텍스트 입력창과 음성 입력 버튼. 음성 입력 시 STT로 변환해 전송
> ❹ 대화 기록 목록: 이전 세션 목록을 최근순으로 조회
> ❺ 대화 기록 상세보기: 선택한 세션의 전체 대화와 자동 생성된 요약(session_summary)을 표시
> ❻ 대화 기록 삭제: 선택한 세션을 삭제. 삭제 전 확인 팝업 노출

> ❽ (예외) 외부 API 오류로 응답 생성에 실패한 경우 페르소나 톤에 맞춘 대체 응답을 노출

> ❺ 의 요약은 `CHAT_SESSIONS.session_summary` 이며 `MLCM_310` 종료조건에 따라 **세션 종료 시 자동 생성**됩니다.
>
> ❽ 은 `NFR-DV-003` 의 대체 응답 요건에 대응합니다.

## SD-09. slide9 `MAIN_JOIN_02` — 키(신장) 입력란 추가

`db/schema.sql` 의 `USERS.height_cm` 에 **입력 경로가 어디에도 없습니다.** 체성분 지표 해석에 필요한 값인데 받는 화면이 없습니다.

**교체 — 화면설명 ❹~❻ 부분**
> ❹~❼ 사용자 인적사항: 이름, 생년월일, 성별, 키 입력

> 기존 ❼(비상 연락처)와 ➑(회원가입 완료)의 번호가 하나씩 밀립니다.
>
> **`height_cm` 은 04 객체정의서와 `db/schema.sql` 에 이미 확정된 컬럼입니다.** 받는 화면을 만드는 것 자체는 확정 사항이고, 정할 것은 위치뿐입니다. 컬럼을 없애는 쪽은 04·05 를 되돌리는 개정이 되므로 선택지가 아닙니다.
>
> ① `MAIN_JOIN_02` 에서 선택 입력 — 위 문안
> ② `MAIN_JOIN_03` 에서 체성분 동의와 함께 입력 — 체성분이 선택 항목이라 맥락은 자연스러우나, **연동을 건너뛴 사용자는 키를 입력할 기회가 없어집니다**
>
> **①을 권장합니다.** ②를 택하면 `MAIN_JOIN_03` 화면설명에도 함께 반영해야 합니다.

## SD-E1. `USERS.role` 컬럼 신설 ⭐⭐

**관리자 기능이 요구사항·기능명세·발표자료에 모두 있는데, 데이터 모델에 관리자라는 개념이 없습니다.**

| 문서 | 관리자 언급 |
|---|---|
| 02 `MLCM_501` | 관련 액터 **관리자**, 선행조건 "관리자 계정으로 로그인되어 있어야 함" |
| 02 `FR-MN-003` | 관리자가 전체 사용자 위험도 분포를 조회하고 고위험군을 우선 식별 |
| 02 `MLCM_510` 5단계 | "이후 관리자가 통계·모니터링 목적으로 조회할 수 있도록" |
| 04 3) 개인정보 보호 | 접근통제를 "본인 및 권한 있는 관리자로 제한" |
| 발표자료 slide5 | 핵심 기능에 "관리자 관제" |

그런데 `db/schema.sql` 의 `USERS` 에는 `role` 도 `is_admin` 도 없습니다. 04 객체정의서에도 없습니다. **지금 스키마로는 어떤 계정이 관리자인지 판별할 방법이 없어 `MLCM_501` 을 구현할 수 없습니다.**

### 개정안

```sql
role VARCHAR(20) NOT NULL DEFAULT 'USER'
    CHECK (role IN ('USER', 'ADMIN')),
```

`DEFAULT 'USER'` 로 두면 **회원가입 흐름을 전혀 건드리지 않습니다.** `05-C` 에서 `persona_type` 에 `DEFAULT 'FRIEND'` 를 넣은 것과 같은 이유입니다.

관리자 계정은 일반 회원가입 후 승격합니다. 시드로 넣으려면 bcrypt 해시를 SQL 에 하드코딩해야 해 오히려 지저분해집니다.

```sql
UPDATE USERS SET role = 'ADMIN' WHERE email = '<관리자 이메일>';
```

### 별도 관리자 테이블을 만들지 않는 이유

테이블을 나누면 **로그인 로직·JWT 발급 경로·비밀번호 정책이 각각 둘**이 됩니다. 관리자 한두 명 때문에 인증 체계를 복제하는 셈입니다.

분리가 정당화되는 경우는 관리자 인증 경로가 물리적으로 분리돼야 하거나(별도 도메인·외부 IdP), 관리자에게 사용자와 전혀 다른 속성이 많거나, 규제상 분리가 요구될 때인데 **이 프로젝트는 셋 다 해당하지 않습니다.**

### 딸려오는 개정

| 문서 | 내용 |
|---|---|
| `db/schema.sql` | `USERS` 에 `role` 컬럼 추가 |
| 04 DB요구사항분석서 | 2) 객체 정의서의 `USERS` 속성 목록에 `role(USER/ADMIN)` 추가 |
| 05 테이블명세서 | 컬럼 정의표 1행 + CREATE 스크립트 |
| 화면설계서 | `SD-N6` `ADMIN_LOGIN_01` |

02 요구사항정의서는 손댈 필요가 없습니다. `MLCM_501` 선행조건이 이미 관리자 로그인을 전제하고 있어 `role` 은 그 요구사항의 구현일 뿐입니다.

### 덤 — `02-F` 의 근거가 완성됩니다

암호화 개정안(`02-F` (6))의 핵심 방어 논리가 이 문장입니다.

> 라이프로그 측정치는 컬럼 암호화 대신 **접근통제(본인 및 권한 있는 관리자로 제한)** 로 보호한다

**지금은 "권한 있는 관리자"를 판별할 수단이 스키마에 없어 이 문장이 공중에 떠 있습니다.** `role` 이 들어가야 "접근통제를 어떻게 구현하나요"에 답할 수 있습니다.
