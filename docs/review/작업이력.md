# 2026.07.29 (야간 2차) — 활동 시각 3컬럼 추가 확정

`05-E` 를 **컬럼을 추가하는 방향으로 확정**했습니다.

| 컬럼 | 타입 | 대응 메타데이터 |
|---|---|---|
| `activity_start_at` | TIMESTAMPTZ | 활동 시작 시간 |
| `activity_end_at` | TIMESTAMPTZ | 활동 종료 시각 |
| `total_active_min` | INTEGER | 총활동 시간(min) |

**근거** — 기업(라라랩스) 제공 메타데이터에 있는데 대응 컬럼이 없어 **적재 시 버려지는 데이터**였습니다. 기업주제 캡스톤에서 기업이 준 항목을 스키마가 못 받는 상태는 방어하기 어렵습니다. 수면은 `sleep_start_at`·`sleep_end_at`·`total_sleep_min` 으로 시작·종료·총시간을 다 받는데 활동만 `steps`·`distance`·`calories` 총량뿐이라 **구조도 비대칭**이었습니다.

## 타입을 `TIMESTAMPTZ` 로 한 이유

메타데이터는 `hh:mm:ss` 로 제공되지만 `TIME` 을 쓰지 않았습니다.

1. **04 문서 `2) 식별자 및 시각 컬럼 표준화`** 가 "모든 날짜/시간 컬럼은 TIMESTAMPTZ 로 통일"을 이미 규정합니다. `TIME` 은 우리가 정한 표준을 스스로 깨는 셈입니다.
2. **자정을 넘긴 활동 구간**을 `TIME` 으로는 표현할 수 없습니다(종료 < 시작). 수면 컬럼이 `TIMESTAMPTZ` 인 이유와 같습니다.

**NULL 허용**입니다. PMData·GLOBEM 과 Health Connect 일부 구간에 활동 시각이 없으므로, 분석은 값이 있는 구간에 한해 수행합니다.

## 검토했으나 채택하지 않은 대안

**`raw_payload`(JSONB) 에 넣어두는 절충안** — 컬럼을 늘리지 않고 원본을 보존할 수 있어 스키마 변경 비용이 0 입니다. 다만 기간별 집계·인덱스 조회가 어려워지고, **문서상으로는 "기업 데이터를 받는다"고 말할 근거가 약해집니다.** 컬럼으로 명시하는 편이 방어에 유리하다고 판단했습니다.

## 반영 과정에서 발생한 결함 2건 — 모두 해소

**둘 다 "붙여넣기 위치" 문제입니다.** 앞서 기록한 마크다운 기호·스마트 따옴표와 같은 계열입니다.

### ① 안내용 앞뒤 줄까지 붙여넣어 컬럼 중복

체크리스트가 위치를 잡기 쉽도록 `calories` 와 `sleep_start_at` 을 **문맥으로 함께 보여준 것**을 그대로 붙여넣어, 05 CREATE 스크립트에서 두 컬럼이 각각 두 번씩 나왔습니다.

```
calories INTEGER DEFAULT 0 CHECK (calories >= 0),
calories INTEGER DEFAULT 0 CHECK (calories >= 0),   ← 중복
```

같은 컬럼이 두 번 있으면 PostgreSQL 이 `column "calories" specified more than once` 로 거부합니다.

→ **체크리스트 작성 규칙을 바꿨습니다.** 코드 블록에 앞뒤 줄을 넣을 때는 **삭제할 줄을 화살표로 표시**하고, 삽입 항목은 **주변 줄 없이 넣을 텍스트만** 제시합니다.

### ② 04 객체 정의서 — 잘못된 행에 붙여넣어 원본 소실

활동 컬럼 3개를 `시계열 라이프로그(LIFELOG_METRICS)` 가 아니라 **`정서 위험도 예측 결과(EMOTION_RISK_SCORES)` 행에** 붙여넣어, 그 행의 원래 속성 목록이 라이프로그 컬럼 목록으로 **통째로 덮어써졌습니다.**

`score_id`·`emotion_score`·`risk_level`·`model_version`·`evaluated_at` 이 문서에서 사라진 상태였습니다.

**git 에 남아 있던 이전 커밋의 추출본에서 원문을 복구**했습니다.

> **커밋 전이라도 이전 커밋의 추출본이 안전망이 됩니다.** HWP 는 바이너리라 diff 를 볼 수 없지만, `docs/extracted/*.txt` 는 텍스트라 `git show HEAD:<경로>` 로 언제든 원문을 꺼낼 수 있습니다. **추출본을 같은 커밋에 넣는 규칙이 실제로 값을 했습니다.**

## 4-3. 팀 공용 DB — 캠퍼스 공용 PostgreSQL 확보

**운영 규칙**

- **`db/schema.sql` 은 PM(이응균)이 1회만 실행합니다.** 공용 DB 라 각자 실행하면 `CREATE TABLE` 이 충돌합니다. 현재 스크립트에 `IF NOT EXISTS` 가 없습니다.

> **⚠ 스키마 실행 전 확인** — `db/schema.sql` 이 `gen_random_uuid()` 를 쓰는데 이는 PostgreSQL 13 이상에서만 내장 함수입니다. 캠퍼스 서버 버전이 낮으면 `CREATE EXTENSION IF NOT EXISTS pgcrypto;` 를 먼저 실행해야 합니다. 접속 후 `SELECT version();` 으로 확인하세요.

건강에 관한 정보는 [개인정보 보호법 제23조](https://www.law.go.kr/%EB%B2%95%EB%A0%B9/%EA%B0%9C%EC%9D%B8%EC%A0%95%EB%B3%B4%EB%B3%B4%ED%98%B8%EB%B2%95/%EC%A0%9C23%EC%A1%B0) 및 같은 법 시행령 제18조의 **민감정보**에 해당합니다.

**제23조 제2항이 민감정보 처리 시 안전성 확보 조치를 요구**하므로, 이것이 `02-F` 의 계층적 보호 설계를 뒷받침하는 근거가 됩니다. "암호화를 다 안 했다"가 아니라 **"법이 요구하는 안전성 확보 조치를 위험도에 따라 설계했다"** 로 프레이밍할 수 있게 되었습니다.

> **[확인] 원시 측정치는 해석의 여지가 있습니다.** 걸음 수·수면 시간 개별 측정치가 그 자체로 "건강에 관한 정보"인지는 다툼이 가능하지만, **결합해 산출한 정서 위험도·감정 분류 결과는 정신건강 상태에 관한 정보**이므로 민감정보로 보는 것이 안전합니다.

### ② 제3자 제공 동의 요건 (`02-K`) — **삭제 결정이 맞음**

[개인정보 보호법 제17조 제2항](https://www.law.go.kr/lsLawLinkInfo.do?lsJoLnkSeq=900078379&chrClsCd=010202)은 제3자 제공 동의 시 아래를 알리도록 합니다.

1. 개인정보를 제공받는 자
2. 제공받는 자의 이용 목적
3. 제공하는 개인정보의 항목
4. 제공받는 자의 보유·이용 기간

여기에 동의 거부 권리와 거부에 따른 불이익도 고지해야 합니다. 기존 문안의 **"해당 기관에 제공될 수 있습니다"는 네 가지를 하나도 특정하지 않아** 요건을 충족하지 못합니다. 실제로 제공하는 데이터도 없으므로 삭제가 정확한 처리입니다.

### ③ 확인 과정에서 발견 — **민감정보 별도 동의 요건 누락** ⭐⭐

제23조 제1항은 민감정보를 처리하려면 **다른 개인정보 처리에 대한 동의와 별도로** 동의를 받도록 합니다.

## 02-C. 위기탐지·응답생성 — 병렬 호출 채택

**응답 속도를 우선하여 병렬(비동기 동시 호출) 구조로 확정합니다.** 순차 호출은 OpenAI 왕복이 2회가 되어 3초 응답 요건을 넘길 가능성이 높고, 별도 지표인 위기 탐지 1.5초 요건과도 충돌합니다.

### CAUTION 처리 — 재생성하지 않음

병렬 구조에서는 공감 응답이 위기 판정 *전에* 이미 생성되므로, 페르소나가 부정 감정 맥락을 모른 채 답한 문장이 나갑니다. **재생성하지 않고 그대로 사용하며, 감정별 힐링 콘텐츠 추천을 함께 노출**합니다.

- CAUTION 은 CRITICAL 과 달리 즉각적 위험 상황이 아니라, 지연을 2배로 늘려 재생성할 이유가 약합니다.
- 대신 **페르소나 시스템 프롬프트에 부정 감정 공감 톤을 상시 포함**시켜, 맥락을 몰라도 크게 빗나가지 않도록 설계합니다. 이것이 MLCM_400 의 "위로 대화와 함께 콘텐츠 추천" 요건을 지연 없이 충족하는 방법입니다.

### API 비용 — 2배 감수, 다만 관리

매 턴 호출이 2회가 되어 비용이 2배입니다. 속도를 우선하기로 했으므로 감수하되 아래로 증가폭을 줄입니다.

1. **1차 키워드 필터에 걸리면 공감 응답 생성을 호출하지 않습니다.** 어차피 위기 UI 로 전환되어 쓰지 않을 응답입니다.
2. 위기 탐지 호출은 판정 JSON 만 받으므로 `max_tokens` 를 작게 잡습니다.

> **발표 대비** — "왜 호출을 2번 하나요"에 대한 답은 **"안전 기능을 응답 생성에 종속시키지 않기 위해 독립 호출로 분리했다"** 입니다. 순차로 묶으면 응답 생성이 실패할 때 위기 탐지도 함께 실패합니다. 비용이 아니라 안전 설계의 문제로 프레이밍하세요.

## 원 개정안에서 수정해 반영한 것 3건

1. 매체 암호화를 **조건부화** — PostgreSQL 은 자체 TDE 가 없어 OS/클라우드 레벨로만 가능. 실제로 켜지 않으면 미이행 보장이 됨
2. "단독으로는 개인을 특정할 수 없는 구조" 주장 **완화** — USERS 와 측정치가 단일 DB 안에 물리적 FK 로 연결되어 `JOIN` 한 번이면 실명과 붙음. 접근통제를 주 통제수단으로 재배치
3. **평가셋 작성자 분리 요건 추가** — 프롬프트 설계자가 평가셋도 만들면 Recall 90% 가 자동으로 나옴
