# 2026.08.02 (37차) — 위기 상태 화면에서 라벨과 표정을 걷어냈습니다

PM 지적 두 건. 둘 다 **안전 문제**였고 근거가 문서에 있었습니다.

## 1. 위기인데 마음이가 웃고 있었습니다

`MaeumeMascot` 에 얼굴이 하나뿐이라(`• ᴗ •`) 위험도와 무관하게 웃었습니다.
「지금 마음이 많이 힘들어 보여요」 옆에서 웃는 얼굴은 **공감이 아니라 무시로
읽힙니다.**

### 슬픈 표정으로 바꾸지 않았습니다

캐릭터가 같이 괴로워하면 감정을 더 키우고, 사용자가 자기 상태를 「남까지 힘들게
하는 것」으로 받아들이게 됩니다. **위기 화면에 경고색을 쓰지 않는 것과 같은
이유**입니다. 담담한 표정(`• · •`)으로 갔습니다 — 눈은 그대로라 시선은 계속
사용자를 향하고 입만 다뭅니다. 배경색도 어둡게 하지 않았습니다.

인사말의 `😊` 와 「오늘도 수고했어요**!**」의 느낌표도 같이 정리했습니다.

## 2. 「위기」라는 단어를 사용자에게 보여주고 있었습니다

**감정 마스터 9종에 「위기」·「절망」이 있습니다.** 이걸 홈 헤드라인 27pt 로 그대로
띄우고 있었습니다.

### 근거가 두 개

- **02 요구사항 「진단 금지」** — 감정 이름을 헤드라인으로 박으면 데이터 관찰이 아니라
  **사람에 대한 판정**으로 읽힙니다
- **화면설계서가 그렇게 하라고 한 적이 없습니다.** ❶ 은 「대표 감정 **이모지**, 정서
  점수…」 였습니다. **구현이 문서에서 벗어난 것**이었습니다

노출 지점은 `home_screen.dart` 한 줄뿐이었습니다. 리포트·관리자 화면은 감정 이름을
텍스트로 쓰지 않습니다(위험도 색으로만).

### 관리자 화면은 그대로 둡니다

거기서 「위기」는 담당자가 판단하는 데 필요한 정확한 용어입니다. **본인이 보는 화면과
전문가가 보는 화면은 기준이 다릅니다.**

### 이모지로 대체하지 않았습니다

문서는 이모지를 말하지만, 위기 감정에 😢 같은 것을 쓰면 방금 피한 「슬픈 표정」 문제가

문구가 이미 상태를 전달하므로 라벨이 정보를 더하지 않습니다.

## ⚠ 먼저 기록 — 앱에 인증을 건너뛰는 플래그가 생겼습니다

화면설계서 캡처를 뜨려면 매번 로그인하고 탭을 눌러 들어가야 했습니다. 위기 화면은

| 플래그 | 하는 일 |
|---|---|
| `DEV_LOGIN=true` | 켤 때 데모 계정으로 **자동 로그인** |
| `SCREEN=<키>` | 그 화면으로 **바로 시작** |

- 계정은 `.example` 도메인이라 실제로 존재할 수 없습니다
- 실패하면 조용히 넘어가지 않고 **로그를 남기고** 평소 로그인 화면으로 갑니다

플래그 유무 양쪽으로 APK 빌드를 확인했습니다.

> **제출·시연 빌드에 이 플래그를 주지 않는지 확인해야 합니다.** `CLAUDE.md` ·

33차에서 관리자 웹을 고치고 나서 **앱에 같은 구조가 있는지 찾아봤습니다.**

| 화면 | 언제 튀나 |
|---|---|

| `MAIN_LIFELOG_01` | 기간(일·주·월) 전환 · 당겨서 새로고침 |

원인은 하나입니다. **다시 불러올 때 보여줄 것이 이미 있는데도 화면을 로딩으로
갈아치웁니다.** 리포트가 가장 심합니다 — 분포·곡선·라이프로그·요약이 한꺼번에
사라졌다 돌아옵니다.

## 규칙을 하나로 맞췄습니다

- 보여줄 것이 **없을 때만** 로딩(최초 진입)
- 다시 불러오는 중에는 이전 내용을 두고 **흐리게만**(`Opacity 0.45`)
- 흐린 동안은 **조작을 막습니다**(`IgnorePointer`)
- **성공한 결과만 보관**합니다. 통신이 한 번 끊겼다고 보고 있던 기록을 버리면
  다음 조회에서 다시 로딩부터 시작합니다

> 당겨서 새로고침은 `RefreshIndicator` 가 이미 위에서 진행을 알립니다. 본문까지
> 비우는 건 중복이고, 첫 화면인 홈에서 특히 눈에 띄었습니다.

## 흐린 상태에 `RepaintBoundary` 를 달지 않았습니다

리포트 PDF 는 **화면을 캡처해** 만듭니다. 흐린 상태가 찍히면 **바뀐 기간의 머리말에
이전 기간의 그림**이 들어갑니다. 상담기관에 내는 문서라 그런 조합이 나오면 안 됩니다.
`IgnorePointer` 로 내보내기 버튼도 막습니다.

## `then(...).ignore()` — 되돌리지 마세요

`_loadAndKeep()` 을 `async`/`await` 로 쓰면 조회가 **즉시 실패**할 때 `FutureBuilder`
가 구독하기 전에 오류가 도착해 **미처리 예외로 보고**됩니다. 화면은 정상 처리되는데
로그만 더러워지고 위젯 테스트는 실패합니다.

future 를 만들자마자 리스너를 달아 그 경합을 없앴습니다. 화면 처리는 `FutureBuilder`
가 하므로 파생 future 의 오류만 흘려보냅니다. 세 화면 주석에 이유를 적어뒀습니다.

## 테스트 3건

실패해도 이전 결과를 버리지 않음.

세 번째는 처음에 전제를 잘못 잡아 실패했습니다. 「실패 후 기간을 되돌리면 캐시가
보인다」로 짰는데, 되돌리는 것도 새 조회라 또 실패했습니다. **다음 조회가 성공하는

「버튼 누르거나 검색할 때 화면 움직임이 너무 많다」는 지적을 받고 **브라우저에서

| | 고치기 전 | 고친 뒤 |
|---|---|---|

## 원인 4가지

### 1. 조회할 때마다 표를 걷어냈다

`setRows(null)` → `LoadingPanel` → 다시 표. **한 번 누를 때마다 두 번 튑니다.**
디바운스된 검색은 글자를 멈출 때마다 이걸 반복합니다.

이전 목록을 그대로 두고 `is-pending` 으로 **흐리게만** 처리하도록 바꿨습니다. 로딩
박스는 최초 진입에만 뜹니다.

### 2. `table-layout` 이 auto 였다

결과 집합이 바뀔 때마다 다섯 컬럼 폭이 전부 재계산됩니다. 대상자 표만 `fixed` 로
바꾸고 폭을 %로 고정했습니다. 잘리는 값은 `title` 로 봅니다.

> 위기 사건 이력 표에는 적용하지 않았습니다. 필터가 없어 다시 조회하지 않습니다.

### 3. 스크롤바가 생겼다 없어졌다

목록이 길어지면 세로 스크롤바가 생기고, 짧아지면 사라지면서 **화면 전체가 좌우로
15px 밀립니다.** 검색창이 1030→1045 로 튄 게 이것이었습니다.
`:root { scrollbar-gutter: stable }` 로 자리를 비워뒀습니다.

### 4. 지우기 버튼이 검색창 폭을 바꿨다

첫 글자에서 `×` 가 생기며 오른쪽 정렬된 검색창이 밀립니다. 항상 자리를 차지하게 두고
`visibility` 로만 끕니다. 안 보일 때는 `tabIndex={-1}`·`aria-hidden` 으로 초점·낭독에서
뺍니다.

## 곁들여 — 문구가 데이터와 짝이 맞도록

이전 목록을 남기게 되면서 새 위험이 생겼습니다. 문구가 **살아 있는** `filter`·`query`
를 읽으면, 다시 불러오는 동안 이전 목록 위에 새 조건이 얹혀 `"하늘" 검색 결과 33명`
같은 없는 상태가 만들어집니다.

결과를 만들어낸 조건을 값과 **함께** 담고(`{ items, query, filter }`) 문구는 그쪽만
읽습니다. 문구 생성은 `labels.js` 로 빼고 테스트 7건을 붙였습니다 — 화면만 봐서는
틀어진 걸 알기 어려운 종류입니다.

## 배운 것 — 레이아웃 문제는 재고 고친다

「움직임이 많다」는 체감을 눈으로 좇으면 가장 큰 원인 하나만 잡고 끝납니다.
`MutationObserver` 로 프레임마다 `getBoundingClientRect()` 를 찍으니 **넷 다** 드러났고,
고친 뒤 같은 방법으로 각 값이 1종류로 수렴하는 것까지 확인했습니다.

관리자 웹은 DOM 테스트가 없어 레이아웃은 이 방법으로 검증합니다.

# 2026.08.02 (32차) — 관리자 대상자 검색, 데모 페르소나

## 대상자 검색 (`GET /admin/users?q=`)

관제 대상이 늘면 위험도 필터만으로는 특정 인물을 못 찾습니다. 이름·이메일 부분 일치
검색을 넣고 **위험도 필터와 AND** 로 걸었습니다 — "심각한 사람 중에서 김씨"가
관제에서 실제로 필요한 동작입니다.

### LIKE 메타문자를 이스케이프했습니다

`%` 를 그냥 넘기면 **한 글자로 전 사용자 명단이 뜹니다.** 관리자가 의도하지 않아도
검색창에 실수로 들어간 한 글자가 전체 명단을 띄우는 건 개인정보 관점에서 사고입니다.
`_` 는 더 나쁩니다 — 임의의 한 글자로 동작해 **틀린 사람이 나오는데 오류는 안 납니다.**

역슬래시·`%`·`_` 를 이스케이프하고 두 경우를 테스트로 고정했습니다.

### 연락처로는 검색할 수 없습니다

`phone` 은 AES-256-GCM 컬럼 암호화라(02-F 3항) 같은 값도 암호문이 매번 다릅니다.
복호화해 비교하려면 전 사용자를 메모리로 올려야 해서 하지 않습니다. **검색 편의보다
저장 시점의 보호를 택한 결과**입니다(안건 4). 코드 주석에 남겼습니다.

### 검색은 SQL, 위험도 필터는 파이썬

기존 `risk_level` 필터는 전 사용자를 가져온 뒤 파이썬에서 거릅니다(`limit`/`offset` 도
마찬가지). 검색까지 같은 방식으로 하면 매 타이핑마다 전 사용자를 메모리로 올리게 되어
`WHERE` 절로 넣었습니다. **기존 필터의 인메모리 처리는 그대로 남아 있습니다** —
대상자가 수천 명 규모가 되면 손봐야 합니다.

### 화면

- **디바운스 250ms.** 글자마다 요청하면 앞선 요청이 뒤늦게 도착해 결과가 뒤집힙니다
- **빈 결과 문구를 구분**했습니다. 같은 문구를 쓰면 검색어를 고쳐야 하는지 필터를
  풀어야 하는지 알 수 없습니다 → `"하늘"에 해당하는 대상자가 없습니다. 안정 필터를 풀고…`
- 결과 건수 표시, 지우기 버튼

> **문서 처리** — `SD-N5` 화면설명은 ❶~❺ 5줄을 이미 다 써서 ❻ 을 넣으려면 기존 항목을
> 덜어내야 합니다. 검색은 ❷ 를 좁히는 수단이지 별개 기능이 아니므로 **와이어프레임
> 주석**으로 남기는 쪽을 권합니다. 체크리스트 `SD-A④` 에 등록했습니다.

## 로그인 화면 — 단계적 노출

첫 화면부터 빈 입력란 두 개를 띄우면 앱의 첫인상이 무겁습니다.

```
0단계  마스코트 확대 + 문구 + [로그인] [회원가입]
1단계  이메일 칸 (회원가입 감춤, 뒤로가기 생김)
2단계  비밀번호 칸 + 「비밀번호를 잊으셨나요?」
```

비밀번호 칸은 **이메일이 형태를 갖춘 시점**(`@`·`.` 포함)에 나타납니다. 한 글자마다 나타나면 화면이 흔들리고, 완벽한 검증을 요구하면 오타 하나에 칸이 사라져 더 답답합니다. 한 번 나타난 칸은 다시 숨기지 않습니다.

**자동완성이 약해집니다**(비밀번호 칸이 없는 동안 이메일만 채워짐). MVP 단계에서는 첫인상이 우선이고 자동 로그인이 붙으면 반복 입력 자체가 사라진다는 PM 판단으로 감수합니다.

**배경 그라데이션은 로그인 화면에만 씁니다**(확정). 회원가입·비밀번호 재설정은 입력과 약관이 길게 이어져 스크롤 중 배경이 변하면 산만합니다.

### 헤드라인 전환 — 세 번 갈아엎은 끝에

`오늘의 마음도 / 포근히 / 안아줄게요`(3줄)가 2줄로 바뀌는 구간입니다.

1. 교차 페이드 — 두 문구가 **동시에** 흐려져 반투명끼리 포개지며 뭉갬
2. 세 덩어리로 쪼개 이동 — `안아줄게요` 가 **대각선으로 `포근히` 위를 지나감**
3. ㄱ자 경로(옆→위) — 겹침은 없어졌으나 움직임이 기계적
4. **최종: 교차 페이드 + `switchOutCurve`/`switchInCurve` 로 앞뒤 구간 분리**

> 2번에서 배운 것 — **좌표를 `expanded` 로 즉시 계산하고 크기만 애니메이션에 맡기면 안 됩니다.** 둘이 다른 시간축으로 움직여 중간 프레임에서 줄이 어긋납니다.

## 회원가입 — 기본/선택 분리와 `?` 설명

화면설계서가 비상 연락처를 「선택사항」으로 적고 있는데 **화면에만 구분이 없었습니다.**

- **선택** — 비상 연락처 · 키

선택 묶음은 **접어서 감추지 않고 첫 칸이 살짝 보이게** 잘랐습니다. 완전히 접으면 대부분 그냥 지나칩니다. 흐려지는 자리에 `v` 를 얹고, 펼친 뒤에는 같은 자리에 `^` 가 옵니다.

### 반복되는 감사 패턴 4가지

같은 종류의 결함이 계속 나왔습니다. 새 문서를 검수할 때 먼저 의심할 지점입니다.

1. **같은 주장이 여러 절에 반복** — `01-N`(방법론↔3장) · `01-O④`(기대효과↔활용방안) · `01-P①`(유사서비스↔차별성) · `01-Q`(주요기술↔사용기술) · `01-R`(1장↔6장 기대효과)
   - **절을 지우는 게 답이 아닌 경우가 있습니다.** 「차별성」처럼 장을 닫는 종합 절이나 1장의 양식 칸은 위치상 필요하므로, 반복된 문장을 뒤 장 참조로 바꾸고 고유 정보만 남깁니다
   - **개요 장(1장)이 특히 위험합니다.** 개요는 뒤 장을 미리 요약하는 성격이라, 뒤 장을 채우면서 1장을 줄이지 않으면 그대로 중복이 됩니다
2. **다른 칸이 이미 말하는 것을 비고에 재진술** — 단위 17칸 · `PK UUID` 8곳 · `gen_random_uuid()` 8곳 · 테이블설명의 컬럼 나열 · `05-R②`(NN 칸이 말하는 "선택 입력")
3. **출처와 함께 제시한 수치를 요약 표에서 다시 인용** — `01-P②`(STP 의 18.3%/19.59%) · `01-R`(1장 기대효과의 80.3%/51.1%)
4. **출처 없는 정량 주장** — `01-U`(경쟁사 "세션당 평균 1~2분"). 참고문헌 9건에도 2장 유사 서비스 분석에도 근거가 없었습니다

### 비고·설명 칸을 채우려고 채우지 마세요

**칸이 있으면 채워야 한다는 압박이 실제로 문서를 나쁘게 만들었습니다.** 단위 17칸, `PK UUID` 8곳, `gen_random_uuid()` 8곳이 모두 그 결과입니다.

- **적을 것** — 그 칸 말고는 알 수 없는 것. 값 범위, enum 값, 참조 대상, 구현 방법, 설계 근거
- **적지 말 것** — 컬럼명·타입·제약 칸이 이미 말하는 것, 04 에 전체 원칙으로 선언된 것, 다른 칸 서술의 재진술

**비워두는 게 정상입니다.** 최종적으로 79개 컬럼 중 28개만 채워졌고 51개가 빈칸입니다.

> ⚠ **지울 때 남길 것까지 지우지 마세요.** `05-O` 에서 FK 참조 대상 6곳과 CHECK 값 목록 3곳이 함께 지워져 `05-P` 로 복원했습니다. **`FK`·`CK` 칸의 `Y` 는 "제약이 있다"만 말하고 "어디를 참조하는지 / 어떤 값이 허용되는지"는 말하지 못합니다.**

## `결정-1` — 연락처는 **선택 입력**으로 확정

### 발표 시 "연락처는 어떻게 쓰나요"

**"확장 가능성"으로 답하지 않기로 했습니다.** 모든 미사용 컬럼을 정당화하는 만능 논리라 변별력이 없고, "나중에 쓸지 몰라 미리 받아둔다"는 최소수집 원칙 위반의 전형이라 오히려 감점 위험이 있습니다.

**질문을 "왜 받나"에서 "왜 이렇게 보호하나"로 옮깁니다.**

> 연락처는 유출 시 즉각적 2차 피해(스미싱·보이스피싱)가 발생하는 항목이라 컬럼 단위 AES-256-GCM 을 적용했습니다. 반대로 라이프로그 측정치는 기간별 집계와 복합 인덱스 조회가 서비스 핵심 동작이라 의도적으로 컬럼 암호화에서 제외하고 접근통제로 보호했습니다. 위험도에 따라 보호 수준을 나눈 설계이며 연락처가 그 최상위 계층입니다. 선택 입력이므로 미입력 사용자도 전 기능을 이용할 수 있습니다.

### AES-256-GCM 비용 — 확인 결과

| 항목 | 비용 |
|---|---|
| 라이선스·서비스 요금 | **0원.** 표준 알고리즘이며 Python `cryptography` · Node `crypto` 내장. 클라우드 KMS 를 쓸 때만 과금되고 본 과제는 미사용 |
| 연산 | **무시 가능.** AES-NI 하드웨어 명령으로 초당 GB 단위. 전화번호 20바이트는 마이크로초 |
| 저장 용량 | 20자 → Base64 약 64자. 3배지만 절대량이 미미 |
| 실제 부담 | **키 관리 설계.** `.env` 에 두면 DB 유출은 막지만 서버 유출은 못 막음. IV 는 매 암호화마다 새로 생성해 암호문과 함께 저장(GCM 은 IV 재사용이 치명적) |

**돈이 들지 않으므로 "왜 일부만 암호화했나"에 "비용 때문"이라고 답하면 안 됩니다.** 사실이 아니고 되짚어 물으면 무너집니다. **"조회 성능과 서비스 핵심 동작 때문"** 이 정확합니다.

## `05-K` — 민감정보 동의 기록 2컬럼 추가 (A안)

## `device_name` — 확인 결과 컬럼 유지

**Health Connect 에서 기기 정보를 읽을 수 있습니다.** `Metadata.device`(`Device` 객체)가 `manufacturer`·`model`·`type` 을 제공하며, **자동·능동 기록 데이터는 `type` 이 필수**입니다.

다만 두 가지 제약이 있어 비고를 정정했습니다.

1. 값을 넣는 주체가 **데이터를 쓴 앱**(삼성헬스·Fitbit 등)이라 그 앱이 채우지 않으면 **NULL** 일 수 있음
2. `Galaxy Watch 6` 같은 마케팅 명이 아니라 **제조사 + 모델 코드**(예: `Samsung` + `SM-R900`)로 들어옴

기존 비고 `사용자 디바이스 명칭 (예: Galaxy Watch 6)` 는 사실과 달랐습니다.
근거 — [Metadata requirements](https://developer.android.com/health-and-fitness/health-connect/metadata) · [Read raw data](https://developer.android.com/health-and-fitness/health-connect/read-data)

## `raw_payload` 삭제

2. **자정을 넘긴 활동 구간**을 `TIME` 으로는 표현할 수 없습니다(종료 < 시작). 수면 컬럼이 `TIMESTAMPTZ` 인 이유와 같습니다.

3. **학습 데이터에 SpO2 가 없습니다.** PMData · GLOBEM · 기업 제공 데이터 어디에도 없습니다. **GLOBEM 스크린타임 문제의 반대 방향**입니다 — 그때는 학습엔 있고 서비스가 못 만드는 피처였고, 이건 서비스는 받는데 학습 데이터에 없는 피처입니다. **둘 다 모델이 쓸 수 없습니다.**
4. **측정 신뢰도.** 손목 광학 센서 SpO2 는 의료기기 대비 오차가 크고 야간 자동 측정 결측이 많습니다. 기기·앱에 따라 데이터 유무도 갈립니다.

**시점 비용도 고려했습니다.** 컬럼 하나를 추가하면 `db/schema.sql` · 05 컬럼 정의표 · 05 CREATE 스크립트 · 04 객체 정의서 · 02 수집 항목·동의 항목 · 03 데이터 정의 및 JSON 샘플까지 **다시 열어야** 하고, 붙여넣기 사고(마크다운 기호 · 스마트 따옴표 · 고치다 한 글자 더 지움)가 재발할 위험이 있습니다.

- **LifeSnaps** 가 LISN 의 수집 항목(활동량·수면단계·심박·HRV)과 가장 정합적입니다. Fitbit Sense 기반이라 신호 구성이 거의 일치하고, PANAS·STAI 자가보고가 붙어 있어 **감정 9종 · risk_score 매핑에 직접 쓸 수 있습니다.** 4개월 연속 데이터라 **LSTM Autoencoder 의 정상 패턴 학습**에 필요한 장기 시계열도 확보됩니다.
- **Depresjon** 은 신호가 활동량 단독이라 약하지만 **MADRS 라는 임상 척도 라벨**을 가집니다. LightGBM 2차 위험도 분류의 라벨 근거로 씁니다.

> **⚠ WESAD 는 재검토가 필요합니다.** 현재 01 기획서·발표자료 slide12 에 들어 있지만, **실험실 환경에서 유도한 급성 스트레스** 데이터라 일상 라이프로그와 도메인이 다릅니다. 15명 규모도 작습니다. 유지하려면 "급성 스트레스 반응 참조용"으로 역할을 한정해 서술하는 편이 안전합니다.

### 위기 대화 탐지 평가셋

**해외 코퍼스를 번역해서 평가셋으로 쓰는 것은 권장하지 않습니다.** 서비스가 한국어 챗봇이므로 (1) 번역체가 실제 한국어 발화와 다르고 (2) 번역 품질이 평가 지표에 섞여 들어갑니다.

**대신 라벨링 기준만 차용합니다.**

- **CLPsych 2019 Shared Task** 의 위험도 4단계 — `no / low / moderate / severe risk` 체계를 자체 평가셋의 라벨링 기준으로 채택합니다. [ACL Anthology](https://aclanthology.org/W19-3003/)
- 효과: **"라벨 체계를 팀이 임의로 정한 게 아니라 국제 공유 태스크 기준을 따랐다"** 는 방어 논리가 생깁니다. 평가셋이 전량 자체 작성이 된 상황에서 `02-B` 의 자가검증 취약점을 상당 부분 보완합니다.
- 참고: [UMD Reddit Suicidality Dataset](https://psresnik.github.io/umd_reddit_suicidality_dataset.html) (SuicideWatch 11,129명 + 대조군 11,129명, CLPsych 2019 학습·평가 데이터 포함)은 **DUA 서명 등 기관 절차가 필요**해 6주 일정에는 넣기 어렵습니다. 라벨 기준 참조용으로만 인용하세요.

**따라서 평가셋 200건은 전량 팀 자체 작성이며, `02-B` 의 "프롬프트 설계자와 분리된 인원이 작성" 요건은 선택이 아니라 필수입니다.**

## 4-3. 팀 공용 DB — 캠퍼스 공용 PostgreSQL 확보

각자 로컬 DB 를 쓰면 5주차 통합 테스트 시점에 스키마 불일치가 터지는 문제가 있었습니다.

Neon·Supabase 등 외부 클라우드는 검토 대상에서 제외합니다.

> **🔑 접속 정보는 저장소에 두지 않습니다.**
> 이 저장소는 **공개(public)** 라 커밋하는 순간 노출되고, 삭제해도 커밋 히스토리에 남습니다.
> 접속 정보는 **단톡방 고정 공지**와 **Notion 프로젝트 페이지**에만 둡니다.

**운영 규칙**

- **`db/schema.sql` 은 PM(이응균)이 1회만 실행합니다.** 공용 DB 라 각자 실행하면 `CREATE TABLE` 이 충돌합니다. 현재 스크립트에 `IF NOT EXISTS` 가 없습니다.
- 애플리케이션 코드에 접속 정보를 직접 쓰지 않고 **`.env` 로 분리**합니다. `.gitignore` 에 이미 포함되어 있습니다.
- **포트가 기본값(5432)이 아닙니다.** DBeaver·psql 접속 시 공지의 포트로 바꿔야 합니다. 접속 실패 문의의 대부분이 여기서 발생합니다.

> **⚠ 스키마 실행 전 확인** — `db/schema.sql` 이 `gen_random_uuid()` 를 쓰는데 이는 PostgreSQL 13 이상에서만 내장 함수입니다. 캠퍼스 서버 버전이 낮으면 `CREATE EXTENSION IF NOT EXISTS pgcrypto;` 를 먼저 실행해야 합니다. 접속 후 `SELECT version();` 으로 확인하세요.

## 02-C. 위기탐지·응답생성 — 병렬 호출 채택

**응답 속도를 우선하여 병렬(비동기 동시 호출) 구조로 확정합니다.** 순차 호출은 OpenAI 왕복이 2회가 되어 3초 응답 요건을 넘길 가능성이 높고, 별도 지표인 위기 탐지 1.5초 요건과도 충돌합니다.

### CAUTION 처리 — 재생성하지 않음

병렬 구조에서는 공감 응답이 위기 판정 *전에* 이미 생성되므로, 페르소나가 부정 감정 맥락을 모른 채 답한 문장이 나갑니다. **재생성하지 않고 그대로 사용하며, 감정별 힐링 콘텐츠 추천을 함께 노출**합니다.

- CAUTION 은 CRITICAL 과 달리 즉각적 위험 상황이 아니라, 지연을 2배로 늘려 재생성할 이유가 약합니다.
- 대신 **페르소나 시스템 프롬프트에 부정 감정 공감 톤을 상시 포함**시켜, 맥락을 몰라도 크게 빗나가지 않도록 설계합니다. 이것이 MLCM_400 의 "위로 대화와 함께 콘텐츠 추천" 요건을 지연 없이 충족하는 방법입니다.

### API 비용 — 2배 감수, 다만 관리

매 턴 호출이 2회가 되어 비용이 2배입니다. 속도를 우선하기로 했으므로 감수하되 아래로 증가폭을 줄입니다.

1. **1차 키워드 필터에 걸리면 공감 응답 생성을 호출하지 않습니다.** 어차피 위기 UI 로 전환되어 쓰지 않을 응답입니다.
2. 위기 탐지 호출은 판정 JSON 만 받으므로 `max_tokens` 를 작게 잡습니다.

> **발표 대비** — "왜 호출을 2번 하나요"에 대한 답은 **"안전 기능을 응답 생성에 종속시키지 않기 위해 독립 호출로 분리했다"** 입니다. 순차로 묶으면 응답 생성이 실패할 때 위기 탐지도 함께 실패합니다. 비용이 아니라 안전 설계의 문제로 프레이밍하세요.

## 4-1. 평가셋 200건 — 담당 배분

AI Hub 접근 불가로 평가셋이 전량 자체 작성이 되면서, **"프롬프트 설계자와 평가셋 작성자 분리"가 선택이 아니라 필수 요건**이 되었습니다.

| 역할 | 담당 | 분량 |
|---|---|---|
| 판정 프롬프트 설계 | 김건영 | — (평가셋 작성 제외) |
| 평가셋 작성 · 총괄 | 이응균 | 100건 |

## 원 개정안에서 수정해 반영한 것 3건

1. 매체 암호화를 **조건부화** — PostgreSQL 은 자체 TDE 가 없어 OS/클라우드 레벨로만 가능. 실제로 켜지 않으면 미이행 보장이 됨
2. "단독으로는 개인을 특정할 수 없는 구조" 주장 **완화** — USERS 와 측정치가 단일 DB 안에 물리적 FK 로 연결되어 `JOIN` 한 번이면 실명과 붙음. 접근통제를 주 통제수단으로 재배치
