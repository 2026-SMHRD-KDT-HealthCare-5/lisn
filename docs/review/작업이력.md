# 2026.07.31 (24차) — 관리자·리포트·홈, 분석 파이프라인 관통

## 백엔드 API 가 전부 채워졌습니다

| 그룹 | 내용 |
|---|---|
| `admin` | 위험도 분포 · 대상자 목록 · 상세 리포트 · 위기 사건 이력 |
| `reports` | 본인 정서 리포트 (`MLCM_500`) |
| `home` | 홈 합성 엔드포인트 + 콘텐츠 추천 새로고침 |
| `analysis` | `MLCM_210` 분석 트리거 · 결과 적재 |

## 파이프라인이 처음으로 끝까지 돌았습니다

```
앱 push → UPSERT 적재 → 백그라운드 분석 트리거 → AI 서버 판정
       → EMOTION_RISK_SCORES 적재 → 홈/리포트 반영
```

AI 서버 스텁을 띄워 검증했습니다. `ANXIETY` / score 82 / `CAUTION` 이 적재되고 홈의 `action` 이 자동으로 `CONTENT` 로 바뀌었습니다.

**AI 서버가 없어도 push 는 성공합니다.** 분석 실패로 push 를 되돌리면 라이프로그가 유실됩니다. 다음 주기에 다시 분석되면 되므로 조용히 넘어가고 로그만 남깁니다.

분석은 **백그라운드 태스크**로 돌립니다. 동기로 하면 AI 추론이 끝날 때까지 앱이 대기하는데, 앱은 결과가 아니라 "수신됐다"만 알면 됩니다.

## 설계 판단

- **대시보드 집계는 사용자별 최신 1건만 셉니다.** 전체 행을 집계하면 자주 측정한 사용자가 분포를 왜곡합니다. `MLCM_501` 2단계의 "전체 대상자 분포"는 사람 수 기준입니다
- **대상자 목록에 미평가자도 포함**합니다(`risk_level=null`). 관리자 입장에서 "분석된 적 없는 사람"도 관리 대상입니다
- **리포트 조회 로직을 본인·관리자가 공유**합니다. `MLCM_501` 4단계가 "`MLCM_500` 과 동일한 시각화 컴포넌트 재사용" 을 요구하므로 데이터도 같은 모양이어야 합니다
- **분석 이력이 없으면 `409`** 입니다. 빈 차트를 내리면 "분석 실패" 인지 "아직 데이터 없음" 인지 클라이언트가 구분할 수 없습니다
- 홈의 수면 요약은 **합계가 아니라 최근값**을 씁니다. 15분 주기로 같은 수면 구간이 반복 적재되므로 합치면 부풀려집니다
- **`risk_level` 매핑은 AI 서버가 확정**합니다(04 문서 6항). 비즈니스 서버가 다시 계산하면 규칙이 두 곳에 생겨 어긋납니다. 여기서는 값이 규격에 맞는지만 검사합니다

## 알아둘 것 — `role` 은 JWT 에 박힌다

`UPDATE users SET role='ADMIN'` 만 하고 **기존 토큰을 계속 쓰면 403 입니다.** 승격 후 재로그인이 필요합니다. 검증 중에 실제로 걸렸습니다.

## 남은 것

- **`HEALING_CONTENTS` 가 비어 있어 추천이 0건입니다.** 04 문서 7항이 "사전 안전 검수를 거친 콘텐츠만" 을 원칙으로 못 박아 사람이 골라야 합니다
- `GET /reports/export` (PDF) 미구현. 서버 생성이냐 클라이언트 생성이냐를 먼저 정해야 합니다 — 코드에 `TODO(PDF)` 로 선택지를 적어뒀습니다
- 홈의 「AI 한줄 요약」 미구현. `EMOTION_RISK_SCORES` 가 채워진 뒤에 붙입니다
- AI 추론 서버 본체 (모델링 영역)

# 2026.07.31 (23차) — lifelog·chat 라우터, 위기 탐지 2단계 구현

## lifelog — 앱 push 수신

`POST /lifelog/batch` 가 `MLCM_200` 의 핵심입니다. `(user_id, collected_at)` UNIQUE 기준 **PostgreSQL `ON CONFLICT DO UPDATE`** 로 적재합니다.

**검증에서 UPSERT 가 실제로 동작하는 것을 확인했습니다.** 같은 `collected_at` 으로 재전송하니 행이 늘지 않고 `steps` 가 3200 → 9999 로 갱신됐습니다. 전송 실패 후 재시도로 같은 시각이 다시 와도 중복이 생기지 않습니다.

- **`last_synced_at` 은 서버가 확정해 응답으로 돌려줍니다.** 앱이 자기 시계로 갱신하면 단말 시간이 틀어졌을 때 그 구간이 영구 유실됩니다
- 배치 상한 200건, 초과 시 **413**. 서버가 잘라내면 유실이 조용히 생깁니다
- 체성분은 측정 시점에만 발생해 주기가 달라 별도 엔드포인트로 분리했습니다. 15분 배치에 섞으면 빈 값뿐인 행이 쌓입니다
- 조회는 최신순 고정입니다. 정렬 파라미터를 열면 `(user_id, collected_at DESC)` 복합 인덱스와 어긋납니다

## chat — 위기 탐지 2단계

`CLAUDE.md` 의 LLM 작업 규칙을 밟았습니다. `PROMPT_REFERENCE.md`·`USAGE_LOG.md` 를 읽고 **`openaiDeveloperDocs` MCP 로 공식 문서를 조회**한 뒤 구현했습니다. 상세는 [`../llm/USAGE_LOG.md`](../llm/USAGE_LOG.md) LLM-002.

확인한 계약 — 현재는 **Responses API** 입니다. `client.responses.parse(model=..., input=[...], text_format=PydanticModel)` → `response.output_parsed`.

| 파일 | 역할 |
|---|---|
| `data/crisis_keywords.json` | 1차 키워드 사전. 03-B 요구대로 설정 파일로 분리 |
| `services/safety.py` | PII 마스킹 + 키워드 스캔. **외부 API 무의존** |
| `services/llm.py` | 페르소나 응답 · 위기 판정 · 세션 요약 |
| `api/v1/chat.py` | 세션·메시지·기록 조회/삭제 |

### `NFR-DV-003` fallback 이 실증됐습니다

`OPENAI_API_KEY` 가 없는 상태로 검증했는데 **LLM 호출이 전부 실패했는데도 키워드 필터가 단독 동작해 위기를 잡았습니다.**

| 입력 | 판정 | 근거 |
|---|---|---|
| 일상 발화 | `NORMAL` / `CHAT` | KEYWORD |
| "지쳤고 아무도 없는" | `CAUTION` / `CONTENT` | KEYWORD |
| "다 사라지고 싶어, 죽고 싶다" | **`CRITICAL` / `EMERGENCY`** | KEYWORD |

`CRITICAL` 일 때 `reply` 가 `null` 인 것도 확인했습니다. 병렬로 생성된 일반 응답을 서버가 버립니다.

응답의 `source` 필드로 **문맥 판단을 거친 결과인지 키워드 단독 판정인지 구분**할 수 있게 했습니다. `NFR-DV-003` 이 요구하는 "판정 근거를 로그에 기록" 을 API 응답으로도 노출한 셈입니다.

### 설계 판단

- **스트리밍(SSE)을 쓰지 않습니다.** LLM 챗의 실무 표준이지만, 위기 판정 전에 흘린 글자는 회수할 수 없습니다. `CRITICAL` 인데 이미 나간 문장이 남으면 안전 기능이 무력화됩니다
- 위기 판정과 응답 생성을 `asyncio.gather` 로 **병렬** 호출합니다. 순차면 OpenAI 왕복 2회라 `NFR-DV-001` 3초를 넘깁니다
- 안전 가이드라인을 페르소나와 무관하게 시스템 프롬프트에 고정했습니다 — `FR-AI-005`
- 키워드 사전에 `죽겠다` 를 **넣지 않았습니다.** "배고파 죽겠다" 오탐이 과도합니다. `죽고 싶`·`죽어버리` 같은 의도 표현만 넣었습니다

## 미검증 — 반드시 남은 것

**LLM 경로(2차 문맥 판정)는 확인하지 못했습니다.** API 키가 없어 키워드 fallback 만 돌았습니다. 키 설정 후 재평가가 필요하고, 특히 **관용 표현("배고파 죽겠다")을 LLM 이 걸러내는지** 확인해야 합니다. 지금은 키워드에서 그 표현을 뺐기 때문에 통과하지만, LLM 이 붙으면 판정이 달라질 수 있습니다.

# 2026.07.31 (22차) — users·devices 라우터, 연락처 컬럼 암호화

## 구현

## 연락처 암호화를 실제로 걸었다

인증 구현 때 TODO 로 남겼던 `02-F`(3) 입니다. 검증 결과 **DB 에는 `PTCzGg3BNGxD...` 로 저장되고 API 응답에서는 `010-1234-5678` 로 복호화**됩니다.

암호화 대상은 `USERS.phone` **하나뿐**입니다. 라이프로그·체성분 측정치는 기간별 집계와 복합 인덱스가 서비스의 핵심 동작이라 컬럼 암호화를 적용하면 기능 자체가 불가능해집니다 — `02-F`(6) 의 근거를 코드 주석에도 남겼습니다.

## 이 과정에서 버그 2건 — 뿌리는 하나

1. **signup 이 `phone` 을 평문으로 저장**하고 있었습니다. TODO 로 표시해둔 그 자리입니다
2. 그래서 `GET /users/me` 가 평문을 복호화하려다 **500** 이 났습니다

`decrypt()` 가 실패할 때 **조용히 원문을 돌려주지 않고 명시적으로 예외를 던지도록** 했습니다. 원문을 반환하면 평문 저장이 정상인 것처럼 보여 같은 사고가 반복됩니다.

> ⚠ 암호화 도입 전에 만든 계정은 `phone` 이 평문이라 `/users/me` 가 실패합니다. 개발 DB 이므로 해당 행을 지우면 됩니다.

## 설계 판단 3건

- **연동 재등록은 새 행을 만들지 않고 기존 행을 갱신**합니다. 앱이 권한을 재승인할 때마다 행이 쌓이면 `last_synced_at` 이 어느 행 기준인지 알 수 없게 됩니다. 검증에서 같은 `connection_id` 가 유지되는 것을 확인했습니다
- 연동 조회·수정 쿼리에 **`user_id` 를 함께 겁니다.** 타인의 `connection_id` 로 접근하면 404 입니다
- `PATCH /users/me` 는 `exclude_unset` 을 씁니다. 안 쓰면 "안 보낸 필드"와 "비우려는 필드"를 구분할 수 없어 `phone` 이 통째로 날아갑니다

## 검증

실제 서버로 확인했습니다.

- 프로필 조회 — `phone` 복호화 · `height_cm` · `role` · `persona_type` 정상
- 페르소나 변경 시 `phone` 유지
- 비밀번호 변경 현재 비밀번호 불일치 400
- 연동 등록 → 같은 플랫폼 재등록 시 동일 `connection_id`
- 항목별 동의 철회 반영 · 타인 연동 접근 404

## 남은 것

### 반복되는 감사 패턴 4가지

같은 종류의 결함이 계속 나왔습니다. 새 문서를 검수할 때 먼저 의심할 지점입니다.

1. **같은 주장이 여러 절에 반복** — `01-N`(방법론↔3장) · `01-O④`(기대효과↔활용방안) · `01-P①`(유사서비스↔차별성) · `01-Q`(주요기술↔사용기술) · `01-R`(1장↔6장 기대효과)
   - **절을 지우는 게 답이 아닌 경우가 있습니다.** 「차별성」처럼 장을 닫는 종합 절이나 1장의 양식 칸은 위치상 필요하므로, 반복된 문장을 뒤 장 참조로 바꾸고 고유 정보만 남깁니다
   - **개요 장(1장)이 특히 위험합니다.** 개요는 뒤 장을 미리 요약하는 성격이라, 뒤 장을 채우면서 1장을 줄이지 않으면 그대로 중복이 됩니다
2. **다른 칸이 이미 말하는 것을 비고에 재진술** — 단위 17칸 · `PK UUID` 8곳 · `gen_random_uuid()` 8곳 · 테이블설명의 컬럼 나열 · `05-R②`(NN 칸이 말하는 "선택 입력")
3. **출처와 함께 제시한 수치를 요약 표에서 다시 인용** — `01-P②`(STP 의 18.3%/19.59%) · `01-R`(1장 기대효과의 80.3%/51.1%)
4. **출처 없는 정량 주장** — `01-U`(경쟁사 "세션당 평균 1~2분"). 참고문헌 9건에도 2장 유사 서비스 분석에도 근거가 없었습니다

### 비고·설명 칸을 채우려고 채우지 마세요

**칸이 있으면 채워야 한다는 압박이 실제로 문서를 나쁘게 만들었습니다.** 단위 17칸, `PK UUID` 8곳, `gen_random_uuid()` 8곳이 모두 그 결과입니다.

- **적을 것** — 그 칸 말고는 알 수 없는 것. 값 범위, enum 값, 참조 대상, 구현 방법, 설계 근거
- **적지 말 것** — 컬럼명·타입·제약 칸이 이미 말하는 것, 04 에 전체 원칙으로 선언된 것, 다른 칸 서술의 재진술

**비워두는 게 정상입니다.** 최종적으로 79개 컬럼 중 28개만 채워졌고 51개가 빈칸입니다.

## `SD-E1` — `USERS.role` 신설

관리자 로그인 화면이 필요한지 따지다 더 큰 문제를 발견했습니다. **관리자 기능이 `MLCM_501`·`FR-MN-003`·`MLCM_510`·04 접근통제·발표자료 slide5 에 모두 있는데 `USERS` 에 `role` 도 `is_admin` 도 없었습니다.** 어떤 계정이 관리자인지 판별할 수단이 없어 `MLCM_501` 을 구현할 수 없는 상태였습니다.

```sql
role VARCHAR(20) NOT NULL DEFAULT 'USER' CHECK (role IN ('USER', 'ADMIN'))
```

`DEFAULT 'USER'` 로 회원가입 흐름을 건드리지 않습니다(`05-C` 와 같은 방식). 관리자는 일반 가입 후 `UPDATE` 로 승격합니다.

**별도 관리자 테이블은 채택하지 않았습니다.** 로그인 로직·JWT 발급 경로·비밀번호 정책이 각각 둘이 되어, 관리자 한두 명 때문에 인증 체계를 복제하는 셈입니다. 분리가 정당화되는 건 인증 경로가 물리적으로 분리돼야 하거나(별도 도메인·외부 IdP), 관리자 속성이 전혀 다르거나, 규제상 요구될 때인데 셋 다 해당하지 않습니다.

**부수 효과** — `02-F`(6) 의 *"접근통제(본인 및 권한 있는 관리자로 제한)"* 라는 방어 논리가 지금까지 판별 수단 없이 떠 있었는데, 이 컬럼으로 성립하게 됐습니다.

### AES-256-GCM 비용 — 확인 결과

| 항목 | 비용 |
|---|---|
| 라이선스·서비스 요금 | **0원.** 표준 알고리즘이며 Python `cryptography` · Node `crypto` 내장. 클라우드 KMS 를 쓸 때만 과금되고 본 과제는 미사용 |
| 연산 | **무시 가능.** AES-NI 하드웨어 명령으로 초당 GB 단위. 전화번호 20바이트는 마이크로초 |
| 저장 용량 | 20자 → Base64 약 64자. 3배지만 절대량이 미미 |
| 실제 부담 | **키 관리 설계.** `.env` 에 두면 DB 유출은 막지만 서버 유출은 못 막음. IV 는 매 암호화마다 새로 생성해 암호문과 함께 저장(GCM 은 IV 재사용이 치명적) |

## 타입을 `TIMESTAMPTZ` 로 한 이유

2. **자정을 넘긴 활동 구간**을 `TIME` 으로는 표현할 수 없습니다(종료 < 시작). 수면 컬럼이 `TIMESTAMPTZ` 인 이유와 같습니다.

## 산소포화도(SpO2) — 수집하지 않음

**컬럼을 만들지 않고, 보존도 하지 않습니다.**

> 처음에는 `raw_payload`(JSONB) 에 원본으로 담아두는 절충안을 검토했으나, **`05-G` 로 `raw_payload` 자체가 삭제되어 보존 경로가 없습니다.** 활동 시각도 JSONB 절충안이 아니라 정식 컬럼(`05-E`)으로 갔습니다. 같은 판단 기준을 적용하면 SpO2 는 **정식 컬럼으로 넣거나 아예 받지 않는 것** 둘 중 하나이며, 아래 근거로 후자를 택합니다.

**근거 4가지**

1. **정서와 직접 연관이 약합니다.** SpO2 는 본래 호흡기·심혈관 지표이고, 정신건강으로 오는 경로는 *수면무호흡 → 수면 질 저하 → 우울·피로* 로 **한 단계를 경유하는 간접 경로**입니다.
2. **그 경로가 이미 커버돼 있습니다.** `deep_sleep_min` · `light_sleep_min` · `rem_sleep_min` · `awake_min` · `sleep_onset_min` · `sleep_efficiency_pct` 로 수면 질을 상세히 받고 있어 정보가 중복됩니다.
3. **학습 데이터에 SpO2 가 없습니다.** PMData · GLOBEM · 기업 제공 데이터 어디에도 없습니다. **GLOBEM 스크린타임 문제의 반대 방향**입니다 — 그때는 학습엔 있고 서비스가 못 만드는 피처였고, 이건 서비스는 받는데 학습 데이터에 없는 피처입니다. **둘 다 모델이 쓸 수 없습니다.**
4. **측정 신뢰도.** 손목 광학 센서 SpO2 는 의료기기 대비 오차가 크고 야간 자동 측정 결측이 많습니다. 기기·앱에 따라 데이터 유무도 갈립니다.

**시점 비용도 고려했습니다.** 컬럼 하나를 추가하면 `db/schema.sql` · 05 컬럼 정의표 · 05 CREATE 스크립트 · 04 객체 정의서 · 02 수집 항목·동의 항목 · 03 데이터 정의 및 JSON 샘플까지 **다시 열어야** 하고, 붙여넣기 사고(마크다운 기호 · 스마트 따옴표 · 고치다 한 글자 더 지움)가 재발할 위험이 있습니다.

## 4-3. 팀 공용 DB — 캠퍼스 공용 PostgreSQL 확보

각자 로컬 DB 를 쓰면 5주차 통합 테스트 시점에 스키마 불일치가 터지는 문제가 있었습니다.

Neon·Supabase 등 외부 클라우드는 검토 대상에서 제외합니다.

> **🔑 접속 정보는 저장소에 두지 않습니다.**
> 이 저장소는 **공개(public)** 라 커밋하는 순간 노출되고, 삭제해도 커밋 히스토리에 남습니다.
> 접속 정보는 **단톡방 고정 공지**와 **Notion 프로젝트 페이지**에만 둡니다.

**운영 규칙**

- **`db/schema.sql` 은 PM(이응균)이 1회만 실행합니다.** 공용 DB 라 각자 실행하면 `CREATE TABLE` 이 충돌합니다. 현재 스크립트에 `IF NOT EXISTS` 가 없습니다.
- 애플리케이션 코드에 접속 정보를 직접 쓰지 않고 **`.env` 로 분리**합니다. `.gitignore` 에 이미 포함되어 있습니다.
- **포트가 기본값(5432)이 아닙니다.** DBeaver·psql 접속 시 공지의 포트로 바꿔야 합니다. 접속 실패 문의의 대부분이 여기서 발생합니다.

> **⚠ 스키마 실행 전 확인** — `db/schema.sql` 이 `gen_random_uuid()` 를 쓰는데 이는 PostgreSQL 13 이상에서만 내장 함수입니다. 캠퍼스 서버 버전이 낮으면 `CREATE EXTENSION IF NOT EXISTS pgcrypto;` 를 먼저 실행해야 합니다. 접속 후 `SELECT version();` 으로 확인하세요.

## 02-C. 위기탐지·응답생성 — 병렬 호출 채택

**응답 속도를 우선하여 병렬(비동기 동시 호출) 구조로 확정합니다.** 순차 호출은 OpenAI 왕복이 2회가 되어 3초 응답 요건을 넘길 가능성이 높고, 별도 지표인 위기 탐지 1.5초 요건과도 충돌합니다.

### CAUTION 처리 — 재생성하지 않음

병렬 구조에서는 공감 응답이 위기 판정 *전에* 이미 생성되므로, 페르소나가 부정 감정 맥락을 모른 채 답한 문장이 나갑니다. **재생성하지 않고 그대로 사용하며, 감정별 힐링 콘텐츠 추천을 함께 노출**합니다.

- CAUTION 은 CRITICAL 과 달리 즉각적 위험 상황이 아니라, 지연을 2배로 늘려 재생성할 이유가 약합니다.
- 대신 **페르소나 시스템 프롬프트에 부정 감정 공감 톤을 상시 포함**시켜, 맥락을 몰라도 크게 빗나가지 않도록 설계합니다. 이것이 MLCM_400 의 "위로 대화와 함께 콘텐츠 추천" 요건을 지연 없이 충족하는 방법입니다.

### API 비용 — 2배 감수, 다만 관리

매 턴 호출이 2회가 되어 비용이 2배입니다. 속도를 우선하기로 했으므로 감수하되 아래로 증가폭을 줄입니다.

1. **1차 키워드 필터에 걸리면 공감 응답 생성을 호출하지 않습니다.** 어차피 위기 UI 로 전환되어 쓰지 않을 응답입니다.
2. 위기 탐지 호출은 판정 JSON 만 받으므로 `max_tokens` 를 작게 잡습니다.

> **발표 대비** — "왜 호출을 2번 하나요"에 대한 답은 **"안전 기능을 응답 생성에 종속시키지 않기 위해 독립 호출로 분리했다"** 입니다. 순차로 묶으면 응답 생성이 실패할 때 위기 탐지도 함께 실패합니다. 비용이 아니라 안전 설계의 문제로 프레이밍하세요.

## 1-1. 미수신 판정 임계 — 3시간

`DEVICE_HEALTH_CONNECTIONS.last_synced_at` 이 **3시간 이상** 갱신되지 않으면 미수신으로 감지하고 FCM 무음 푸시를 발송합니다.

- 더 짧으면(예: 30분) Doze 모드의 정상 지연에도 푸시가 나가 배터리·비용이 낭비됩니다.
- 더 길면(예: 12시간) 15분 주기 수집의 의미가 흐려집니다.
- 라이프로그 분석이 최근 14일 개인별 정규화를 전제하므로, 3시간 단위 결측은 분석을 막지 않습니다.
