# 2026.07.30 (10차) — `05-S` `LIFELOG_METRICS` 컬럼 순서 반영 확인

HWP 재편집 후 Python 이 없어 `tools/hwp2txt.ps1` 로 재추출해 확인했습니다. 이 도구는 표 구조(행·열 경계)가 무너지지만, 컬럼명·타입·비고가 테이블마다 고유해서 **선형 텍스트에 등장하는 순서만으로 행 순서를 추적하는 데는 문제가 없었습니다.**

컬럼 정의표가 권장 순서로 정확히 재배열됐습니다.

> `metric_id` → `user_id` → `steps` → `distance` → `calories` → `activity_start_at` → `activity_end_at` → `total_active_min` → `sleep_start_at` → `sleep_end_at` → `total_sleep_min` → `deep_sleep_min` → `light_sleep_min` → `rem_sleep_min` → `awake_min` → `sleep_onset_min` → `sleep_efficiency_pct` → `heart_rate` → `hrv` → `collected_at`

옮긴 5개 행(`distance`·`calories`·`activity_start_at`·`activity_end_at`·`total_active_min`)의 NN/PK/FK/UK/CK·비고가 원래 값 그대로 붙어왔고, 컬럼 개수도 20개로 그대로입니다. CREATE 스크립트는 손대지 않아 `db/schema.sql` 과 계속 일치합니다. 새 텍스트에서 마크다운 기호·스마트따옴표 오염은 0건입니다.

`05-N③`(작성일자 8곳, 2026.07.29 → 07.30)은 아직 `2026.07.29` 그대로입니다 — 체크리스트가 "마지막에 처리"로 지정한 항목이라 이 시점에 안 된 것이 정상입니다.

## 프론트엔드는 문서에 맞춘다

Flutter 앱을 열어보니 **화면설계서를 참조하지 않고 만들어져 있었습니다.** 화면 7개가 구현돼 있는데 문서의 화면 목록과 구성·기능 범위가 다르고, `pubspec.yaml` 의존성이 `flutter` + `cupertino_icons` 뿐이라 **API 연동 코드가 0줄**입니다.

처음에는 "앱이 문서보다 앞서 있다"고 봤습니다(회원가입에 연락처 입력란이 있고 민감정보 동의가 분리돼 있어 `SD-A②③` 이 이미 반영된 것처럼 보였음). **틀린 판단이었습니다.** 문서를 안 보고 만든 것이라 우연히 맞은 것이고, 근거로 삼을 수 없습니다.

**앱이 아니라 문서가 정본이며, 앱을 문서에 맞춰 재구축합니다.**

## `SD-E1` — `USERS.role` 신설

관리자 로그인 화면이 필요한지 따지다 더 큰 문제를 발견했습니다. **관리자 기능이 `MLCM_501`·`FR-MN-003`·`MLCM_510`·04 접근통제·발표자료 slide5 에 모두 있는데 `USERS` 에 `role` 도 `is_admin` 도 없었습니다.** 어떤 계정이 관리자인지 판별할 수단이 없어 `MLCM_501` 을 구현할 수 없는 상태였습니다.

```sql
role VARCHAR(20) NOT NULL DEFAULT 'USER' CHECK (role IN ('USER', 'ADMIN'))
```

`DEFAULT 'USER'` 로 회원가입 흐름을 건드리지 않습니다(`05-C` 와 같은 방식). 관리자는 일반 가입 후 `UPDATE` 로 승격합니다.

**별도 관리자 테이블은 채택하지 않았습니다.** 로그인 로직·JWT 발급 경로·비밀번호 정책이 각각 둘이 되어, 관리자 한두 명 때문에 인증 체계를 복제하는 셈입니다. 분리가 정당화되는 건 인증 경로가 물리적으로 분리돼야 하거나(별도 도메인·외부 IdP), 관리자 속성이 전혀 다르거나, 규제상 요구될 때인데 셋 다 해당하지 않습니다.

**부수 효과** — `02-F`(6) 의 *"접근통제(본인 및 권한 있는 관리자로 제한)"* 라는 방어 논리가 지금까지 판별 수단 없이 떠 있었는데, 이 컬럼으로 성립하게 됐습니다.

## `01-P` — 「차별성」 절: 삭제에서 재작성으로

처음에는 **절을 지우자**고 했습니다. 「유사 서비스 분석 및 비교」가 경쟁사 3곳과 대조해 비교표까지 만들어 근거를 완성했고 `STP Positioning` 이 그것을 한 줄로 선언하니, 「차별성」은 그 사이의 중간 요약이라는 판단이었습니다.

**틀린 판단이었습니다.** 2장이 `시장 현황 → 유사 서비스 분석 → SWOT → STP → 차별성` 으로 흐르는데, 「차별성」을 빼면 장이 **STP 표에서 끝납니다.** 표는 전략을 나열할 뿐 장을 닫지 못합니다. 「차별성」은 앞 항목들을 최종 정리하는 위치이므로 구조상 필요합니다.

**반복이라는 지적 자체는 유효했지만 답이 삭제가 아니었습니다.** 반복된 문장을 앞 절 참조로 바꾸고, 빈 자리를 앞 절에 없는 내용으로 채우는 재작성으로 전환했습니다.

| | 처리 |
|---|---|
| `수집·분석·대응 통합` | `근본적 차별화` 재주장을 빼고 **"앞의 비교에서 확인한 바와 같이"** 로 앞 절 참조. 종합 절의 어법 |
| `선택형 페르소나와 멀티모달 대화` | `MBTI형 T/F` · `음성(STT/TTS)` 는 「유사 서비스 분석」에 **없는 정보**여서 독립 항목으로 승격 |
| `위험 단계별 대응 분기` | **신규.** 유사 서비스 분석 표가 Wysa 를 `△`(위기 발화 감지·안전 안내)로 표기했는데 **왜 `△` 인지는 표에서 드러나지 않음.** `주의 → 콘텐츠 추천` vs `심각 → 109 전환` 의 대비가 그 자리를 채움 |

`STP Targeting` 의 `(18.3%, 19.59%)` 도 제거했습니다. 「시장 현황」에서 출처와 함께 이미 제시한 수치를 요약 표에서 괄호로 다시 쓰면 **근거 없이 숫자만 반복**됩니다. 반면 `Segmentation` ↔ `Positioning` 의 `상담 부담` / `상담 장벽 낮춤` 은 **문제·해법 쌍이라 STP 구조상 자연스러워** 그대로 뒀습니다.

| 라이선스·서비스 요금 | **0원.** 표준 알고리즘이며 Python `cryptography` · Node `crypto` 내장. 클라우드 KMS 를 쓸 때만 과금되고 본 과제는 미사용 |

## 타입을 `TIMESTAMPTZ` 로 한 이유

메타데이터는 `hh:mm:ss` 로 제공되지만 `TIME` 을 쓰지 않았습니다.

1. **04 문서 `2) 식별자 및 시각 컬럼 표준화`** 가 "모든 날짜/시간 컬럼은 TIMESTAMPTZ 로 통일"을 이미 규정합니다. `TIME` 은 우리가 정한 표준을 스스로 깨는 셈입니다.
2. **자정을 넘긴 활동 구간**을 `TIME` 으로는 표현할 수 없습니다(종료 < 시작). 수면 컬럼이 `TIMESTAMPTZ` 인 이유와 같습니다.

**NULL 허용**입니다. PMData·GLOBEM 과 Health Connect 일부 구간에 활동 시각이 없으므로, 분석은 값이 있는 구간에 한해 수행합니다.

## 산소포화도(SpO2) — 수집하지 않음

**컬럼을 만들지 않고, 보존도 하지 않습니다.**

> 처음에는 `raw_payload`(JSONB) 에 원본으로 담아두는 절충안을 검토했으나, **`05-G` 로 `raw_payload` 자체가 삭제되어 보존 경로가 없습니다.** 활동 시각도 JSONB 절충안이 아니라 정식 컬럼(`05-E`)으로 갔습니다. 같은 판단 기준을 적용하면 SpO2 는 **정식 컬럼으로 넣거나 아예 받지 않는 것** 둘 중 하나이며, 아래 근거로 후자를 택합니다.

**근거 4가지**

1. **정서와 직접 연관이 약합니다.** SpO2 는 본래 호흡기·심혈관 지표이고, 정신건강으로 오는 경로는 *수면무호흡 → 수면 질 저하 → 우울·피로* 로 **한 단계를 경유하는 간접 경로**입니다.
2. **그 경로가 이미 커버돼 있습니다.** `deep_sleep_min` · `light_sleep_min` · `rem_sleep_min` · `awake_min` · `sleep_onset_min` · `sleep_efficiency_pct` 로 수면 질을 상세히 받고 있어 정보가 중복됩니다.
3. **학습 데이터에 SpO2 가 없습니다.** PMData · GLOBEM · 기업 제공 데이터 어디에도 없습니다. **GLOBEM 스크린타임 문제의 반대 방향**입니다 — 그때는 학습엔 있고 서비스가 못 만드는 피처였고, 이건 서비스는 받는데 학습 데이터에 없는 피처입니다. **둘 다 모델이 쓸 수 없습니다.**
4. **측정 신뢰도.** 손목 광학 센서 SpO2 는 의료기기 대비 오차가 크고 야간 자동 측정 결측이 많습니다. 기기·앱에 따라 데이터 유무도 갈립니다.

**시점 비용도 고려했습니다.** 컬럼 하나를 추가하면 `db/schema.sql` · 05 컬럼 정의표 · 05 CREATE 스크립트 · 04 객체 정의서 · 02 수집 항목·동의 항목 · 03 데이터 정의 및 JSON 샘플까지 **다시 열어야** 하고, 붙여넣기 사고(마크다운 기호 · 스마트 따옴표 · 고치다 한 글자 더 지움)가 재발할 위험이 있습니다.

**따라서 평가셋 200건은 전량 팀 자체 작성이며, `02-B` 의 "프롬프트 설계자와 분리된 인원이 작성" 요건은 선택이 아니라 필수입니다.**

## 4-3. 팀 공용 DB — 캠퍼스 공용 PostgreSQL 확보

각자 로컬 DB 를 쓰면 5주차 통합 테스트 시점에 스키마 불일치가 터지는 문제가 있었습니다.
**학교에서 제공하는 공용 PostgreSQL 인스턴스를 받아 이 문제가 해소되었습니다.**
Neon·Supabase 등 외부 클라우드는 검토 대상에서 제외합니다.

> **🔑 접속 정보는 저장소에 두지 않습니다.**
> 이 저장소는 **공개(public)** 라 커밋하는 순간 노출되고, 삭제해도 커밋 히스토리에 남습니다.
> 접속 정보는 **단톡방 고정 공지**와 **Notion 프로젝트 페이지**에만 둡니다.

**운영 규칙**

- **`db/schema.sql` 은 PM(이응균)이 1회만 실행합니다.** 공용 DB 라 각자 실행하면 `CREATE TABLE` 이 충돌합니다. 현재 스크립트에 `IF NOT EXISTS` 가 없습니다.
- 애플리케이션 코드에 접속 정보를 직접 쓰지 않고 **`.env` 로 분리**합니다. `.gitignore` 에 이미 포함되어 있습니다.
- **포트가 기본값(5432)이 아닙니다.** DBeaver·psql 접속 시 공지의 포트로 바꿔야 합니다. 접속 실패 문의의 대부분이 여기서 발생합니다.

> **⚠ 스키마 실행 전 확인** — `db/schema.sql` 이 `gen_random_uuid()` 를 쓰는데 이는 PostgreSQL 13 이상에서만 내장 함수입니다. 캠퍼스 서버 버전이 낮으면 `CREATE EXTENSION IF NOT EXISTS pgcrypto;` 를 먼저 실행해야 합니다. 접속 후 `SELECT version();` 으로 확인하세요.

[개인정보 보호법 제17조 제2항](https://www.law.go.kr/lsLawLinkInfo.do?lsJoLnkSeq=900078379&chrClsCd=010202)은 제3자 제공 동의 시 아래를 알리도록 합니다.

## 02-C. 위기탐지·응답생성 — 병렬 호출 채택

**응답 속도를 우선하여 병렬(비동기 동시 호출) 구조로 확정합니다.** 순차 호출은 OpenAI 왕복이 2회가 되어 3초 응답 요건을 넘길 가능성이 높고, 별도 지표인 위기 탐지 1.5초 요건과도 충돌합니다.

### CAUTION 처리 — 재생성하지 않음

병렬 구조에서는 공감 응답이 위기 판정 *전에* 이미 생성되므로, 페르소나가 부정 감정 맥락을 모른 채 답한 문장이 나갑니다. **재생성하지 않고 그대로 사용하며, 감정별 힐링 콘텐츠 추천을 함께 노출**합니다.

- CAUTION 은 CRITICAL 과 달리 즉각적 위험 상황이 아니라, 지연을 2배로 늘려 재생성할 이유가 약합니다.
- 대신 **페르소나 시스템 프롬프트에 부정 감정 공감 톤을 상시 포함**시켜, 맥락을 몰라도 크게 빗나가지 않도록 설계합니다. 이것이 MLCM_400 의 "위로 대화와 함께 콘텐츠 추천" 요건을 지연 없이 충족하는 방법입니다.

### API 비용 — 2배 감수, 다만 관리

매 턴 호출이 2회가 되어 비용이 2배입니다. 속도를 우선하기로 했으므로 감수하되 아래로 증가폭을 줄입니다.

1. **1차 키워드 필터에 걸리면 공감 응답 생성을 호출하지 않습니다.** 어차피 위기 UI 로 전환되어 쓰지 않을 응답입니다.
2. 위기 탐지 호출은 판정 JSON 만 받으므로 `max_tokens` 를 작게 잡습니다.

> **발표 대비** — "왜 호출을 2번 하나요"에 대한 답은 **"안전 기능을 응답 생성에 종속시키지 않기 위해 독립 호출로 분리했다"** 입니다. 순차로 묶으면 응답 생성이 실패할 때 위기 탐지도 함께 실패합니다. 비용이 아니라 안전 설계의 문제로 프레이밍하세요.

## 1-1. 미수신 판정 임계 — 3시간

`DEVICE_HEALTH_CONNECTIONS.last_synced_at` 이 **3시간 이상** 갱신되지 않으면 미수신으로 감지하고 FCM 무음 푸시를 발송합니다.

- 더 짧으면(예: 30분) Doze 모드의 정상 지연에도 푸시가 나가 배터리·비용이 낭비됩니다.
- 더 길면(예: 12시간) 15분 주기 수집의 의미가 흐려집니다.
- 라이프로그 분석이 최근 14일 개인별 정규화를 전제하므로, 3시간 단위 결측은 분석을 막지 않습니다.

푸시 이후에도 수신되지 않는 구간은 결측 처리하고, 분석 파이프라인은 해당 구간을 제외하고 동작합니다.
