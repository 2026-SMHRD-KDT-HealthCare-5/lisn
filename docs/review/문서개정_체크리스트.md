## 02-A. NFR-DV-003 — 위기 탐지 독립 동작 보장 **[교체]** ⭐

**문제** 위기 탐지 2차 판정을 OpenAI에 의존하기로 확정한 이상, 현재의 "독립적 동작 보장"은 **지킬 수 없는 보장**입니다. 안전 기능에 대한 미이행 보장은 심사에서 가장 취약한 지점입니다.

**현재**
> OpenAI API 응답 실패/타임아웃 시 최대 2회 재시도 후 정형화된 대체 응답을 제공하며, 위기 문맥 탐지 로직은 API 장애와 무관하게 독립적으로 동작함을 보장

**교체**
> OpenAI API 응답 실패/타임아웃 시 최대 2회 재시도 후 페르소나 톤에 맞춘 정형화된 대체 응답을 제공한다.
> 위기 문맥 탐지는 1차 키워드 기반 규칙 필터와 2차 LLM 문맥 분석의 2단계로 구성되며, 2차 분석이 불가능한 상황(API 장애·타임아웃)에서도 1차 키워드 필터는 백엔드 내부에서 독립적으로 동작하여 탐지 기능이 완전히 중단되지 않도록 보장한다.
> 이 경우 문맥 판단이 불가능하므로 미탐(False Negative)을 최소화하는 방향의 보수적 임계치를 적용하며, 오탐(False Positive)을 허용한다. 안전 기능의 특성상 위기를 놓치는 비용이 불필요한 안내를 노출하는 비용보다 크다는 원칙에 따른다.
> 또한 2차 분석 실패 사실을 로그에 기록하여 사후 검토가 가능하도록 한다.

## 02-B. NFR-AI-001 — 위기 탐지 성능 기준 **[교체]** ⭐

**문제** 프롬프트 기반 판정은 학습 과정이 없어 Train/Validation/Test 분할이 존재하지 않습니다. 측정 대상과 방법이 없으면 0.88은 **검증 불가능한 선언**이 됩니다.

**현재**
> LSTM Autoencoder+LightGBM 기반 위험도 분류 모델은 정확도(Accuracy) 85% 이상, F1-Score 0.80 이상을 목표로 하며, 위기 문맥 탐지 모델은 F1-Score 0.88 이상을 목표로 함

**교체**
> LSTM Autoencoder + LightGBM 기반 위험도 분류 모델은 정확도(Accuracy) 85% 이상, F1-Score 0.80 이상을 목표로 한다.
> 위기 문맥 탐지는 별도 학습 모델이 아닌 키워드 규칙 + LLM 프롬프트 기반 판정 로직으로 구현하므로, 성능은 자체 구축한 고정 평가셋(위기 발화·비위기 발화 각 100건 내외, 총 200건 이상)에 대한 판정 결과로 측정한다.
> 목표 지표는 재현율(Recall) 90% 이상, F1-Score 0.85 이상으로 하며, 안전 기능 특성상 정밀도(Precision)보다 재현율을 우선한다.
> **평가셋은 판정 프롬프트 설계자와 분리된 인원이 작성하며**, 라벨링 기준과 평가 결과를 별도 부록으로 관리한다.

> **⚠ 굵게 표시한 문장을 반드시 넣으세요.** 프롬프트를 만든 사람이 평가 문장도 쓰면 자기가 상정한 표현만 평가셋에 들어가서 Recall 90%가 자동으로 나옵니다. "그 평가셋은 누가 만들었나요" 질문 하나로 지표 전체가 무너집니다.
>
> **목표치 0.88 → 0.85 하향**은 프롬프트 방식의 특성을 반영한 것입니다. 0.88을 유지하고 싶다면 그대로 두되, 평가셋 규모가 작을수록 지표 변동이 크다는 점을 발표에서 언급하세요.

## 02-F. NFR-DE-002 — 암호화 정책 **[교체]** ⭐⭐

**문제** 암호화된 컬럼은 범위 조회·정렬·집계·인덱스가 불가능합니다. 그런데 04 문서 5항은 `(user_id, collected_at DESC)` 복합 인덱스를 **필수**로 규정하고, MLCM_210은 최근 14일 개인별 정규화를 전제합니다. **동일 산출물 내 요건이 상호 모순**입니다.

**교체**
> 민감 데이터는 유출 시 피해 규모와 조회 요건을 함께 고려하여 위험도 기반의 계층적 보호 체계를 적용한다.
> **(1) 전송 구간 보호** — 앱↔백엔드, 백엔드↔AI 서버 간 모든 API 통신에 HTTPS/TLS를 적용한다.
> **(2) 저장 매체 보호** — 클라우드 환경에 배포하는 경우 데이터베이스 볼륨의 디스크 암호화 옵션을 활성화한다.
> **(3) 컬럼 단위 암호화(AES-256-GCM)** — 유출 시 즉각적인 2차 피해가 발생하는 항목(연락처, 외부 서비스 인증 토큰이 도입될 경우 해당 토큰)에 한해 적용한다.
> **(4) 단방향 해시** — 비밀번호는 Bcrypt/Argon2로 저장하며 복호화하지 않는다.
> **(5) 마스킹** — 챗봇 대화 저장 시 성명·전화번호·주소 등 개인식별정보를 정규식 기반으로 [MASK] 치환한 후 JSONB로 저장한다.
> **(6) 컬럼 암호화 제외 항목 및 근거** — 라이프로그 측정치, 체성분 측정치, 분석 스코어는 시계열 범위 조회·기간별 집계·복합 인덱스 활용이 서비스의 핵심 동작에 해당하여 컬럼 단위 암호화 적용 시 기능 구현이 불가능하다. 해당 항목은 (1)(2)의 보호와 접근통제(본인 및 권한 있는 관리자로 제한)로 보호한다. 측정치 테이블 자체에는 실명·연락처가 존재하지 않으므로 부분 유출 시 식별 위험이 제한되며, 동일 DB 내 조인으로는 식별이 가능하므로 접근통제를 주된 통제수단으로 삼는다.
> **(7) 성능 요건** — 암호화·복호화 처리로 인한 API 응답 지연 증가는 200ms 이내로 유지한다.
> **(8) 음성 데이터(해당 기능 구현 시)** — STT 변환 완료 즉시 원본 음성 파일을 삭제하고 변환 텍스트만 보관한다.

> **원안에서 2곳을 고쳤습니다.**
> - **(2)**: 원안은 "매체 단위 암호화를 적용한다"였는데, PostgreSQL은 자체 TDE가 없어 OS/클라우드 레벨로만 가능합니다. 실제로 켜지 않을 거면 **02-A에서 지적한 것과 똑같은 미이행 보장**이 됩니다. 조건부로 낮췄습니다. → **[확인]** 실제 배포 환경을 정한 뒤 문장을 확정하세요.
> - **(6)**: 원안의 "단독으로는 개인을 특정할 수 없는 구조"는 방어가 안 됩니다. USERS와 측정치가 **단일 PostgreSQL 안에 물리적 FK로 연결**되어 있어 `JOIN` 한 번이면 실명과 붙습니다. 주장을 낮추고 접근통제를 주 통제수단으로 재배치했습니다.
>
> **발표 프레이밍**: "암호화를 안 했다"가 아니라 **"위험도에 따라 보호 수준을 차등 적용했다"**. (6)의 근거 문장이 핵심이니 삭제하지 마세요.
>
> **[확인] 법령 근거**: 개인정보보호법상 건강정보는 민감정보로 분류되어 일반 개인정보와 기준이 다를 수 있습니다. 조문을 인용하려면 **최신 개정 여부까지 직접 확인**하고, 확신이 없으면 조문 인용 없이 설계 논리만 쓰는 편이 안전합니다.

**CREATE 스크립트 교체**
```sql
CREATE TABLE DEVICE_HEALTH_CONNECTIONS (
    connection_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL REFERENCES USERS(user_id) ON DELETE CASCADE,
    device_name VARCHAR(100),
```

## 05-B. USERS.phone — 컬럼 길이 **[교체]** ⭐

**문제** 02-F (3)에서 연락처를 AES-256-GCM 대상에 넣었는데, 현재 `phone`은 `VARCHAR(20)`입니다. IV·인증태그를 포함한 암호문을 Base64로 담으면 **60자를 넘어 저장이 불가능**합니다.

## 05-C. USERS.persona_type — 회원가입 INSERT 실패 **[교체]** ⭐⭐

**문제 (실제 결함)** 현재 스크립트는 이렇습니다.

```sql
persona_type VARCHAR(50) NOT NULL CHECK (persona_type IN ('FRIEND','COUNSELOR')),
```

`NOT NULL`인데 **DEFAULT가 없습니다.** 그런데 화면설계서 `MAIN_JOIN_02`(회원가입 정보 입력)는 이메일·비밀번호·이름·생년월일·성별만 받고, 페르소나 선택은 로그인 **이후** `MLCM_300`에서 이루어집니다. **지금 스크립트대로면 회원가입 INSERT가 실패합니다.**

`CHAT_SESSIONS.persona_type`에는 `DEFAULT 'FRIEND'`가 있는데 `USERS`에만 없는 비대칭도 함께 정리해야 합니다.

**변경 (택1)**
- (권장) `DEFAULT 'FRIEND'` 추가 → `CHAT_SESSIONS`와 일관
- 또는 `NOT NULL` 제거하고 NULL 허용 → 미선택 상태를 명시적으로 표현
