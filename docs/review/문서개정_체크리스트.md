## 03-E. 심박수·HRV 출처 구분 **[교체]** ⭐⭐

**위치** 라이프로그 블록 → `1. 데이터 준비` → `데이터 정의` 칸 (PDF 3페이지)

**현재**
> …심박수·HRV는 자율신경계 반응과 스트레스·정서 상태 간 상관관계가 선행연구(WESAD 등)에서 보고된 지표로, **1차 모델 학습 데이터셋부터 포함한다.**

**문제** — **기업 제공 데이터에 심박수·HRV 가 없습니다.** 메타데이터의 라이프로그 13항목·집계 23항목 어디에도 없습니다. PMData 의 HRV 도 표준 SDNN 이 아니라 **일별 심박수 표준편차 프록시**입니다.

지금은 **"어느 데이터의 HRV 인가"** 에 답할 수 없는 상태입니다.

**교체**
> …심박수·HRV 는 자율신경계 반응과 스트레스·정서 상태 간 상관관계가 선행연구(WESAD 등)에서 보고된 지표이다. 다만 **데이터 출처별로 확보 수준이 다르다.** 기업 제공 데이터셋은 수면·활동·체성분 중심으로 구성되어 심박수·HRV 를 포함하지 않으며, 공개 데이터셋(PMData)은 분 단위 심박수를 제공하나 표준 SDNN 대신 **일별 심박수 표준편차를 HRV 대용 지표로 산출**한다. 실서비스에서는 Health Connect 가 제공하는 심박수·HRV 를 그대로 수집한다. 따라서 1차 모델은 수면·활동 지표를 공통 피처로 사용하고, **심박수·HRV 는 확보 가능한 구간에 한해 보조 피처로 활용**한다.

> **⚠ 이걸 안 고치면 나오는 질문** — "학습에 쓴 HRV 와 서비스에서 수집하는 HRV 가 같은 값인가요". 지금 문서로는 답할 수 없습니다. **출처별 차이를 먼저 인정하고 대응을 적어두는 편이 훨씬 방어적입니다.**
>
> **연동** `LIFELOG_METRICS.heart_rate` · `hrv` 컬럼과 02 문서의 수집 항목은 **그대로 둡니다.** 실서비스는 Health Connect 로 받으므로 유효합니다. 바꾸는 건 **학습 데이터 설명**뿐입니다.

## 05-C. USERS 스크립트 — 스마트 따옴표로 실행 불가 **[교체]** ⭐⭐ 🔥

> **`DEFAULT 'FRIEND'` 와 `VARCHAR(20)` 통일은 이미 반영 완료입니다.** 원래 결함(회원가입 INSERT 실패)은 해소됐습니다.
> **다만 반영 과정에서 새 문제가 생겼습니다.**

**현재** — USERS 의 CREATE 스크립트

```
persona_type VARCHAR(20) NOT NULL DEFAULT 'FRIEND’ CHECK (persona_type IN ('FRIEND', ...
```

**닫는 따옴표가 스마트 따옴표(`’`)입니다.** 여는 쪽은 일반 따옴표(`'`)인데 닫는 쪽만 바뀌었습니다. 한글의 **자동 따옴표 변환** 때문입니다.

**이 상태로 복사해서 실행하면 SQL 문법 오류가 납니다.** 눈으로는 거의 구분이 안 돼서, 문서만 보고 스키마를 만드는 사람은 원인을 찾기 매우 어렵습니다.

**교체** — 닫는 따옴표를 일반 따옴표로

```sql
persona_type VARCHAR(20) NOT NULL DEFAULT 'FRIEND'
    CHECK (persona_type IN ('FRIEND', 'COUNSELOR')),
```

> **한글에서 자동 따옴표 변환을 끄고 작업하세요.**
> `도구 → 빠른 교정 → 빠른 교정 내용 → 입력 자동 서식` 에서 따옴표 변환 항목 해제.
> **다른 CREATE 스크립트도 전부 확인하세요.** `CHAT_SESSIONS` 는 정상이지만 나머지는 대조가 필요합니다.

## 05-A. DEVICE_HEALTH_CONNECTIONS **[교체]**

**현재**

| 위치 | 현재 |
|---|---|
| 컬럼 정의표 | `Access Token \| access_token \| TEXT \| - \| … \| OAuth Access Token` |

**테이블 설명 교체**
> 헬스 플랫폼(Health Connect) 연동 권한 승인 상태 및 항목별 수집 동의 범위 관리

**컬럼 변경** — `access_token TEXT` 행 삭제, 아래 2행 추가

| 컬럼명 | 컬럼 ID | 타입 | NN | 비고 |
|---|---|---|---|---|
| 권한 승인 여부 | permission_granted | BOOLEAN | Y | 기기 내 Health Connect 권한 승인 상태, DEFAULT FALSE |
| 최종 동기화 일시 | last_synced_at | TIMESTAMPTZ | | 미수신 감지 및 재시도 판단 기준 |

**CREATE 스크립트 교체**
```sql
CREATE TABLE DEVICE_HEALTH_CONNECTIONS (
    connection_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL REFERENCES USERS(user_id) ON DELETE CASCADE,
    device_name VARCHAR(100),
    platform_type VARCHAR(50) NOT NULL
        CHECK (platform_type IN ('HEALTH_CONNECT', 'APPLE_HEALTH')),
    permission_granted BOOLEAN NOT NULL DEFAULT FALSE,
    agreed_at TIMESTAMPTZ NOT NULL,
    last_synced_at TIMESTAMPTZ,
    consent_scopes JSONB NOT NULL DEFAULT
        '{"activity": true, "sleep": true, "body_composition": false}'
);
```

> `APPLE_HEALTH` 는 구현 제외이지만 **enum 값은 유지합니다.** 빼면 `platform_type` 컬럼에 값이 하나뿐이라 컬럼의 존재 이유가 사라집니다.

## 05-E. 활동 시각 컬럼 — 수용 여부 판단 **[확인]**

기업 메타데이터에는 있는데 **`LIFELOG_METRICS` 에 대응 컬럼이 없는** 항목이 셋입니다.

| 메타데이터 항목 | 단위 | LISN 스키마 |
|---|---|---|
| 활동 시작 시간 | `hh:mm:ss` | 없음 |
| 활동 종료 시각 | `hh:mm:ss` | 없음 |
| 총활동 시간 | `min` | 없음 |

**수면은 `sleep_start_at`·`sleep_end_at`·`total_sleep_min` 으로 시작·종료·총시간을 모두 받는데, 활동은 `steps`·`distance`·`calories` 만 있고 시각 정보가 없습니다.** 구조가 비대칭입니다.

- **받는다면** → `activity_start_at` · `activity_end_at` · `total_active_min` 3개 컬럼 추가. `db/schema.sql` · 05 컬럼 정의표 · CREATE 스크립트 · 04 객체 정의서까지 연쇄 수정
- **안 받는다면** → 그대로 두되, 기업 데이터 적재 시 이 세 항목은 버린다는 점을 인지

> **판단 기준** — 활동 시각이 정서 분석에 쓰이는지입니다. "밤늦은 시간대 활동", "활동 시작 시각의 규칙성" 같은 피처를 만들 계획이면 필요하고, 하루 총량만 쓸 거면 불필요합니다.
>
> **`raw_payload`(JSONB) 로 받아두는 절충안**도 있습니다. 컬럼을 늘리지 않고 원본을 보존할 수 있어, 나중에 쓰기로 하면 그때 꺼내 쓰면 됩니다. **김건영 님과 확인하세요.**
