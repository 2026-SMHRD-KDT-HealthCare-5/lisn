## 0. 요약

기획서를 고치는 이유는 **두 가지가 한 방향이기 때문**입니다.

1. **기획서와 빅데이터분석정의서가 서로 다른 말을 하고 있습니다.** 기획서는 F1 80% 를 목표로
   걸고 있었는데, 분석정의서는 이미 그 목표에 도달하지 못해 채택하지
   않았다고 기록했습니다.
2. **차별점으로 내건 「상시 모니터링」에 출구가 없습니다.** 감지 결과가
   사용자에게 도달하는 경로가 시스템에 존재하지 않습니다.

둘을 따로 고칠 수 없습니다. 모순을 푸는 방법이 곧 차별점을 세우는
방법입니다 — **「감정을 맞힌다」에서 「변화를 재고 먼저 말을 건다」로**
목표를 옮기면 두 문제가 같이 풀립니다.

## 1. 왜 지금 고치나 — 근거

### 1-1. 기획서와 빅데이터분석정의서의 충돌

| 문서 | 문장 |
|---|---|
| **기획서** 3장 목표② | "위험 단계 분류 정확도(F1-score) 80% 이상을 목표로 하며" |
| **빅데이터분석정의서** 분석 평가 결과 | "공개 데이터셋 기반 지도학습 모델은 목표 성능(Accuracy 85%↑, F1-Score 0.80↑)에 도달하지 못해 채택하지 않음" |

빅데이터분석정의서가 기록한 실측값입니다.

- GLOBEM(참가자 40명) 우울 이진 라벨 기준 **ROC-AUC 0.528**, 95% CI 0.476~0.579
- LifeSnaps(참가자 63명, 감정 라벨 7종) 재검증 **0.479~0.540**.
  SAD 0.485 · TENSE/ANXIOUS 0.497 로 **0.5 미만**
- "참가자 수와 피처 수를 늘려도 결과가 변하지 않아 **표본 부족이 아닌 신호
  자체의 한계**로 판단한다"

**이건 실패가 아니라 결과입니다.** 참가자 단위 분할을 지켜서 얻은 값이고,
무작위 분할이면 0.9 이상으로 과대평가된다는 것까지 빅데이터분석정의서가 적어뒀습니다.
방법론이 올바랐기 때문에 나온 숫자입니다.

## 2. 바꿀 틀

```
지금  라이프로그 → 감정 9종 분류 → 위험도 → 액션(사용자가 앱을 열면)
      └ 라벨이 없고 신호가 약해 학습이 안 됨(AUC 0.5)

새로  라이프로그 → 개인 기준선 이탈 측정 → 지속되면 먼저 접촉
      └ 라벨 불필요. 예측이 아니라 관측이므로 정확도 주장을 하지 않음
        위험도 3단계 대응은 그대로 유지
```

**핵심은 「예측」이 아니라 「대조」입니다.** 평소의 그 사람과 오늘의 그
사람을 비교하는 것은 분류 문제가 아니라 기술통계입니다. 맞고 틀림을 가릴
대상이 아니므로 AUC 0.5 라는 결과와 충돌하지 않습니다.

- **κ 가 실패 지표에서 분류 도구로 바뀝니다.** 일치한 행은 정답을 확정하고,

- **`PL-29` 확인 질문의 근거가 완성됩니다.** 「모델이 못 잡는다」가 아니라
  **「원래 문맥 없이는 정할 수 없는 문제다」**가 됩니다

### ⚠ 두 가지를 반드시 함께 둡니다

**① 불일치가 전부 「애매해서」는 아닙니다.**

```
「드라마에서 주인공이 죽는 장면이 슬펐어요」   A=low  B=no
```

이건 애매한 것이 아니라 **한쪽이 잘못 읽은 것**입니다. 그래서 문안에
「**조정 과정에서 … 합의한**」을 넣었습니다. **불일치를 자동으로 「확인
필요」로 돌리면 안 됩니다** — 두 사람이 훑으면서 진짜 갈리는 것과 실수를
갈라야 합니다.

**② 모델이 전부 「판별 불가」로 답하면 만점이 됩니다.**

문안 마지막 문장이 이것을 막습니다. **판별 불가 비율을 함께 기록**하지
않으면 이 방법은 자기 기만이 됩니다. `PL-30` 2턴 평가에서 같이 셉니다.

## `PL-34` 빅데이터분석정의서 **2. 전처리** — 전처리 데이터를 실물로 **[교체]** ⭐⭐

**왜** — **바로 앞 「1. 수집」은 실제 JSON 예시를 보여줍니다**(`total_sleep_min:
280`, `sleep_efficiency_pct: 71.0` …). 전처리만 추상어 한 줄이라 대칭이

Vector` 는 **LSTM 입력용 서술**인데 그 모델은 채택하지 않았습니다.

**교체 문안 — 전처리 과정**

```
1. 이상치 정제 및 결측치 처리: 센서 신호 튀어짐(Noise)을 제거하고, 결측일은
   보간하지 않고 해당 지표를 그날의 산출 대상에서 제외한다. 측정되지 않은
   값을 0으로 채우면 활동량 급감과 구분되지 않는다.
2. 개인 기준선 산출: 사용자별 최근 14일 기록에서 지표별 중앙값과 중앙절대
   편차(MAD)를 구한다. 평균이 아니라 중앙값을 쓰는 이유는, 기기를 착용하지
   않은 날 하나가 평균을 끌어내려 다음 날을 이탈로 오판하기 때문이다.
3. 이탈도 정량화: 당일 값을 개인 기준선 대비 robust z-score 로 변환한다.
   지표별로 위험한 방향을 정해 두고 그 방향의 이탈만 계상한다. 더 잘 잔 날은
   이탈로 보지 않는다.
4. 시각 지표 변환: 입면 시각과 활동 개시 시각은 18시를 기준으로 한 경과 분
   으로 변환한다. 자정을 기준으로 하면 23:30에서 01:00으로 늦어진 것이
   빨라진 것으로 계산된다.
```

**교체 문안 — 전처리 데이터**

```
전처리 데이터는 사용자·일자 단위의 이탈도 레코드이며, 7개 지표에 대한
개인 기준선 대비 robust z-score 와 이탈 지표 목록·연속 이탈일수로 구성된다.

  지표      총수면 · 걸음수 · 수면효율 · 입면지연 · 야간각성 ·
            입면시각 · 활동개시
  산출값    지표별 이탈도(z), 이탈 지표 목록(deviant_features),
            연속 이탈일수(streak_days)

(예시)
{
  "user_id": "c39a12e0-5712-42ba-822d-60603126f000",
  "collected_at": "2026-07-27",
  "deviations": {
    "총수면": 1.2, "걸음수": 0.8, "수면효율": 2.6,
    "입면지연": 3.1, "야간각성": 1.4, "입면시각": 2.2, "활동개시": 0.9
  },
  "deviant_features": ["입면지연", "수면효율", "입면시각"],
  "streak_days": 8
}
```

> ⚠ **예시 값입니다.** 실제 산출은 사용자마다 다르며, 지표 정의의 정본은
> 저장소 `ai/server/main.py` 의 `_FEATURES` 입니다.

## `PL-35` 빅데이터분석정의서 **3. 데이터 분석** — 모델 나열이 아니라 분석으로 **[교체]** ⭐⭐

**위치** 빅데이터분석정의서 › 3. 데이터 분석 · 담당 **김건영**

**왜** — 지금 「데이터 분석 시나리오」가 **`LSTM Autoencoder` → `LightGBM`
파이프라인 설명**입니다. **수집한 데이터를 어떻게 볼 것인지가 아니라 어떤

「데이터 분석 결과」도 `EMOTION_RISK_SCORES` 레코드 JSON 인데, 그것은
**시스템 산출물이지 분석 결과가 아닙니다.**

> ⚠ 시나리오 번호가 **1 · 2 · 5** 로 되어 있습니다(3·4 없음). 교체하면서
> 함께 정리됩니다.

**교체 문안 — 데이터 분석 목표**

```
집단 간 감정 분류가 아니라 개인 내 변화 탐지를 목표로 한다. 같은 수면
시간이라도 사람마다 평소가 다르므로, 절대값이 아니라 그 사용자의 평소

사용자가 스스로 인지하기 전에 접촉하는 것이 분석의 목적이다.
```

**교체 문안 — 데이터 분석 시나리오**

```
1. 기준선 대비 이탈 판정: 지표별 이탈도(z)가 임계치를 넘은 지표가 2개
   이상인 날을 이탈일로 본다. 지표 하나만 튀는 것은 측정 오차일 수 있다.
2. 지속성 판정: 마지막 날부터 연속된 이탈일수를 센다. 연속 이탈이 이어지는
   구간을 선제 접촉(MLCM_220)의 발동 조건으로 사용한다.
3. 대화 신호 결합: 챗봇 대화에서 산출된 감정 코드 및 위기 판정 결과를
   함께 본다. 라이프로그 이탈과 대화 신호는 각각 독립적으로 산출되며,
   어느 한쪽만으로도 판정이 성립한다.
4. 위험도 매핑: 감정 코드와 강도에 따라 3단계 위험도(NORMAL / CAUTION /
   CRITICAL)를 판정한다. CRISIS 감정은 강도와 무관하게 CRITICAL 로
   확정하고 긴급 상담 연결을 트리거한다.
5. 근거 제시: 이탈이 큰 지표 목록을 함께 산출하여, 선제 접촉 발화가
   무엇이 달라졌는지를 관찰 사실로 전달할 수 있게 한다.
```

**교체 문안 — 데이터 분석 결과**

```
분석 결과는 사용자·일자 단위의 정서 위험도 레코드로 산출된다.

  라이프로그 이탈  anomaly_score, streak_days, deviant_features
  정서 판정        emotion_code, emotion_score
  위험도           risk_level, risk_score
  판정 근거        model_version

model_version 은 판정 방식을 식별하는 값이며, 규칙 기반 판정은 rule-
접두사를 사용한다. 접두사가 rule- 인 결과는 학습된 모델의 출력이 아니므로
모델 성능의 근거로 인용하지 않는다. 운영 중인 값의 정본은 저장소
ai/server 의 구현이며, 본 문서는 명명 규칙만 규정한다.
```

> ### `model_version` 을 문서에 박지 않는 이유
>
> 현재 문서는 `"model_version": "v1.2.0"` 으로 특정 값을 적어두었는데
> **실제 값과 다릅니다.** 판정 방식이 바뀔 때마다 문서를 따라 고쳐야 하고,
> 안 고치면 지금처럼 어긋납니다.
>
> **문서는 규칙을, 코드는 값을 갖습니다.** `rule-` 접두사의 의미를 문서가
> 규정하면, 값이 바뀌어도 문서는 유효합니다. 이 저장소가 `db/schema.sql` 을

> **기존 「모델링 목표에 개인 내 변화 탐지 반영」 항목과 한 덩어리입니다.**

## 5. 안전 설계 — 기획서에 반드시 남길 것

선제 접촉은 **잘못하면 감시로 느껴집니다.** 기획서 SWOT 의 위협 항목에
"B2G 연계 '감시' 인식 시 신뢰도 하락 리스크가 있음"이 이미 적혀 있습니다.
선제 접촉은 그 리스크를 정면으로 키우는 기능이므로, 방어 설계를 문서에
같이 넣어야 합니다.

1. **옵트인** — 설정의 알림 수신 동의가 꺼져 있으면 접촉하지 않습니다
2. **근거 명시** — "왜 지금 말을 거는지"를 반드시 함께 보여줍니다.
   근거 없는 접촉이 감시로 읽힙니다
3. **빈도 상한** — 하루 1회, 접촉 후 3일 쿨다운
4. **진단 금지** — 관찰 사실만 전달합니다(`FR-AI-002`)
5. **CRITICAL 은 푸시 대상이 아닙니다** — 위기 상태를 잠금화면에 띄우면
   본인이 아닌 사람에게 노출될 수 있습니다. 109 안내는 앱 안에서만

> `SO 전략` 문단에 이미 "위험도 기반 계층적 데이터 보호 설계를 앞세워,
> 민감정보 규제 강화와 '감시' 우려라는 위협에 선제 대응한다"가 있습니다.
> **여기에 위 5개를 덧붙이는 것이 가장 자연스럽습니다.**

## 6. 반영 절차

**순서가 중요합니다.** 발표자료가 화면에 뜨는 것이라 가장 급하고, 기획서와 요구사항정의서는
같은 모순을 공유하므로 붙여서 처리해야 어긋나지 않습니다.

1. **발표자료 PPTX** `PL-20` ~ `PL-24` — `tools/patch-pptx-text.ps1` 사용.
   **PowerPoint 로 다시 저장하지 마세요**(임베드 폰트가 풀립니다)
   - 적용 후 검증: 슬라이드 수 · 전체 파트 수 · 각 슬라이드 `[xml]` 파싱
2. **기획서 HWP** `PL-01` ~ `PL-13` — Part A(모순 해소) 부터
3. **요구사항정의서 HWP** `PL-14` ~ `PL-19` — `NFR-AI-001` 부터. 기획서와 같은 문장이라
   따로 하면 한쪽만 고쳐집니다
4. **빅데이터분석정의서·데이터베이스요구사항분석서 · 테이블명세서** — 소규모
5. HWP 를 고쳤으면 **PDF 내보내기** → `python tools/doc2txt.py` 로 추출본 재생성
6. 추출본으로 대조. **문구 검색으로 판정하지 마세요** — 표 안 문장은 셀
   폭에 맞춰 쪼개집니다. 절 전체를 읽어 확인하세요
7. HWP·PDF·PPTX·추출본을 **같은 커밋에** 넣습니다
8. 반영 완료 항목은 `docs/진행/작업이력.md` 로 옮기고 이 문서에서 지웁니다

### 반영 후 자기점검

```bash
python tools/check_docs.py
```
