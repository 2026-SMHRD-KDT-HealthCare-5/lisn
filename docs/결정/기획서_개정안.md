## 0. 요약

기획서를 고치는 이유는 **두 가지가 한 방향이기 때문**입니다.

1. **01 과 03 이 서로 다른 말을 하고 있습니다.** 기획서는 아직 F1 80% 를
   목표로 걸고 있는데, 분석정의서는 이미 그 목표에 도달하지 못해 채택하지
   않았다고 기록했습니다. 심사에서 반드시 잡힙니다.
2. **차별점으로 내건 「상시 모니터링」에 출구가 없습니다.** 감지 결과가
   사용자에게 도달하는 경로가 시스템에 존재하지 않습니다.

둘을 따로 고칠 수 없습니다. 모순을 푸는 방법이 곧 차별점을 세우는
방법입니다 — **「감정을 맞힌다」에서 「변화를 재고 먼저 말을 건다」로**
목표를 옮기면 두 문제가 같이 풀립니다.

## 2. 바꿀 틀

```
지금  라이프로그 → 감정 9종 분류 → 위험도 → 액션(사용자가 앱을 열면)
      └ 라벨이 없고 신호가 약해 학습이 안 됨(AUC 0.5)

새로  라이프로그 → 개인 기준선 이탈 측정 → 지속되면 먼저 접촉
      └ 라벨 불필요. 예측이 아니라 관측이므로 정확도 주장을 하지 않음
        위험도 3단계 대응은 그대로 유지
```

**핵심은 「예측」이 아니라 「대조」입니다.** 평소의 그 사람과 오늘의 그
사람을 비교하는 것은 분류 문제가 아니라 기술통계입니다. 맞고 틀림을 가릴
대상이 아니므로 AUC 0.5 라는 결과와 충돌하지 않습니다.

# Part A. 01↔03 모순 해소

## `PL-01` 3장 목표② — 성능 목표 재정의 **[최우선]**

**위치** 3. 개발 내용 › 프로젝트 목표 › ②

**현재 문장**

> ② 2단계 AI 모델을 통한 위험 단계 자동 판정
> 라벨이 없는 초기 데이터에서는 LSTM Autoencoder로 이상 패턴을 1차 탐지하고, 데이터가 축적되면 LightGBM으로 위험 단계 스코어(NORMAL/CAUTION/CRITICAL)를 2차 정밀 분류하여, 라이프로그와 챗봇 대화 메타데이터를 정밀 반영한 위험도 대응 파이프라인을 구동한다.
> 위험 단계 분류 정확도(F1-score) 80% 이상을 목표로 하며, 특히 위험 누락 최소화가 중요한 CRISIS/CRITICAL 위기 상황은 키워드 규칙과 LLM 문맥 분석을 결합한 2단계 위기 탐지 로직을 통해 재현율(Recall) 90% 이상을 확보한다.

**개정 문안**

```
② 개인 기준선 이탈 탐지를 통한 위험 단계 자동 판정
공개 데이터셋 기반 지도학습(LSTM Autoencoder + LightGBM)의 학습 타당성을
사전 검증한 결과, 라이프로그만으로 감정 상태를 분류하는 것은 목표 성능에
도달하지 못하였다(상세 근거는 03 빅데이터분석정의서 「학습 방법」 참조).
이에 본 과제는 집단 간 감정 분류가 아니라 개인 내 변화 탐지로 판정 방식을
전환한다. 사용자 개인의 최근 14일 패턴을 기준선으로 삼아 수면 시각·입면
시간·야간 각성·수면 효율·활동 개시 시각의 이탈 정도를 정량화하고, 이탈이
지속되는 구간을 위험 단계(NORMAL/CAUTION/CRITICAL)로 판정한다.
개인 기준선 이탈 탐지는 라벨을 필요로 하지 않으므로, 합성 이상 패턴 주입
시나리오에서의 탐지율과 오탐률로 성능을 검증한다. 위험 누락 최소화가
중요한 CRISIS/CRITICAL 위기 상황은 키워드 규칙과 LLM 문맥 분석을 결합한
2단계 위기 탐지 로직을 통해 재현율(Recall) 90% 이상을 확보한다.
```

**근거**

- `F1-score 80%` 목표를 **삭제**합니다. 03 이 미달로 채택하지 않았다고 이미
  기록했으므로, 01 에 남겨두면 두 문서가 반대 결론을 갖습니다.
- **`Recall 90%` 는 유지합니다.** 이건 대화 기반 위기 탐지이고, 평가셋 200건이
  있어 실제로 측정 가능합니다. 라이프로그 쪽 목표와 성격이 다릅니다.
- 새 성능 지표(합성 이상 주입 탐지율)는 **03 의 「분석 검증 방안」 3항**
  ("실제 생체 이상 파형 데이터 주입을 통한 … 임계치 성능 검증")과 이미
  같은 말입니다. 03 에 있는 것을 01 의 목표로 끌어올리는 것뿐입니다.

**연동** 03 모델링 목표 · 02 `MLCM_210` · `ai/server/main.py` `_predict()`

**위치** 3. 개발 내용 › 프로젝트 목표 › ①

> ① 완전 자동화된 데이터 파이프라인 구축
> 경쟁 서비스(마인드카페·Wysa 등)는 능동적 감정 입력(텍스트 작성, 이모티콘 선택 등)이 있어야 정서 상태 파악이 가능한 반면, 본 서비스는 스마트워치 생체신호(Health Connect)만으로 이 입력 절차 자체를 배제한다.

**개정 문안** (문단 끝에 두 문장 추가)

```
나아가 감지에서 그치지 않고 접촉까지 자동화한다. 경쟁 서비스는 감지 결과를

사용자는 앱 실행 자체가 이루어지지 않는다. 본 서비스는 개인 기준선 이탈이
```

## 5. 안전 설계 — 기획서에 반드시 남길 것

선제 접촉은 **잘못하면 감시로 느껴집니다.** 기획서 SWOT 의 위협 항목에
"B2G 연계 '감시' 인식 시 신뢰도 하락 리스크가 있음"이 이미 적혀 있습니다.
선제 접촉은 그 리스크를 정면으로 키우는 기능이므로, 방어 설계를 문서에
같이 넣어야 합니다.

1. **옵트인** — 설정의 알림 수신 동의가 꺼져 있으면 접촉하지 않습니다
2. **근거 명시** — "왜 지금 말을 거는지"를 반드시 함께 보여줍니다.
   근거 없는 접촉이 감시로 읽힙니다
3. **빈도 상한** — 하루 1회, 접촉 후 3일 쿨다운
4. **진단 금지** — 관찰 사실만 전달합니다(`FR-AI-002`)
5. **CRITICAL 은 푸시 대상이 아닙니다** — 위기 상태를 잠금화면에 띄우면
   본인이 아닌 사람에게 노출될 수 있습니다. 109 안내는 앱 안에서만

> `SO 전략` 문단에 이미 "위험도 기반 계층적 데이터 보호 설계를 앞세워,
> 민감정보 규제 강화와 '감시' 우려라는 위협에 선제 대응한다"가 있습니다.
> **여기에 위 5개를 덧붙이는 것이 가장 자연스럽습니다.**
