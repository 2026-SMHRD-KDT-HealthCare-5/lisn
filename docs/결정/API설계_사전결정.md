> **작성일** 2026.07.30 · **현행성 점검** 2026.07.31 · API 명세를 쓰기 전에 정해야 했던 것들
>
> 여기서 정한 것이 엔드포인트의 요청·응답 스키마를 직접 결정합니다.
> 나중에 바꾸면 클라이언트·서버 양쪽을 고쳐야 하므로 먼저 못 박습니다.

## 1. 인증 — 단일 JWT, refresh 없음

**결정**: access token 하나만 쓴다. refresh token 을 도입하지 않는다.

### 왜 refresh 가 없었나

찾아보니 **빠진 게 아니라 처음부터 단일 JWT 설계**였습니다.

- `refresh` 는 산출물 7종·`docs/review/`·`schema.sql` 어디에도 **0건**
- 02 는 일관되게 *"JWT 토큰을 발행하여 세션을 생성"* 이라고만 서술. access/refresh 구분 자체가 없음
- `04-F` 로 *"인증 외부화"* → *"자체 인증(Direct Auth)"* 확정. 외부 IdP 도 안 씀

문제는 **화면설계서 12장 시절 `MAIN_LOGIN_01` 에 「로그인 유지」 체크박스가 있었다**는 점입니다. 그때부터 이미 설계 공백이었고, v0.6 개정에서 그 항목이 빠지면서 우연히 정합해졌습니다.

**`SD-07`(사라진 기능 복원)이 그 공백을 되살릴 뻔했습니다.** 복원 근거가 "예전에 있었으니까" 뿐인데, 그것 때문에 인증 체계를 확장하는 건 배보다 배꼽입니다.

### 확정 내용

| 항목 | 값 |
|---|---|
| 토큰 | access token 단일 |
| 만료 | **24시간** |
| 갱신 | 없음. 만료 시 재로그인 |
| 로그아웃 | **클라이언트 토큰 삭제**. 서버측 블랙리스트 미구현 |
| 페이로드 | `sub`(user_id), `role`, `exp` |

만료를 24시간으로 잡은 이유 — 실무 표준은 access 30분~1시간에 refresh 로 갱신하는 구조지만, refresh 가 없는 상태에서 1시간을 쓰면 매시간 재로그인이 됩니다. 데모 환경에서 감당이 안 됩니다.

블랙리스트를 안 만드는 근거는 **02 가 이미 여지를 열어뒀기 때문**입니다.

> `MLCM_101` — 세션/토큰 무효화(클라이언트 토큰 삭제 + **필요 시** 서버측 블랙리스트 처리)

stateless JWT 는 서버가 상태를 안 들고 있어서 진짜 무효화가 불가능합니다. 블랙리스트를 만들면 그게 곧 세션 테이블이라, "stateless 로 갔다가 stateful 을 덧붙이는" 최악의 조합이 됩니다.

### 딸려오는 문서 개정

- **`SD-07` 수정** — 「로그인 유지」를 복원 대상에서 제외. 「계정 찾기」만 복원(`MLCM_102` 진입점이 실제로 없어서 필요)

## 2. 앱 push 계약 — 문서에 이미 있음

**`MLCM_200` 에 상세히 정의돼 있었습니다.** 새로 정할 게 거의 없습니다.

| 단계 | 내용 |
|---|---|
| 1 | 앱 백그라운드 워커가 **최소 15분** 간격 실행. Doze·앱 대기 버킷으로 지연될 수 있음 |
| 2 | 권한 확인. 없으면 중단하고 재승인 안내 |
| 3 | **`last_synced_at` 이후 신규분만** Health Connect 에서 조회 (델타 방식) |
| 4 | 백엔드 수집 API 로 push |
| 5 | 백엔드가 `(user_id, collected_at)` 기준 **UPSERT** 적재 후 `last_synced_at` 갱신 |
| 6 | 전송 실패 시 앱이 **30초 간격 최대 3회** 재시도. 최종 실패분은 **단말 보관 후 다음 주기에 합산 전송** |
| 7 | 백엔드가 `last_synced_at` **3시간 이상 미갱신** 시 미수신 감지 → **FCM 무음 푸시**로 동기화 유도. 그래도 미수신이면 **결측 처리** |

### 추가로 정한 것

| 항목 | 값 | 근거 |
|---|---|---|
| 요청 형태 | `POST /lifelog/batch` · `{ "items": [...] }` | 델타 전송이라 항상 배열 |
| 배치 상한 | **200건** | 15분 간격이면 하루 96건. 실패 누적·지연을 감안해도 넉넉함. 초과 시 나눠 전송 |
| 초과 시 | `413` 반환 | 서버가 잘라내면 유실이 조용히 생김 |
| 응답 | `{ "accepted": n, "last_synced_at": "..." }` | 앱이 다음 델타 기준점을 서버 값으로 갱신 |

`last_synced_at` 을 **응답으로 돌려주는 게 핵심**입니다. 앱이 자기 시계로 갱신하면 단말 시간이 틀어졌을 때 데이터가 영구 유실됩니다.

### 새로 발견한 문서 모순

**`FR-DP-001` 이 아직 서버 pull 서술입니다.**

> 현재: 스마트 기기 센서를 통해 1분 단위로 생성 및 축적되는 원시 데이터를, **백엔드 스케줄러가 15분 주기로 API를 호출하여 자동 수집**한다.

`MLCM_200` 과 `NFR-DV-002` 는 앱 push 로 개정됐는데 **기능 요구사항 표만 안 따라왔습니다.** 같은 문서 안의 모순입니다.

**교체안**
> 스마트 기기 센서를 통해 축적되는 원시 데이터를 앱 백그라운드 워커가 최소 15분 간격으로 조회하여 백엔드 수집 API로 전송한다. 백엔드는 (user_id, collected_at) 기준 UPSERT로 중복 없이 적재하는 기능

## 3. 대화 API 응답 형태

**결정**: 단발 요청·응답. 위기 판정 결과를 **같은 응답에 실어서** 반환한다.

`02-C`(`NFR-DV-001`)로 위기 탐지와 응답 생성을 **병렬 호출**하기로 확정했습니다. 그러면 서버가 두 결과를 받아 합성한 뒤 한 번에 내려주는 게 자연스럽습니다.

```
POST /chat/sessions/{session_id}/messages
{ "content": "요즘 너무 힘들어" }

200 OK
{
  "message_id": "...",
  "reply": "많이 힘드셨겠어요. ...",
  "risk": {
    "level":  "NORMAL | CAUTION | CRITICAL",
    "action": "CHAT | CONTENT | EMERGENCY"
  }
}
```

- `CRITICAL` 이면 `reply` 를 `null` 로 두고 `action: "EMERGENCY"` 만 내린다. 병렬로 생성된 일반 응답은 **서버가 버린다**
- `CAUTION` 이면 `reply` 와 함께 `action: "CONTENT"` 를 내려 클라이언트가 콘텐츠 추천을 띄운다

**스트리밍(SSE)을 안 쓰는 이유** — LLM 챗은 스트리밍이 실무 표준이지만, **위기 판정이 끝나기 전에 응답을 흘리면 CRITICAL 일 때 이미 나간 글자를 회수할 수 없습니다.** 안전 기능이 스트리밍과 상충합니다. `NFR-DV-001` 의 3초 요건은 단발로도 충족 가능합니다.

**판단을 클라이언트에 두지 않는 것**이 원칙입니다. 서버가 `action` 까지 확정해서 내려주고 클라이언트는 렌더만 합니다. 위험도 매핑 규칙(ANGER 70 기준 분기 등)이 클라이언트에 복제되면 반드시 어긋납니다.

## 4. 마이그레이션 — alembic 배제

**결정**: `db/schema.sql` 이 유일한 정본. `requirements.txt` 에서 `alembic` 을 제거한다.

정본이 둘이면 반드시 어긋납니다. 그리고 alembic 을 쓰려면 SQLAlchemy 모델을 정본으로 삼아 `autogenerate` 하는 게 정석인데, 그러면 **문서(04·05)와 대조할 기준이 `schema.sql` 이 아니라 파이썬 코드**가 됩니다. 산출물 문서와의 정합성이 이 프로젝트의 핵심이므로 그쪽이 손해입니다.

스키마 변경 시에는 `DROP DATABASE` 후 재생성합니다. 개발 기간이라 유지할 데이터가 없습니다.

## 5. 공통 규약

실무 표준을 그대로 따르되, 캡스톤 규모에서 과한 것은 뺍니다.

| 항목 | 결정 | 비고 |
|---|---|---|
| 에러 응답 | FastAPI 기본 `{ "detail": "..." }` + HTTP 상태코드 | 커스텀 에러코드 체계는 과함. 상태코드로 충분히 구분됨 |
| 페이징 | `?limit=20&offset=0` | 커서 기반이 실무 표준이나 데이터 규모상 offset 으로 충분 |
| 정렬 | 시계열은 항상 최신순 고정 | 정렬 파라미터를 열면 인덱스 설계와 어긋남 |
| 시각 | **ISO 8601 UTC** 문자열 | `TIMESTAMPTZ` 와 일치. 로컬 시간 변환은 클라이언트 몫 |
| 네이밍 | `snake_case` | Python·PostgreSQL 과 일관. 변환 계층을 두지 않음 |
| 경로 | `/api/v1/...` | 버전 접두사는 나중에 붙이면 전부 고쳐야 함 |

## 6. API 명세서의 위상 — 산출물 아님

**결정**: FastAPI 가 자동 생성하는 **OpenAPI(`/docs`)가 정본**. 마크다운 명세는 착수용 초안으로만 쓰고 구현 후에는 갱신하지 않는다.

실무에서 정확히 이 방식이 표준입니다. **코드가 곧 명세**이고, 별도 문서를 병행하면 반드시 어긋납니다.

현재 인증 API 6개 구현이 시작됐으므로 구현된 계약은 OpenAPI를 우선합니다. 나머지 미구현
API는 초안의 **엔드포인트 목록 + 요청/응답 스키마**를 착수 기준으로 사용합니다.

산출물 제출 대상이 아니므로 번호 체계(`06_`)를 붙이지 않고 `docs/API명세_초안.md` 로 둡니다.

## 7. AI 추론 서버 경계

**결정**: 같은 문서 안에서 **절을 나눠** 기술한다. 별도 문서로 분리하지 않는다.

실무 기준은 이렇습니다.

- 내부 서비스 간 API 도 명세는 하되 **외부(클라이언트) API 와 구분**한다. 인증 방식이 다르고(외부 JWT / 내부 서비스 토큰·네트워크 격리), 변경 주기도 다르기 때문
- 다만 **서비스가 2개뿐이면 문서를 쪼개지 않는다.** 문서가 늘어날수록 동기화 비용만 커짐

그래서 초안 문서를 이렇게 나눕니다.

```
docs/API명세_초안.md
├── 공통 규약
├── 외부 API   (앱 · 관리자 웹 → 비즈니스 서버)   JWT 인증
└── 내부 API   (비즈니스 서버 ↔ AI 추론 서버)     인증 없음, 네트워크 격리 전제
```

**내부 API 에 인증을 안 두는 이유** — 두 서버가 같은 네트워크 안에 있고 외부에 노출되지 않는 전제입니다. 여기에 토큰 체계를 만들면 관리할 비밀이 하나 더 늘 뿐 실질 보안 이득이 없습니다. 배포 시 AI 서버 포트를 외부에 열지 않는 것으로 갈음합니다.
