# 배포 아키텍처 — 왜 이 구성인가

> **작성일** 2026.08.24 · 클라우드 배포를 시작하기 전에 정해야 했던 것들
>
> "어떻게 하는지"는 [`infra/README.md`](../../infra/README.md) 에 있습니다.
> 여기는 그 구성을 **왜** 골랐는지만 다룹니다.

## 배경

최종발표자료(슬라이드 7 STACK)가 이미 "인프라: 로컬 데모"라고 밝혀뒀고,
슬라이드 15(HONEST STATUS)에는 "배포 인프라 미정 — 클라우드 배포는 다음
단계 과제"라고 명시돼 있습니다. 여기서 하는 일은 **그 다음 단계**입니다.
발표(8/28)까지 4일 남은 시점에 시작했다는 제약이 아래 선택 대부분의
근거입니다 — "이론적으로 더 나은 구성"보다 "4일 안에 안정적으로 되는
구성"을 우선했습니다.

## 1. NCP VM 1대 + Docker Compose — Kubernetes(NKS)·관리형 DB 를 안 쓴 이유

**결정**: Compute Server 1대에 Docker Compose 로 4개 컨테이너(postgres·
backend·ai-server·nginx)를 올린다.

### 왜 NKS 가 아닌가

Kubernetes 는 스케일링·롤링 업데이트가 강점입니다. 이 프로젝트엔 둘 다
해당하지 않습니다 — 발표 시연은 **동시 사용자 소수**(심사위원 관제 화면
확인 정도)이고, 롤링 업데이트가 필요할 만큼 트래픽이 끊기면 안 되는
서비스도 아닙니다. NKS 는 클러스터 자체의 학습·설정 비용이 남은 시간
대비 크고, 실패 지점(매니페스트·인그레스·볼륨클레임)이 컴포즈보다
훨씬 많습니다. 지금 중요한 건 확장성이 아니라 **발표 당일 안 죽는 것**
입니다.

### 왜 Cloud DB for PostgreSQL(관리형)이 아닌가

관리형 DB 는 백업·장애조치가 자동이라 이상적입니다. 다만 프로비저닝·
VPC 피어링·접속 정보 연동에 반나절 이상 걸리고, 이 프로젝트 규모(9개
테이블, 데모 트래픽)에서 얻는 이득이 설정 시간 대비 작습니다. 컨테이너
postgres + 볼륨으로 충분하고, 필요하면 나중에 그대로 관리형으로 옮길 수
있습니다(`DATABASE_URL` 하나만 바꾸면 되는 구조 — 4절 참고).

## 2. 서비스 경계 — 컴포즈에서도 기존 설계를 그대로 지킨다

**결정**: `postgres`·`ai-server` 는 host 포트를 열지 않는다. `nginx` 만
80/443 을 연다.

기존 설계 문서가 이미 이 경계를 정해뒀습니다 — 새로 만든 규칙이 아니라
**로컬 개발 때의 경계를 클라우드에서도 그대로 유지**한 것입니다.

- `docs/결정/API설계_사전결정.md` 7절 — AI 서버는 내부 통신 전용, 인증
  없음을 전제로 설계됨. 외부에 열면 그 전제가 깨집니다
- 요구사항정의서 `NFR-DV-003` — 위기 문맥 탐지(키워드 필터)가 AI 서버가
  아니라 backend 에 있는 이유가 "AI 서버 장애 시에도 단독 동작"입니다.
  AI 서버가 외부에 노출될 이유 자체가 없습니다
- `NFR-DE-002` (1) — "앱↔백엔드, 백엔드↔AI 서버 간 모든 API 통신에
  HTTPS/TLS 를 적용한다." 백엔드↔AI 서버는 같은 VM 안 컨테이너 네트워크라
  이미 외부에 안 드러나고, 앱↔백엔드는 nginx 의 443 이 담당합니다

ACG(NCP 보안그룹)에서 8000·8001·5432 규칙을 아예 안 만드는 것으로
인프라 레벨에서 한 번 더 막았습니다 — 애플리케이션 설정이 실수로 뚫려도
네트워크 단에서 막히는 이중 방어입니다.

## 3. 도메인 — 구매하지 않고 nip.io

**결정**: 정식 도메인을 사지 않고 `<공인IP>.nip.io` 로 Let's Encrypt
인증서를 받는다.

CLAUDE.md 「릴리스 빌드는 디버그와 다르다」절이 실기기 릴리스 빌드는
평문(HTTP) 을 기본 차단한다고 이미 정리해뒀습니다. 즉 **HTTPS 는 선택이
아니라 필수**입니다. 정식 도메인 구매·DNS 전파에 쓸 시간이 없어 nip.io
를 택했습니다 — 비용 0원, 즉시 발급 가능하고, Let's Encrypt 입장에서는
실제로 공개 해석되는 도메인이라 정식 도메인과 발급 절차가 동일합니다.

부수 효과로, `network_security_config.xml` 의 `<domain>` 목록에 IP 를
등록해야 했던 로컬 실기기 연동의 번거로움(CIDR 미지원이라 IP 가 바뀔 때마다
손으로 추가해야 했던 문제)이 **완전히 사라집니다.** 그 파일은 평문 예외
목록이고, HTTPS 트래픽은 애초에 그 파일을 거치지 않습니다.

## 4. 시크릿 — 정본 하나, 이미지에는 안 굽는다

**결정**: `backend/.env` 를 로컬 개발과 배포가 공유한다. 새 `.env.production`
을 만들지 않는다. 컨테이너 네트워크 주소로 바뀌어야 하는 값(`DATABASE_URL`·
`AI_SERVER_URL`)만 `docker-compose.yml` 의 `environment:` 가 덮어쓴다.

`db/schema.sql` 을 스키마의 정본으로 두고 어디에도 복제하지 않는다는
이 저장소의 원칙(CLAUDE.md)과 같은 이유입니다. 정본이 둘이 되면 "지금
서버에 어떤 값이 적용 중인가"를 알기 위해 두 파일을 대조해야 합니다.

`firebase-service-account.json`·`.env` 는 이미지에 `COPY` 하지 않고
`docker-compose.yml` 이 런타임에 마운트합니다(`backend/.dockerignore`로
빌드 컨텍스트에서도 원천 제외). 이미지에 시크릿을 구우면, 그 이미지를
어디로 옮기든 값이 따라갑니다 — 컨테이너 레지스트리에 올리게 되는 순간
유출 경로가 하나 늘어납니다.

---

## 5. 관리자 웹 — 컨테이너 안에서 안 만든다

**결정**: `frontend/admin` 은 로컬 PC 에서 `npm run build` 한 결과(`dist/`)를
scp 로 서버에 올려 nginx 가 정적으로 서빙한다. Node 이미지를 빌드
파이프라인에 안 넣는다.

멀티스테이지 Dockerfile(Node 로 빌드 → nginx 이미지로 결과만 복사)이
정석이긴 합니다. 다만 `VITE_API_BASE_URL` 이 **빌드 시점에 번들에
박히는 값**이라, 도메인이 확정되기 전까지 여러 번 다시 빌드해야 하는
지금 상황에서는 로컬에서 즉시 재빌드→scp 가 컨테이너 재빌드보다 빠릅니다.
이 PC 에 이미 Node(v24.14.1)가 있어 별도 설치도 필요 없습니다. 배포가
안정화된 뒤 CI 를 도입하게 되면 그때 멀티스테이지로 옮기는 게 자연스럽습니다.

## 되돌리는 방법

클라우드가 발표 당일 문제를 일으키면, CLAUDE.md 가 원래 정의한 방식
(`backend/` 에서 `uvicorn app.main:app --reload` 로컬 실행)으로 즉시
되돌릴 수 있습니다. 이 문서의 구성은 **로컬 실행 경로를 대체하는 것이
아니라 그 위에 얹은 것**입니다 — `infra/README.md` 8절이 그 폴백을
명시적으로 남겨두는 이유입니다.
