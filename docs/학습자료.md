```
│  관리자 웹      │───────▶│  · 관제 API          │
│  :5173 React    │        └──────────┬───────────┘
└─────────────────┘                   │
                                      │ HTTP

                           ┌──────────────────────┐
                           │  ai/server  :8001    │
```

★ **위기 탐지가 AI 서버가 아니라 backend 에 있는 게 이 그림의 핵심입니다.** 2장에서 설명합니다.

### 하루가 어떻게 흐르나

```
① 수집   앱이 Health Connect 에서 걸음·수면·심박을 읽어 서버로 push
              ↓
② 분석   AI 서버가 「최근 14일 나」 대비 오늘의 편차를 계산 → 위험도
              ↓
③ 케어   위험도가 높으면 앱 홈이 담담한 톤으로 바뀌고, 챗봇이 먼저 말을 건다
              ↓
④ 관제   관리자 웹에서 위기 사건 이력을 본다
```

②의 「최근 14일 나 대비」가 **개인별 Min-Max 정규화**입니다. 절대값으로 판단하지
않는 이유는 사람마다 평소 수면·걸음이 다르기 때문입니다. 하루 4시간 자는 게 평소인
사람에게 4시간은 신호가 아닙니다.

## 2. 왜 서버를 둘로 나눴나

**나눈 이유**: 정서 위험도 분석은 나중에 실제 모델로 교체될 자리입니다. 모델이 들어오면
무거워지고(GPU·메모리), 배포 주기도 다릅니다. 비즈니스 로직과 같은 프로세스에 두면
모델 교체할 때마다 인증·챗봇까지 같이 죽습니다.

### 그런데 위기 탐지는 왜 AI 서버에 없나

**이게 제일 자주 나오는 질문입니다.**

```
NFR-DV-003 — 외부 API 장애 시에도 키워드 필터가 단독으로 동작해야 한다
```

「사람이 죽고 싶다고 말했는데 AI 서버가 내려가서 못 잡았다」가 **일어나면 안 되는**
일이기 때문입니다. 그래서 위기 탐지는 **사용자 요청을 직접 받는 backend** 에 있습니다.

- 📄 `backend/app/services/safety.py` — 키워드 필터
- 📄 `backend/app/services/llm.py` — LLM 문맥 판정

API 명세 초안에는 `/internal/analyze/crisis` 라는 AI 서버 엔드포인트가 있었지만
**철회했습니다.** 되살리지 마세요.

## 3. 핵심 결정 6가지

각 결정에는 **기술적 제약**이나 **문서 요구사항**이 근거로 있습니다. 「그게 편해서」가
아닙니다.

| # | 결정 | 근거 |
|---|---|---|
| 1 | **서버 pull ❌ → 앱 push ⭕** | Health Connect 는 Android **on-device 권한 모델**입니다. 서버가 들고 있을 OAuth 토큰이 아예 없습니다 |
| 2 | **iOS 제외** (단 `APPLE_HEALTH` enum 값은 유지) | Health Connect 가 Android 전용 API. enum 값을 빼면 컬럼에 값이 하나뿐이라 컬럼의 존재 이유가 사라집니다 |
| 3 | **위기 탐지 = 키워드 + LLM 2단계** (KcBERT 파인튜닝 ❌) | 위기 데이터는 라벨을 구하기 어렵고, 학습 결과를 검증할 방법이 없습니다. 규칙은 최소한 **왜 걸렸는지 설명**됩니다 |
| 4 | **전 컬럼 AES-256 ❌ → 위험도 기반 계층적 보호** | 라이프로그 측정치는 **기간별 집계·복합 인덱스**가 서비스 핵심 동작입니다. 암호화하면 인덱스를 못 씁니다 |
| 5 | **문서가 정본, 앱이 아님** | Flutter 앱이 화면설계서를 안 보고 만들어졌습니다. **앱 구현을 근거로 문서를 판단하지 마세요** |
| 6 | **`USERS.role` 추가** | 관리자 기능이 요구사항 5곳에 있는데 데이터 모델에 관리자 개념이 없었습니다 |

### 4번을 조금 더 — 「계층적 보호」가 뭔가

전부 암호화하면 안전할 것 같지만, **집계 쿼리가 불가능해집니다.**

```sql
-- 이게 서비스 핵심 동작입니다. 암호화된 컬럼으로는 못 합니다.
SELECT avg(total_sleep_min) FROM lifelog_daily
 WHERE user_id = ? AND log_date BETWEEN ? AND ?;
```

그래서 **위험도에 따라 나눴습니다.**

| 데이터 | 보호 | 이유 |
|---|---|---|
| 전화번호 | **AES-256-GCM 컬럼 암호화** | 유출 시 즉시 개인 식별. 집계 대상 아님 |
| 비밀번호 | bcrypt 해시 | 복호화할 이유가 없음 |
| 걸음·수면·심박 | 전송 구간(TLS) + 접근 통제 | 집계가 핵심 동작 |

**부작용 하나**: 전화번호가 암호화돼 있어서 **관리자 웹 사용자 검색에서 전화번호로는
못 찾습니다.** 이건 버그가 아니라 설계 결과입니다. 이름·이메일로만 검색합니다.

## 4. 위기 탐지가 실제로 어떻게 도나

### 2단계인 이유

```
사용자: "요즘 사는 게 의미가 없는 것 같아"

1단계 · 키워드 필터  ──▶  신호 강도: MEDIUM
   ⚠ 이건 판정이 아닙니다. 「볼 만한 신호가 있다」까지입니다.

2단계 · LLM 문맥 판정 ──▶  CRITICAL / HIGH / MEDIUM / NONE
   문맥을 봅니다. "죽겠다 배고파서" 를 걸러내는 게 이 단계입니다.
```

키워드만 쓰면 **오탐**이 너무 많고, LLM 만 쓰면 **API 가 죽으면 아예 못 잡습니다.**
둘 다 필요한 이유입니다.

```python
# backend/app/services/safety.py
def keyword_scan(text: str) -> dict:
    """반환값의 level 은 '판정'이 아니라 '신호 강도'다."""
```

### 왜 병렬로 호출하나

```python
# backend/app/services/llm.py — analyze_and_reply()
reply_task  = asyncio.create_task(generate_reply(...))   # 답변 생성
crisis_task = asyncio.create_task(detect_crisis(...))    # 위기 판정
results = await asyncio.gather(reply_task, crisis_task, return_exceptions=True)
```

순차로 하면 LLM 왕복이 2회라 **3초 요건(`NFR-DV-001`)을 넘깁니다.**
병렬이면 실측 **2.19초** 로 통과합니다.

**`return_exceptions=True` 가 중요합니다.** 두 호출은 독립이므로 한쪽이 실패해도
다른 쪽 결과는 살립니다. 위기 판정이 실패했다고 답변까지 날리면 사용자는 그냥
아무 반응도 못 받습니다.

### CRITICAL 이면 답변을 버립니다

병렬로 답변을 이미 만들어놨어도, 위기로 판정되면 **그 답변은 버리고** 긴급 상담
안내로 갑니다.

**그래서 스트리밍(타자 치듯 한 글자씩)을 쓰지 않습니다.** 이미 화면에 흘린 글자는
회수할 수 없습니다. 「응, 그럴 수도 있지」를 절반 보여준 뒤 지우는 것보다
2.19초 기다리는 게 낫습니다.

## 5. LLM 을 어떻게 운영하나

### 공급자가 둘인 이유

| | 언제 | |
|---|---|---|
| **Gemini** | 평소 개발 | 무료 한도 |
| **OpenAI** | 정확도 검사·시연 | **문서상 정본** |

`.env` 의 `LLM_PROVIDER` 로 갈아탑니다.

⚠ **OpenAI 경로를 죽이지 마세요.** 산출 문서(01 기획서, 02 `MLCM_310`/`MLCM_320`)에
「외부 OpenAI API」라고 적혀 있고 **문서는 고치지 않습니다.** 죽이면 문서와 실제가
어긋납니다.

Gemini 는 OpenAI 호환 엔드포인트라 SDK 는 `openai` 를 그대로 씁니다. 다만
**Responses API 를 지원하지 않아** 양쪽 다 Chat Completions 로 통일했습니다.

### 작업마다 다른 모델을 쓰는 이유

무료 한도가 **모델별로** 잡힙니다. 한 모델에 다 몰면 그 모델이 병목이 됩니다.

특히 `reply` 와 `crisis` 는 위에서 본 대로 **동시에** 호출되므로 같은 모델을 쓰면
자기들끼리 한도를 잡아먹습니다. **반드시 갈라놔야 합니다.**

### ⚠ `max_retries=0` 을 되돌리지 마세요

무료 티어는 모델이 통째로 503 이 되는 일이 있습니다. 기본 재시도(2회)면
**죽은 모델 하나가 3초 예산을 통째로 먹습니다 — 실측 13.95초.**

빠르게 실패하고 넘어가는 편이 낫습니다.

### 쓰면 안 되는 모델

| 모델 | 증상 |
|---|---|
| `gemini-3.5-flash` | 503 UNAVAILABLE |
| `gemini-2.5-pro` | 429, 무료 한도 없음 |

실측값은 `docs/llm/USAGE_LOG.md` LLM-004 에 있습니다.

## 6. ⭐ AI 파트 — 왜 모델이 안 들어갔나

**이 장이 이 문서에서 제일 배울 게 많습니다.**

### 지금 상태

`ai/server` 는 **규칙 기반 임시 판정**입니다. `model_version` 이
`rule-placeholder-v0` 이면 모델 결과가 아닙니다. 임계값도 선행연구값이 아니라
임의값이라 **성능 근거로 쓰면 안 됩니다.**

### 왜 모델을 넣지 않았나 — 측정 결과

| 시도 | 참가자 | 피처 | ROC-AUC |
|---|---|---|---|
| 샘플 1개 | 10명 | 8 | 0.485 |
| 샘플 4개 | 40명 | 8 | 0.502 |
| 샘플 4개 | 40명 | **98** | **0.610 ± 0.188** |
| **20회 반복** | 40명 | 98 | **0.528** |

**0.5 는 동전 던지기입니다.**

0.610 을 보고 「오, 좀 되네」 할 뻔했습니다. 그런데 **±0.188** 이 붙어 있습니다.
fold 별로 0.297 ~ 0.864 까지 흔들렸다는 뜻입니다.

그래서 **20번 반복**했더니 평균 **0.528**, 그중 **9번이 0.5 이하**였습니다.
즉 0.610 은 **fold 운**이었습니다.

**왜 이렇게 흔들리나**: 40명을 5-fold 로 나누면 fold 하나에 8명, 그중 양성이 3~4명입니다.
**한 사람이 전체 지표를 좌우합니다.** 데이터가 부족한 겁니다.

> 📌 **인용할 때 0.610 만 떼어 쓰지 마세요.** 반드시 20회 반복값 0.528 과 같이 씁니다.

### 다른 데이터로도 확인했습니다 — 「40명이라서」가 아닙니다

「참가자가 적어서 안 된 것 아니냐」는 반문이 가장 아픈 지점이었습니다.
그래서 **LifeSnaps**(63명 · 감정 라벨 7종 · 피처 65개)로 같은 조건에서
다시 돌렸습니다.

| 감정 | AUC | | 감정 | AUC |
|---|---|---|---|---|
| HAPPY | 0.540 | | TENSE/ANXIOUS | **0.497** |
| TIRED | 0.533 | | SAD | **0.485** |
| NEUTRAL | 0.527 | | ALERT | 0.479 |

**참가자 1.6배 · 피처 8배 · 감정 라벨을 직접 써도 0.48~0.54 입니다.**

- 정작 잡아야 하는 **슬픔·불안이 0.5 아래**입니다
- 0.5 를 넘긴 `TIRED` 는 **수면 시간과 직접 이어진 감정**이라 거의
  동어반복입니다 — 「어제 못 잤으니 피곤하다」를 맞힌 것이지 정서 추정이
  아닙니다

> 💡 **표가 보여주는 패턴이 결론입니다.** 걸음·수면이 잡는 것은
> **각성도**(피곤/각성/이완)이고 **정서가**(슬픔/불안)는 거의 못 잡습니다.
> 생체 신호로 감정 **이름**을 가르는 것 자체에 한계가 있습니다.

### ⚠⚠ 절대 하면 안 되는 것 — 무작위 분할

```python
# ❌ 이렇게 바꾸면 AUC 가 0.9 를 넘습니다. 그리고 그건 거짓입니다.
train_test_split(X, y, random_state=42)

# ⭕ 참가자 단위로 나눕니다
GroupKFold(n_splits=5).split(X, y, groups=participant_id)
```

**왜 부풀려지나**: 피처에 **14일 히스토리**가 들어갑니다. 그래서 같은 사람의
7월 3일과 7월 4일 데이터는 **거의 똑같습니다.**

무작위로 나누면 같은 사람의 3일이 학습에, 4일이 평가에 들어갑니다. 모델은
「이 사람은 우울하다」를 외운 것뿐인데 지표는 0.9 가 나옵니다. **처음 보는
사람에게는 전혀 안 통합니다.**

이걸 **데이터 누수(data leakage)** 라고 합니다. 이 프로젝트에서는 `0.528 → 0.9` 로
극적으로 드러났습니다.

> 💡 시계열·개인 데이터를 다룰 때 **거의 항상** 생기는 함정입니다. 다른 프로젝트에서도
> 「분할 기준이 뭔가」를 제일 먼저 확인하세요.

### 모델을 교체할 때

- **`_predict()` 하나만** 바꿉니다. 반환 6필드는 비즈니스 서버와의 **계약**입니다
- ⚠ **`risk_level_of()` 는 모델이 아니라 정책**(04 문서 6항)입니다. 같이 들어내지 마세요.
  비즈니스 서버가 이 계산을 다시 하면 **규칙이 두 곳에 생겨** 어긋납니다
- ⚠ **데이터가 없을 때 `NORMAL` 을 쓰지 않습니다.** 실측치가 3일치 미만이면 **422 로 끊습니다.**
  편차 0 을 「정상」으로 적재하면 **관제 대시보드에서 위험을 놓칩니다**

## 7. ⭐ 정신건강 UI 에서 하면 안 되는 것

일반적인 UX 규칙이 아닙니다. **이 도메인에만 있는 규칙**이고, 각각 이유가 있습니다.

| 금지 | 왜 |
|---|---|
| **경고색(빨강·주황)** | 불안을 키워 **회피**를 유발합니다. 앱을 안 열게 됩니다. 주목도는 **구조**로 만듭니다 |
| **웃는 마스코트 (위기 시)** | 「내 상태를 무시한다」로 읽힙니다 |
| **슬픈 마스코트 (위기 시)** | 감정을 증폭시키고, 「내가 얘까지 힘들게 했나」가 됩니다 |
| **「위기」·「절망」 같은 감정명 라벨** | 관찰이 아니라 **사람에 대한 판정**으로 읽힙니다. 진단은 02 요구사항이 금지합니다 |
| **위기 시 콘텐츠 추천** | 「음악이나 들으라고?」 즉시 중단합니다 |

### 그럼 위기일 때 마스코트는 어떻게 하나

**담담하게** 합니다. 웃지도 슬퍼하지도 않습니다.

```dart
// frontend/app/lib/widgets/common_widgets.dart
enum MascotMood { smile, calm, thinking }

static MascotMood moodFor(String? riskLevel) => switch (riskLevel) {
      'CRITICAL' || 'CAUTION' => MascotMood.calm,
      _ => MascotMood.smile,
    };
```

`calm` 은 **눈은 그대로 두고 입만 닫습니다** (`• · •`). 배경 그라데이션도
**일부러 어둡게 하지 않았습니다** — 어둡게 하면 그게 경고색 역할을 합니다.

### 「말하지 않기」와 「숨기기」는 다릅니다

감정명을 안 쓴다고 상태를 숨기는 게 아닙니다. **문장으로 말합니다.**

```
❌  오늘의 감정: 「위기」
⭕  지금 마음이 많이 무거워 보여요. 혼자 견디지 않아도 괜찮아요.
```

## 10. 실패 사례집 — 테스트가 있는데 왜 못 잡았나

**이 장이 가장 실무적입니다.** 「테스트를 짰다」와 「버그를 잡는다」는 다릅니다.

### 사례 1 — 조건이 실기기와 달랐다

**증상**: 챗봇 카드가 실기기에서 넘쳤는데, 오버플로 테스트는 통과.

**원인**: 테스트가 카드에 **578dp** 를 주고 있었습니다. 실기기는 **344dp** 입니다.

| 빠뜨린 것 | 크기 |
|---|---|
| 하단 네비게이션 바 | ~80dp |
| 상·하단 안전 영역 | ~48dp |
| 화면 크기를 390×844 로 오인 | 실제 **411×731** |

**교훈**: 화면 테스트는 **기기 조건을 그대로 재현**해야 합니다. 그리고 고치기 전
코드로 되돌려서 **정말 실패하는지** 확인하세요. 안 그러면 「통과하는데 아무것도
검증 안 하는 테스트」가 됩니다.

### 사례 2 — 서비스를 주입 안 해서 진짜 네트워크로 나갔다

**증상**: 「최근 대화」 배지 테스트가 조용히 실패.

**원인**: 화면 코드가 주입받은 서비스 대신 전역 `AppServices.settings` 를 쓰고
있었습니다. 테스트는 mock 을 넘겼는데 **화면은 그걸 안 봤습니다.**

**교훈**: mock 을 넘겼다고 쓰이는 게 아닙니다. **요청이 실제로 mock 으로 갔는지**
확인하세요 (요청을 기록하는 spy 를 쓰면 보입니다).

### 사례 3 — 옆 페이지도 트리에 있었다

**증상**: 「저장된 성격이 첫 화면으로 온다」 테스트가 **틀려도 통과.**

**원인**: `PageView` 는 **옆 페이지도 미리 만들어 둡니다.** 그래서 기본 선택이
틀려도 `find.text('이성적인 분석가')` 는 찾아냅니다.

```dart
// ❌ 존재로 판정
expect(find.text('이성적인 분석가'), findsOneWidget);

// ⭕ 실제로 어느 페이지에 있는지
expect(view.controller?.page?.round(), 기대_인덱스);
```

**교훈**: 「화면에 있다」 ≠ 「화면에 보인다」.

### 사례 4 — 카드만 지우고 제목을 남겼다

설정에서 페르소나 카드를 뺐는데 **「대화 성격」 절 제목이 남아서**, 아무것도 없는
빈 절이 화면에 떴습니다. 테스트가 카드만 확인하고 제목은 안 봤습니다.

**교훈**: 뭔가를 지울 때는 **껍데기도 같이 지웠는지** 확인하세요.

### 사례 5 — 주석이 거짓말했다

`role` 은 JWT 클레임이 아니라 **DB `USERS.role`** 을 봅니다. 토큰에 넣긴 하는데
**아무도 안 읽습니다.**

「여기서 바꾸면 기본값이 됩니다」라는 주석이 사실이 아니었고, 그게 **README 5곳에
복제**돼 있었습니다.

**교훈**: 주석은 코드와 같이 안 늙습니다. **동작이 궁금하면 주석 말고 코드를 보세요.**

### 사례 6 — 있는 척하는 UI

- 빈 버튼 3개 (챗봇 메뉴·검색 등)
- **빨간 배지가 붙은, 눌리지 않는 알림 종**
- **효과가 없는** 설정 토글

**코드를 읽어서는 안 보입니다.** 실행해서 눌러봐야 나옵니다.

**교훈**: 화면 작업은 **켜서 눌러보는 게 리뷰의 일부**입니다.

### 사례 7 — 자정이 지나면 화면이 빈다

`seed_demo_persona.sql` 은 `now()` 기준으로 14일치를 넣습니다. **자정을 넘기면
「오늘」 데이터가 없어져** 홈이 `-` 로 보입니다.

**교훈**: 상대 시각으로 만든 시드 데이터는 **시간이 지나면 조용히 상합니다.**

### 사례 8 — 앱만 다른 이름을 쓰고 있었다

챗봇 성격이 앱에서는 「다정한 공감가 / 이성적인 분석가」, 문서·기획서·시안
**세 곳에서는** 「따스한 공감형 / 현실적인 조언형」이었습니다.

**화면에 큼직하게 뜨는 글자인데도 아무도 못 봤습니다.** 앱만 보면 아무
이상이 없거든요. **어느 쪽이 맞는지 알아야만 문제로 보입니다.**

원인은 이름이 **두 곳에 따로 적혀 있던 것**이었습니다 — 대화 화면 머리말과
카드에요. 한쪽만 고치면 조용히 갈립니다.

**교훈**: 정본이 딴 데 있는 값은 **기계가 대조**하게 하세요. 지금은
`persona_label_test.dart` 가 화면설계서 추출본을 직접 읽어 맞춰봅니다.
`health_permission_drift_test.dart`·`test_schema_drift.py` 와 같은 계열입니다.

### 사례 9 — 서버에는 있는데 앱이 안 쓰고 있었다

체성분 조회와 비밀번호 변경은 **백엔드 엔드포인트가 이미 있었습니다.**
`GET /body-composition` 도 `PATCH /users/me/password` 도요. 부르는 화면만
없었습니다.

더 나쁜 건 **체성분은 수집 동의까지 받고 있었다**는 점입니다. 받은 데이터를
볼 곳이 없는 채로요.

**교훈**: 「구현했다」를 API 단위로 세면 이런 게 안 보입니다. **화면에서
쓰이는지**까지 봐야 합니다.

### 사례 10 — 단독으로는 통과하는 테스트

`A TextEditingController was used after being disposed.`

`showDialog` 가 끝나자마자 컨트롤러를 dispose 하는데, 그 시점에 다이얼로그는
**아직 닫히는 중**이라 `TextField` 가 죽은 컨트롤러를 읽습니다.

테스트를 단독으로 돌리면 통과하고 **전체 실행에서만** 터졌습니다. 처음엔
테스트끼리 간섭하는 줄 알았습니다.

**교훈**: 단독 통과 / 전체 실패는 **테스트 문제가 아니라 앱 문제일 때가
많습니다.** 그리고 릴리스 빌드는 assert 가 빠져 조용히 넘어가므로 더 나쁩니다.

### 사례 11 — 빌드는 성공하는데 클래스가 없었다

`workmanager_android` 가 AGP 9 에서 KGP 적용을 건너뛰면서, 소스는 `java.srcDirs`
에 넣어 **`.kt` 를 아무도 컴파일하지 않았습니다.**

**모듈 빌드는 에러 없이 성공**하고 클래스만 안 나옵니다. 그래서 엉뚱한 곳에서

```
GeneratedPluginRegistrant.java:59: error: cannot find symbol
  new dev.fluttercommunity.workmanager.WorkmanagerPlugin()
```

에러 메시지만 보면 「등록 코드가 잘못됐나」 싶지만, 원인은 **두 단계 앞**에

동작했고, 그 차이가 단서였습니다.

**교훈**: 「없다」는 에러를 만나면 **만들어지긴 했는지**부터 확인하세요.
`find build/<모듈> -name "*.class"` 한 줄로 갈렸습니다.

### 사례 12 — 안전장치가 자기 발등을 찍었다

PowerShell 의 `SupportsShouldProcess` 를 켜면 `$WhatIfPreference` 가 **안에서

**교훈**: 미리보기 모드를 붙였으면 **미리보기로도 한 번 돌려보세요.** 안 그러면
「안전하게 확인하려던 사람만」 에러를 봅니다.

### 사례 13 — 명세를 잘못 읽었다

화면설계서의 「설명 5줄」을 **「항목 5개」로 읽었습니다.** 문서는 `❹~❼` 병합을
명시적으로 허용하고 있었고, `MAIN_JOIN_01` 은 이미 5줄에 7항목을 넣고 있었습니다.

**교훈**: 제약이 이상하게 빡빡해 보이면 **원문을 다시 읽으세요.** 대개 내가 잘못
읽은 겁니다.

### 사례 14 — 안전장치가 **한 곳에만** 있었다

`ENCRYPTION_KEY` 는 `CHANGE_ME` 면 서버가 거부합니다. 그런데 **`JWT_SECRET` 에는
그 검사가 없었습니다.** `.env.example` 이 `JWT_SECRET=CHANGE_ME` 로 배포되고
**이 저장소는 공개**입니다.

새 PC 에서 예제를 복사만 하고 값을 안 바꾸면 서명 키가 공개된 상태로 뜹니다.
그러면 누구나 이걸 직접 서명해 `/admin/*` 을 엽니다.

```json
{"sub": "<아무 uuid>", "role": "ADMIN", "purpose": "access"}
```

그 뒤에 **전 사용자의 정서 리포트**가 있습니다.

**교훈**: 같은 성격의 값이 여럿이면 **하나에만 방어를 넣기 쉽습니다.** 「비슷한 게
또 있나」를 매번 물어보세요. 그리고 이런 값은 **조용히 도는 것보다 못 뜨는
편이 낫습니다.**

### 사례 15 — 글자 수와 바이트 수를 헷갈렸다

비밀번호에 `max_length=64` 를 걸어뒀는데 bcrypt 는 **72바이트** 한계입니다.
한글은 한 글자가 3바이트라 **25자면 75바이트** — 스키마는 통과하고 해시 단계에서
`ValueError` 가 터집니다. 사용자에게는 **500** 으로 보입니다.

**한국어 서비스라 실제로 밟을 수 있는 경로**인데, 영어로 테스트하면 영원히
안 보입니다.

**교훈**: 길이 제한은 **무엇을 세는지** 확인하세요. 그리고 **잘라서 저장하지
마세요** — 입력한 문자열과 실제 비밀번호가 달라집니다.

### 사례 16 — 에뮬레이터에서만 멀쩡했다 ⭐

하루에 **셋이 한꺼번에** 나왔습니다.

| 무엇 | 증상 | 어디서 나야 보이나 |
|---|---|---|
| 평문 HTTP 차단 | 릴리스 APK 가 **전 API 실패** | 릴리스 빌드 |
| `tel` 패키지 가시성 | **109 전화 안 걸림** | 실기기 |
| 카드 탭 없음 | 추천이 **아무 데도 안 감** | 눌러봐야 |

`targetSdk` 36 은 평문 HTTP 를 기본 차단하는데, Flutter 는
`src/debug/AndroidManifest.xml` **에만** 허용을 넣어둡니다. 그래서 디버그·에뮬레이터는
멀쩡하고 릴리스만 죽습니다.

`tel` 은 더 얄궂습니다 — 같은 매니페스트에 Health Connect 용 `<queries>` 가 있고
주석에 「Android 11+ 패키지 가시성 제한 때문에 빠지면 미설치로 보인다」고
**적혀 있었습니다.** 기전은 알고 있었는데 전화에는 적용이 안 됐습니다.

**교훈**: 「테스트가 통과한다」와 「빌드가 된다」와 **「기기에서 동작한다」가 각각
다른 것을 보증합니다.** 제출 전에 **릴리스로 한 번은 빌드해서 켜보세요.**
그리고 증상이 「서버가 죽었다」·「전화 앱이 없다」로 보일 때 이 표를 떠올리세요.

### 사례 17 — 검사가 **우연히** 통과하고 있었다 ⭐

관통 점검의 「위기 시 콘텐츠 추천 중단」이 **가드를 넣기 전에도 통과**했습니다.

당시 `/contents/recommendations` 에는 위기 가드가 없었고, 0건이 나온 이유는
힐링 콘텐츠를 `DESPAIR`·`CRISIS` 감정에 **등록하지 않는다는 큐레이션 기준**
때문이었습니다.

> **「가드가 있어서」가 아니라 「줄 게 없어서」 0건이었습니다.**

누군가 그 감정에 콘텐츠를 넣는 순간 조용히 뚫렸을 것입니다 — **코드를 아무도
안 건드려도** 일어날 수 있는 일입니다.

**교훈**: 초록불이 뜨면 **왜 통과했는지**를 한 번은 확인하세요. 특히 「비어 있으면
정상」 류의 검사는 **비어 있을 다른 이유**가 없는지 봐야 합니다. 그리고 그런
보장은 데이터가 아니라 **코드로** 걸어두세요.

### 사례 18 — 목 응답이 실제보다 관대했다

앱의 오류 문구 인코딩을 의심했습니다. Dart `http` 는 charset 이 없으면 보통
**latin-1** 로 폴백하고, 실제 FastAPI 는 charset 을 안 붙이니까요.

**틀렸습니다.** `http` 1.6 이 `application/json` 에 한해 UTF-8 을 씁니다.

```dart
/// - Defaults to [utf8] if the `Content-Type` is `application/json`
/// - Otherwise, defaults to [latin1] for compatibility
```

다만 기존 테스트들이 목 응답에 **`charset=utf-8` 을 직접 붙여둬서**, 이 의존이
깨져도 알 수 없는 상태였습니다.

**교훈 둘**. 보고하기 전에 **재현**하세요 — 그럴듯한 추론이 틀리는 경우가 많습니다.
그리고 목 데이터는 **실제 응답 그대로** 만드세요. 편의로 붙인 헤더 하나가
검증을 통째로 무의미하게 만듭니다.

### 사례 19 — 주석이 구현과 달랐다 (또)

정서 리포트 결합 차트에 「**감정 추이와 같은 시간축**」이라고 적혀 있는데,
구현은 두 계열을 **각자 화면 폭에** 펼치고 있었습니다.

걸음은 0 을 제외합니다(「0걸음」과 「측정 안 됨」은 다르니까 — 그 판단 자체는
맞습니다). 그래서 두 배열 길이가 흔히 어긋나고, 그러면 **같은 x 가 서로 다른
날**을 가리킵니다. 「그날 수면이 줄고 활동도 줄었다」로 읽히는 그림이 실제로는
다른 날 둘을 겹쳐놓은 것입니다.

**교훈**: 사례 5 와 같은 병입니다. **주석은 의도고 코드가 사실**입니다. 다만
이번엔 주석이 옳고 코드가 틀렸습니다 — 그러니 **주석을 지우지 말고 코드를
맞추세요.** 그림은 틀려도 에러를 안 냅니다.
