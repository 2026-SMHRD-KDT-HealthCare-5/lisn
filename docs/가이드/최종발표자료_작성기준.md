## 4. 문장 기준

지금까지 지적받아 고친 것들입니다. **같은 실수를 반복하지 않습니다.**

### 4-1. 제목은 명사구로 끝냅니다

```
⛔ 왜 서버를 둘로 나눴나          ✅ 둘로 나눈 서버
⛔ 감정 분류 모델은 검증하고 접었습니다  ✅ 감정 분류 대신 개인 기준선 이탈 탐지
⛔ 못 한 것을 그대로 말씀드립니다     ✅ 확장 가능한 부분
```

### 4-2. 자책 문구를 전부 뺍니다

**「못 했다」는 표현은 한 번도 쓰지 않습니다.** 사실은 그대로 두되
프레임을 **「다음 단계」·「확장 가능」**으로 잡습니다. 자책은 방어가
되지 않고, 심사위원에게 **감점 사유를 대신 찾아주는 일**입니다.

```
⛔ 못 한 것을 그대로 말씀드립니다      ✅ 확장 가능한 부분
⛔ 배포 인프라 미정                  ✅ (해결됨 — NCP + Docker Compose)
⛔ 평가 holdout 없음                ✅ 평가셋 확장 — 다음 단계
⛔ 미수신 감지 스케줄러 남음           ✅ (해결됨 — 슬라이드에서 제거)
```

⚠ **먼저 꺼내지 않습니다.** 물어보면 §4-6 의 틀로 답합니다.

### 4-3. 같은 어미를 연달아 쓰지 않습니다

한 슬라이드에서 `~합니다`가 네 번 이상 이어지면 고칩니다.

### 4-4. 애매한 문맥을 남기지 않습니다

```
⛔ 국내 라벨 데이터셋을 구하지 못해     ← 무엇을 못 구했는지 불명확 + 변명조
✅ 참가자 단위로 나눠 평가했더니
```

#### ③ 발표된 수치의 성격 — 재현해서 확인했습니다

> 「저희와 **같은 데이터셋으로 70%를 보고한 논문**을 그대로 재현했습니다.
> 표본이 정확히 일치했고, **그 지표의 기준선이 66.7%**였습니다.
> 참가자를 갈라 놓으면 그 이득이 남지 않았습니다.」

**이게 가장 강한 재료입니다.** 「우리가 못 한 게 아니라 원래 그렇다」를

## 5. ⭐ 영역별 균형 잡힌 자랑거리 — 다섯 곳 중 하나도 빠뜨리지 않습니다

**심사는 "AI 만 잘했다"가 아니라 "전 영역이 다 되는 팀인가"도 봅니다.**
아래는 브리프 채점 비중(§1) 순으로 정렬했고, **각 행 하나는 발표에서
반드시 한 번은 나와야 합니다.** "이미 있음"은 그 슬라이드를 말할 때
문장을 빼먹지 않으면 되고, "대본에만"은 슬라이드를 고치지 않고
**발표자 멘트**로만 채웁니다(슬라이드 골격은 §2 규칙대로 안 바꿉니다).

| 순위 | 영역 | 반드시 할 말 (검증됨) | 어디서 말하나 |
|---|---|---|---|
| 1 | **AI** | 코드 주석에 스스로 "성능 근거로 쓰지 말 것"이라 적혀 있던 **임의 집계식**을 로지스틱 회귀로 교체 — 참가자 내부 AUC **0.491 → 0.609** | ✅ 슬라이드 9 (본문 + 막대그래프) |
| 2 | **백엔드** | 위기 키워드 필터는 **비즈니스 서버 안에** 둡니다 — AI 서버가 죽어도 탐지가 멈추지 않습니다 | ✅ 슬라이드 8 |
| 3 | **프론트** | **릴리스 빌드에서만 드러나는 결함 3종**(평문 HTTP 차단 · 패키지 가시성)을 제출 전에 실측으로 잡았습니다 — 에뮬레이터·디버그로는 절대 안 보이는 것들입니다 | ⚠ **대본에만** — LIVE DEMO(슬라이드 6) 소개 멘트 또는 Q&A |
| 4 | **DB** | 테이블 **9곳 전부 UUID v4** — 열거 공격 방지 | ✅ 슬라이드 14 |
| 5 | **배포** | 클라우드에 실제로 배포했습니다 — **NCP + Docker Compose, HTTPS(Let's Encrypt)** | ⚠ **제안 · 확정 대기** — 슬라이드 8 STACK 줄에 시각 정보로만 추가(말은 안 함, §5-1) |

### 5-1. 왜 이 다섯 개이고, 왜 이렇게 나눴나

- **"목업 데이터가 없다"를 프론트 대표 문장으로 쓰지 않습니다.** 실제
  API 연동은 **당연히 해야 하는 것**이라 자랑이 아니라 방어선입니다.
  대신 **릴리스 빌드 전용 결함**은 "빌드가 된다"와 "동작한다"가 다르다는
  것을 실측으로 보인 것이라 **참신하고 검증 가능**합니다
  (`flutter build apk --release` 로만 재현됨 — CLAUDE.md 참조)
- **배포는 브리프 필수 항목이 아니라서** 슬라이드 골격에 새 줄을 만들
  이유가 약합니다. 대신 **7분 발표 예산이 이미 빠듯해서**(§5-2) 말로
  넣는 대신 **STACK 줄에 시각 정보로만** 추가하는 절충안입니다. 최종
  문구는 PM 확정 대기 — 확정되면 `build_deck.js` 로 포팅합니다(§6)
- **DB 는 브리프에 직접 명시되지 않았지만** 슬라이드 14 표에 이미
  "UUID v4 · 테이블 9곳 전부"가 있어 **추가 작업 없이** 말하기만 하면
  됩니다

### 5-2. 발표 시간 예산 — 말로 더 넣기 전에 계산부터

`docs/가이드/시연_대본.md` 의 실제 내레이션(초/글자 수)을 세어보면
이 팀의 발표 속도는 **약 190자/분**입니다(정서 케어 서비스라 일부러
천천히 읽음 — 일반 발표보다 느립니다). **발표 10분 = 시연영상 3분 +
발언 7분**이므로, 발언 예산은 **약 1,330자**.

16장 중 나레이션이 필요한 건 9장(4·5·8·9·10·12·13·14·15)뿐이고 나머지
7장(표지·CONTENTS·섹션커버 3개·LIVE DEMO 소개·감사합니다)에 70초쯤을
먼저 빼면, **콘텐츠 슬라이드 1장당 평균 37초(약 123자)** 밖에 안 남습니다.
**새 문장 하나를 추가하면 그 슬라이드가 예산의 상당 부분을 더 씁니다** —
말로 넣을 내용은 이 계산을 먼저 하고 결정하세요.
