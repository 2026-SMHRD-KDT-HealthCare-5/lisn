## 2. 「모델을 제대로 했나」에 대한 실측 답변

### 2-1. Isolation Forest — 브리프가 이름을 박은 방법을 재봤습니다

`ai/train/eval_isoforest.py` · LifeSnaps 62명 · 4086 표본 ·
참가자 분할 · 참가자 내부 AUC · 부트스트랩 2000회.

| 구성 | 참가자 내부 AUC | 95% |
|---|---|---|
| 규칙 (중앙값·MAD robust z) | 0.491 | 0.452~0.526 |
| **Isolation Forest (전역)** | 0.473 | 0.449~0.533 |
| **Isolation Forest (개인별)** | 0.494 | 0.470~0.516 |
| **우리 배포본 (학습된 집계)** | **0.609** | **0.563~0.642** |

**Isolation Forest 는 규칙과 구분되지 않고**(+0.001 · +0.005, 둘 다
구간이 0 포함), **우리 배포본이 +0.115** `[+0.055,+0.177]` 로 유의하게
낫습니다.

> **방어 문장** — 「브리프가 지정한 Isolation Forest 를 전역·개인별 두
> 형태로 구현해 같은 조건에서 비교했고, **우리 방식이 유의하게 나아서**
> 그쪽을 채택했습니다. 안 써본 것이 아니라 **재보고 고른 것**입니다.」

### 2-3. (선택) 정서 상태 분류 — 왜 안 넣었나

**브리프에서 「선택」으로 표시된 항목**입니다. 그래도 **26회 검증**했고,
넣지 않을 근거를 만들었습니다.

핵심 실측 세 가지:

**① 같은 데이터로 「70%」를 보고한 논문을 재현했습니다.**
(Karim et al. 2025, medRxiv 2025.02.13.25322254 — LifeSnaps, 38명)

| | 값 |
|---|---|
| 그 논문의 지표(클래스별 평균 정확도)의 **기준선** | **66.7%** |
| 논문 보고치 | 70.0% (**기준선 대비 +3.3%p**) |
| 우리 재현 · 무작위 5겹(논문과 같은 조건) | 66.1% |
| 우리 재현 · **참가자 5겹**(새 사용자) | 65.4% |
| 우리 재현 · 참가자 셔플 대조 | 65.4% |

**표본이 정확히 재현됩니다**(1167일·38명·276/313/578). 논문 방법 절에
`leave-one-subject-out`·`grouped`·`between-subject` 가 **0건**입니다.

**② 이 분야 전체가 그렇습니다.**
[JMIR 2025;27:e77066](https://www.jmir.org/2025/1/e77066) — 42편 전수 검토.

**③ 「되는 경우」의 조건은 다릅니다.**
[npj Digital Medicine 2024](https://www.nature.com/articles/s41746-024-01333-z)

### 2-4. 그리고 필수 항목은 실제로 개선했습니다

브리프의 **필수**는 「기저선 이탈 기반 위험 스코어」입니다.
그 스코어를 **검증하고 개선했습니다.**

```
참가자 내부 AUC   기존 규칙 0.491  →  학습된 집계 0.609
이득 +0.115 (참가자 단위 부트스트랩 95% +0.056 ~ +0.176)
```

- **입력을 하나도 안 늘렸습니다** — 서버가 이미 읽던 7개 지표뿐
- **경보 총량이 같습니다** — 모델 확률을 규칙과 같은 분포로 옮김
- **규칙 바닥·폴백** — 모델이 없거나 지표가 모자라면 규칙으로 동작
- 구현 `ai/server/model_score.py` · 안전 테스트 8건 통과

## 3. 미충족 항목 — 먼저 말하고 이유를 답니다

### 3-1. ✅ 앱 사용 로그 — **2026.08.25 구현했습니다**

브리프 **개발목표 첫 줄**의 「앱 사용 로그 + 웨어러블 생체신호」 중
앞쪽입니다. 8/25 에 **스키마부터 판정까지 관통으로** 넣었습니다.

| 층 | 파일 |
|---|---|
| 수집(Android) | `frontend/app/android/.../AppUsagePlugin.kt` — `UsageStatsManager` |
| 앱 인터페이스 | `frontend/app/lib/services/app_usage_reader.dart` |
| 동기화 | `lifelog_sync.dart` `_attachUsage()` — 하루 경계로 갈라 읽음 |
| 전송 규격 | `backend/app/schemas/lifelog.py` |
| 적재 | `db/schema.sql` `[05-U]` — 3컬럼 |
| **판정** | `ai/server/main.py` `_FEATURES` — 화면사용·야간사용·앱전환 |

**지표 셋** — 「무슨 앱을 썼나」가 아니라 **「평소와 다른가」**를 잽니다.

```
screen_time_min    구간 내 화면 사용 시간
night_screen_min   그중 22시~06시 사용 시간 (수면 방해·야간 반추)
app_session_count  앱 전환 횟수 (짧고 잦은 확인)
```

**웨어러블 지표와 완전히 같은 방식**(개인 14일 기준선 대비 robust z)이라
특별 취급이 없습니다. 실측 확인:

```
① 웨어러블은 평소인데 앱 사용만 무너진 날
   → anomaly 1.0 · 이탈 지표 ['화면사용','야간사용','앱전환']  ✅
② 앱 사용 권한이 없는 사용자(셋 다 None)
   → anomaly 1.0 · 웨어러블 지표만으로 판정 계속            ✅
```

#### 설계에서 지킨 것 세 가지

**① `AccessibilityService` 를 쓰지 않았습니다.** 그쪽은 **화면 내용까지**
읽을 수 있어 Play 정책상 별도 심사 대상이고, 필요한 것보다 훨씬 많은
것을 봅니다. `UsageStatsManager` 는 「어떤 앱이 언제 앞으로 나왔나」만
줍니다.

**② 패키지명·앱 이름을 저장하지 않습니다.** 네이티브에서 **집계값 셋으로
접어서** 넘깁니다. DB 에도 앱 식별자가 없습니다.

**③ 권한이 없으면 `0` 이 아니라 `null` 입니다.** 「0분 썼다」와 「권한이
없어 모른다」는 다릅니다. 0 으로 적재하면 개인 기준선이 내려앉아 실제로
많이 쓴 날이 이탈로 안 잡힙니다. 테스트로 고정했습니다
(`test/app_usage_test.dart` 8건).

> **방어 문장** — 「브리프의 두 입력을 다 구현했습니다. 앱 사용 로그는
> `UsageStatsManager` 로 받되 **패키지명은 저장하지 않고 집계값 셋만**
> 씁니다. `AccessibilityService` 는 화면 내용까지 볼 수 있어 의도적으로
> 피했습니다. 특별권한이라 미승인 사용자가 있는데, 그 경우 **웨어러블
> 지표만으로 판정이 계속됩니다.**」

⚠ **남은 것 — 실기기 확인.** 에뮬레이터에는 사용 이력이 거의 없어 값이
0 에 가깝습니다. Health Connect 실기기 검증과 함께 묶어서 확인하세요.

### 3-2. ⚠ HRV — 컬럼은 있는데 값이 안 들어옵니다

브리프는 「심박·HRV」를 명시하지만, **삼성헬스가 Health Connect 에 HRV 를
넘기지 않습니다.** 스키마에는 `hrv` 컬럼을 뒀고(`LIFELOG_METRICS`),
넘어오는 기기에서는 바로 쓸 수 있습니다.

### 3-3. ⛔ AI Hub 감성·정신건강 데이터 — 접근 불가

**내국인 안심존**에서만 열람 가능해 직접 내려받을 수 없습니다.
GLOBEM·LifeSnaps·PMData 로 대체했고, 브리프의 「공개 웨어러블
(수면·HRV) 데이터셋」 항목은 이것으로 충족됩니다.

### 3-4. ⛔ Apple HealthKit / Kafka·gRPC — 범위 밖

- HealthKit: **macOS·Xcode·Apple Developer Program 필요** → 제외 확정
  (⚠ 「기술적으로 불가능」이라고 하지 마세요. `health` 패키지는 HealthKit
  도 감쌉니다. **장비·계정·일정이 사유**입니다)
- Kafka·gRPC: 브리프에 **「(심화)」로 표시된 항목**

## 4. 예상 질문과 한 줄 답

| 질문 | 답 |
|---|---|
| 「감정 분류 모델은 어디 있나요?」 | **브리프에 「선택」으로 적힌 항목**입니다. 26회 검증했고, 같은 데이터로 70% 를 보고한 논문을 재현해 보니 그 지표의 기준선이 66.7% 였습니다. 근거가 없어 채택하지 않았습니다 |
| 「Isolation Forest 쓰라고 했는데요?」 | 전역·개인별 두 형태로 구현해 비교했습니다. 규칙과 구분되지 않았고(0.473·0.494), 저희 방식이 0.609 로 유의하게 나아 그쪽을 골랐습니다 |
| 「LightGBM Ensemble 은요?」 | 6종을 같은 조건에서 비교했습니다. 62명 규모에서는 부스팅이 과적합돼 로지스틱 회귀가 일관되게 나았습니다 |
| 「성능이 0.6 이면 낮은 것 아닌가요?」 | 이 분야 표본 중앙값이 60.5명이고 42편 중 외부 검증은 1편입니다. 저희는 **참가자 분할 + 셔플 대조 + 중첩 교차검증**까지 했습니다. **같은 잣대로 재면 발표된 수치 상당수가 저희와 비슷하거나 낮습니다** |
| 「기업 데이터는 받았나요?」 | **브리프는 처음부터 「오픈 데이터 활용」입니다.** 공개 데이터셋 3종으로 수행했습니다 |
| 「그래서 미완성 아닌가요?」 | 브리프의 완성도 기준은 **「MVP(데모 수준)」**입니다. **필수 항목은 전부 동작**하고 클라우드에 배포돼 있습니다. 개발목표의 두 입력(앱 사용 로그·웨어러블)도 **둘 다 판정에 들어갑니다** |
| 「앱 사용 로그는 개인정보 아닌가요?」 | 패키지명·앱 이름·화면 내용을 **저장하지 않습니다.** 화면 시간·야간 시간·전환 횟수 **집계값 셋**만 받고, `AccessibilityService` 는 의도적으로 피했습니다 |
| 「AI 가 실제로 뭘 하나요?」 | 개인 14일 기저선 대비 이탈을 재고, 그 이탈들을 **학습된 집계**로 합쳐 위험 스코어를 냅니다. 규칙 대비 참가자 내부 AUC **0.491 → 0.609** 로 올렸습니다 |

## 5. ⚠ 말하면 안 되는 것

- ❌ **「기업이 데이터를 안 줘서 못 했다」** — 브리프는 오픈 데이터를
  지정했습니다. 사실과 다르고 브리프를 안 읽은 것으로 보입니다
- ❌ **「감정 분류를 못 했다」** — 「선택 항목을 검증 후 채택하지
  않았다」가 정확합니다
- ❌ **「85% 정확도 목표」** — 우리 기획서 초안의 값이고 폐기됐습니다
  (`PL-20`~`PL-24`). 발표자료 PPTX 에 아직 남아 있으면 **먼저 고치세요**
- ❌ **「선제 접촉이 곧 나빠질 사람을 미리 찾는다」** — 3일 앞 예측은
  어떤 구성으로도 0.5 를 못 넘었습니다. **「지금 평소와 다른 사람에게
  먼저 말을 건다」**가 정확합니다
- ❌ **「iOS 는 기술적으로 불가능」** — 장비·계정·일정이 사유입니다
