## `NFR-DV-001`·`NFR-TS-001` — 미달이었다가 통과로 바뀐 경위

처음 측정은 **두 건 다 미달**이었습니다(3216.1ms · 6608.3ms).

### 원인 — 버릴 응답을 기다리고 있었습니다

어느 호출이 긴 쪽인지 직접 쟀습니다(n=5).

| | `detect_crisis` | `generate_reply` |
|---|---|---|
| 위기 발화 | 1920.0 / 4007.5ms | **5151.5 / 6379.9ms** |
| 일반 발화 | 1347.7 / 2623.4ms | 2496.1 / 2936.9ms |

`analyze_and_reply` 는 둘을 병렬로 부르고 `gather` 로 **둘 다** 기다렸는데,
CRITICAL 이면 응답을 버립니다. 위기 경로의 시간은 사실상 **버려지는 값을
기다리는 시간**이었습니다.

버릴 것이 확정되면 응답 생성을 취소하도록 고쳐 통과했습니다.
개선 후 `NFR-TS-001` 중앙값 2058.9ms 는 `detect_crisis` 단독 실측
1920.0ms 와 거의 같습니다 — **의도한 메커니즘대로 동작합니다.**

### ⚠ 첫 구현은 효과가 없었습니다

`severity == "HIGH"` 일 때만 취소하게 했더니 오히려 나빠졌습니다
(4964 → 6797ms). 「죽고 싶다」에 LLM 이 **MEDIUM 을 주는 일이 잦고**
(프롬프트가 "실행 의도가 안 드러나면 MEDIUM"), 최종 CRITICAL 은
**HIGH 키워드**가 함께 있어서 나오는데 `analyze_and_reply` 가 키워드를
받지 않아 알 수 없었습니다.

> **판정 규칙이 두 곳에 있으면 이런 일이 납니다.** 규칙이 `chat.py`
> `_decide()` 안에만 있어서 성능 최적화 쪽이 조건을 **따로 적었고 틀렸습니다.**
> `risk_policy.level_for()` 한 곳으로 올리고 양쪽이 같은 함수를 쓰게 했습니다.

### 검토했으나 채택하지 않은 것

`NFR-DV-001` 본문은 "명백한 위기 표현은 **API 왕복 없이 즉시 판정**"을
규정하는데, 이건 여전히 미구현입니다. 그대로 구현하면 3초를 통과하지만
**HIGH 키워드 정밀도가 0.500**(평가셋 200건 · TP 10 / FP 10)이라 오탐
절반이 109 화면으로 갑니다.

```
"예전에 죽고 싶었는데 지금은 괜찮아요."   "친구가 죽고 싶대요."
"소설에 자살하는 인물을 넣으려는데"       "시험 망해서 죽고싶다 ㅋㅋ"
```

**요건의 전제가 실측과 다릅니다** — 「명백한 위기 표현」이 HIGH 사전이
실제로 잡는 것과 일치하지 않습니다. 성능 목표는 이미 충족하므로 급하지
않지만, 나중에 구현하려면 이 정밀도 문제를 먼저 풀어야 합니다.

## ⚠ 측정할 때마다 서버 로그를 함께 보세요

**앞선 두 번의 측정이 무효였습니다.** `.claude/launch.json` 의
`cmd /c "cd backend && set LLM_PROVIDER=openai && ..."` 에서 `&&` 가
전달되지 않아 서버가 Gemini 로 떴고, 모든 호출이 429 로 실패했습니다.
**그 실패 왕복이 170ms 로 찍혀 「통과」로 나왔습니다.**

`LLM-005` 가 이 함정을 적어뒀는데(*"응답 시간만 재면 정상으로 오인합니다"*)
**같은 자리를 다시 밟았습니다.** 숫자만 보면 구분이 안 됩니다.

쉘 문법에 의존하지 않도록 `launch.json` 을 고쳤습니다.

```json
"runtimeExecutable": "python",
"runtimeArgs": ["-c", "import os,sys; os.environ['LLM_PROVIDER']='openai'; os.chdir('backend'); sys.path.insert(0,'.'); import uvicorn; uvicorn.run('app.main:app', host='127.0.0.1', port=8000)"]
```

## ⚠ 측정 변동이 큽니다

같은 코드로 두 번 잰 값입니다.

```
1차  NFR-DV-001  2134.6 / 3216.1ms
2차  NFR-DV-001  2594.6 / 5956.2ms   ← 코드는 그대로, API 변동
```

**n=10 으로는 작은 개선을 구분할 수 없습니다.** 위 결론이 확실하다고 보는
이유는 (1) 위기 경로가 3.3배 줄었고 (2) 그 값이 `detect_crisis` 단독
실측과 일치하기 때문입니다. **일반 경로의 변화는 변동으로 봐야 합니다.**

## MVP 관통 점검 (`tools/smoke_mvp.py`)

**수집 → 분석 → 케어 → 관제 전 구간이 이어집니다. 실패 0건.**

```
[1] 인증   로그인 → JWT · 내 정보
[2] 수집   라이프로그 14건 · 걸음/수면 실측치 존재
[3] 분석   SADNESS / CAUTION score=92.11
[4] 케어   홈 action=EMERGENCY · AI 한줄 요약 · 리포트 14포인트
           위기 시 콘텐츠 추천 중단 (0건)
[5] 대화   세션·응답 · 위기 발화 → EMERGENCY
           위기 시 일반 응답 차단 (reply=None)
[6] 관제   일반 계정 403 · 분포·목록·검색·상세·위기이력
```

### 200 이 아니라 값을 봅니다

`bench_nfr.py` 는 속도를, 이 스크립트는 **흐름이 이어지는지**를 봅니다.
200 만 확인하면 「빈 배열을 정상 응답으로 돌려주는」 상태를 통과로 칩니다.
실제로 걸렸습니다 — 라이프로그가 200 이어도 `steps` 가 전부 null 이면
분석이 못 돕니다.

### 안전 동작이 수치로 확인됐습니다

- **위기 판정 시 콘텐츠 추천 0건** — `MLCM_510` 2단계
- **위기 시 `reply=None`** — 생성된 일반 응답을 버리고 긴급 안내로 전환
- **일반 계정 관제 403** — `USERS.role` 가드

⚠ 판정 근거가 `rule-baseline-v1` 입니다 — **개인 기준선 이탈 규칙이지
모델이 아닙니다.** 임계값도 임의값이라 성능 근거로 쓰면 안 됩니다.
