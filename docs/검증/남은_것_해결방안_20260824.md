## 1. Health Connect 실기기 검증 (남음)

**지금 상태** — 에뮬레이터에는 Health Connect가 없어서 `WorkManager`가
15분 주기로 정상 실행되는 것까지만 확인했습니다. 실제 걸음·수면·심박
데이터가 Health Connect → 앱 → 서버로 흐르는지는 실기기가 있어야
확인됩니다.

**해결 계획**
1. Health Connect가 설치된 안드로이드 실기기 확보(팀원 개인폰 가능 —
   Android 14+ 면 기본 탑재, 이전 버전은 Play 스토어에서 별도 설치)
2. `flutter build apk --release --dart-define=API_BASE_URL=https://101.79.24.15.nip.io`
   로 만든 release APK 설치(디버그 앱이 아니라 release로 해야
   `network_security_config.xml` 등 릴리스 전용 결함까지 같이 잡힙니다)
3. Health Connect 권한 4개(걸음·수면·심박·체중 계열) 허용
4. Samsung Health/Google Fit 등으로 실제 데이터를 며칠치 쌓아 둔
   계정으로 로그인하거나, 워치 연동으로 당일 데이터 생성
5. 15분 뒤 `docker compose exec postgres psql ...` 로 `LIFELOG_METRICS`
   에 새 행이 들어왔는지 확인
6. 3일 이상 쌓이면 `AI_SERVER` 의 개인 기준선 이탈 판정까지 확인 가능

**막힌 것** — 실기기 하나면 됩니다. 노트북·계정 문제는 없습니다.
확보되면 반나절 안에 끝나는 검증입니다.

## 2. 미수신 감지 스케줄러 (남음, 구현_갭 갭3)

**지금 상태** — `NFR-DV-002`가 "3시간 미갱신을 감지"하라고 요구하는데,
이걸 주기적으로 돌려 줄 주체가 아직 없습니다. FCM 인프라(갭1)는
2026.08.21에 이미 풀렸으니 **발송 경로는 있고 트리거만 없는 상태**입니다.

**해결 계획**
1. **PM 결정이 먼저 필요합니다** — `LIFELOG_METRICS`에 "재시도 실패"
   상태를 남기려면 `schema.sql`에 컬럼(또는 별도 테이블)을 추가해야
   하는데, 이게 "문서 쪽은 이미 제출 끝나서 안 건드림" 제약과
   부딪힙니다. 두 갈래 중 하나를 고르면 됩니다:
   - **(A) 스키마를 건드립니다** — 데이터베이스요구사항분석서·
     테이블명세서와 별개로 `schema.sql`만 개정. 제출 문서와 실제
     스키마가 갈리는 걸 감수합니다.
   - **(B) 스키마를 안 건드립니다** — 기존 `OUTREACH_LOGS` 패턴을
     재사용해 "미수신 알림" 을 그 테이블의 한 종류로 기록합니다.
     새 컬럼·새 테이블이 필요 없어 제약과 안 부딪힙니다. **권장**
     — 이미 있는 발송 로그 테이블에 사유 하나만 더 갈라 넣는 것이라
     설계 변경이 작습니다.
2. (B)를 고른다면: `backend/app/services/` 에 스케줄러 함수 추가 —
   `LIFELOG_METRICS`에서 사용자별 마지막 수집 시각을 조회 → 3시간
   초과면 `OUTREACH_LOGS`에 사유 `MISSED_SYNC`로 기록 → 관리자 웹에
   그 사유를 노출(이미 있는 위기 사건 이력 화면 패턴 재사용)
3. 스케줄 실행 주체는 컨테이너 안에서 `APScheduler`(이미 FastAPI
   프로세스 안에서 도는 별도 스레드) 또는 서버의 `cron`(컨테이너
   재시작에도 안 죽게 하려면 전자가 낫습니다)
4. 테스트 3~4건 추가(정상/미수신/경계값 3시간)

**막힌 것** — PM 결정 하나뿐입니다. 결정만 나면 구현 자체는 반나절
분량입니다(SMTP 갭4를 오늘 이 세션에서 처음부터 끝까지 붙이는 데
걸린 시간과 비슷한 규모로 보면 됩니다).

## 3. iOS 미구현 (범위 제외)

**지금 상태** — `frontend/app/ios` 폴더 자체가 제거된 상태입니다.
기술적으로 막힌 게 아니라 **장비·계정·일정 문제**입니다(안건 2 확정
결정, CLAUDE.md 참고).

**해결 계획(참고용 — 이번 캡스톤 범위 밖)**
1. macOS + Xcode 환경 확보(윈도우 PC로는 시뮬레이터·실기기 배포 둘 다
   불가능)
2. Apple Developer Program 가입(연회비 발생, 관리자 승인 필요)
3. `flutter create` 로 ios 폴더 재생성 → Xcode에서 HealthKit
   capability 추가
4. `health` 패키지(13.3.1, MIT)가 HealthKit도 감싸므로 `health_reader.dart`
   의 플랫폼 분기 코드는 대부분 재사용 가능 — 새로 짤 코드는 크지 않음
5. 실기기(아이폰)로 HealthKit 데이터 흐름 검증

**막힌 것** — 이번 6주 일정 안에는 착수하지 않기로 확정된 사항입니다.
발표에서 "왜 안 했나"를 물으면 "기술적으로 막힌 게 아니라 macOS·
Apple 계정·일정 문제였고, `health` 패키지가 HealthKit도 지원해서
기존 코드 대부분을 재사용할 수 있다"고 답하면 됩니다 — 이 답변
자체가 이미 CLAUDE.md에 정리돼 있습니다.

## 4. 평가셋 holdout 없음

**지금 상태** — `0.946`(재현율)은 이 평가셋 211건에서 나온 값이고,
같은 규칙·프롬프트를 **한 번도 본 적 없는 새 문장**으로 재검증한 적은
없습니다. 데이터를 만들고 그 데이터로 스스로를 채점한 것이라, 과적합
여부를 이 숫자만으로는 배제할 수 없습니다.

**해결 계획**
1. 라벨링에 전혀 관여하지 않은 사람이 새 발화 50~100건을 프롬프트나
   기존 평가셋을 보지 않고 작성
2. 같은 2인 교차 라벨링 절차로 정답 라벨을 매김(기존 211건 만들 때와
   동일 기준)
3. 지금 쓰는 프롬프트·모델(`gpt-5.4`)로 그대로 채점 — **프롬프트를
   새 데이터에 맞춰 손대면 의미가 없습니다**
4. 재현율·정밀도·F1을 다시 계산해 기존 0.946/0.921/0.933과 나란히 표기

**막힌 것** — 순수 작업량 문제입니다. 새 발화를 만들고 교차 라벨링하는
데 최소 하루 이상 걸립니다. 8/28 전에 하기엔 빠듯합니다 — 발표에서는
"이번 평가셋의 한계로 인지하고 있고, holdout 검증이 다음 단계"라고
정직하게 답하는 것이 지금 상태에서 가장 방어 가능한 답입니다(실제로
15번 슬라이드가 이미 이렇게 말하고 있습니다).

## 5. 놓친 6건 (분석 완료)

**지금 상태** — 재현율 0.946이 놓친 나머지 6건은 이미 분석까지
끝났습니다. **완곡한 표현·작별 암시·신변 정리 표현**에 몰려 있고,
문장 하나만으로는 사람도 라벨이 갈리는 애매한 사례들입니다. 이건
"못 한 일"이 아니라 "찾아서 분류까지 끝낸 일"입니다.

**해결 계획(선택 — 다음 단계 개선 과제)**
1. 이 6건을 few-shot 예시로 크리스티스 판정 프롬프트에 추가하는 방안
   — 다만 **딱 6건에 맞춰 프롬프트를 고치면 그 6건만 통과하고 다른
   유형은 그대로일 위험**이 있습니다(과적합)
2. 더 안전한 경로: 이 6건이 대표하는 "패턴"(완곡·작별·신변 정리)을
   가진 발화를 더 모아서(holdout 확장과 같이 진행하면 효율적) 그
   패턴군 전체에 대한 재현율을 별도로 재보는 것

**막힌 것** — 없습니다. 이미 분석 완료 상태고, 추가 개선은 holdout
평가셋(4번 항목)과 같이 진행하는 게 효율적이라 그쪽에 묶어 뒀습니다.
