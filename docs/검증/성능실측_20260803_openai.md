## ⚠ 먼저 — 앞선 두 번의 측정은 무효였습니다

`.claude/launch.json` 에 넣은 `cmd /c "cd backend && set LLM_PROVIDER=openai && ..."`
의 `&&` 가 전달되지 않아 **서버가 Gemini 로 떴습니다.** 모든 LLM 호출이
429(무료 한도 소진)로 실패했고, **그 실패 왕복이 170ms 로 찍혀 「통과」로
나왔습니다.**

```
NFR-DV-001 일반 발화   중앙값 170.4ms  최댓값 2615.9ms  예산 3000ms  통과   ← 거짓
NFR-TS-001 위기 발화   중앙값 165.5ms  최댓값 2310.6ms  예산 3000ms  통과   ← 거짓
```

`LLM-005` 가 정확히 이 함정을 적어뒀습니다 — *"화면은 멀쩡해 보입니다.
응답 시간만 재면 정상으로 오인합니다."* **같은 자리를 두 번 밟았습니다.**

> **측정할 때마다 서버 로그를 함께 보세요.** 숫자만 보면 구분이 안 됩니다.
> `preview_logs` 로 429·5xx 가 없는지 확인한 뒤에 수치를 적으세요.

**고친 방법** — 쉘 문법에 의존하지 않도록 `launch.json` 을 바꿨습니다.

```json
"runtimeExecutable": "python",
"runtimeArgs": ["-c", "import os,sys; os.environ['LLM_PROVIDER']='openai'; os.chdir('backend'); sys.path.insert(0,'.'); import uvicorn; uvicorn.run('app.main:app', host='127.0.0.1', port=8000)"]
```

중앙값은 예산 안이지만 **최댓값이 넘습니다.** 10회 중 최소 1회가 3초를

> 참고 — Gemini 기록은 **2.19초**입니다(`LLM-004`). OpenAI 가 더 느립니다.

## ⚠ `NFR-DV-001` 이 규정한 동작이 구현돼 있지 않습니다

요건 본문은 이렇게 씁니다.

> 1차 키워드 필터는 LLM 호출 이전에 로컬에서 선(先)수행하여, **명백한 위기
> 표현은 API 왕복 없이 즉시 판정한다.**

실제 `chat.py` `send_message()` 는 키워드 스캔을 먼저 하지만, **그 결과와
무관하게 항상 LLM 을 기다립니다.** 「죽고 싶」이 들어간 발화도 5초를 기다린
뒤 응답을 버립니다(`EMERGENCY` 면 `reply = None`).

### 그런데 단순히 끊으면 안 됩니다

키워드 단독으로 즉시 판정하면 `NFR-TS-001` 은 **158ms 로 통과**합니다.
하지만 **HIGH 키워드 정밀도가 0.500** 입니다(평가셋 200건 · TP 10 / FP 10).

```
"예전에 죽고 싶었는데 지금은 괜찮아요."
"친구가 죽고 싶대요. 제가 어떻게 해줘야 할까요?"
"죽고 싶은 건 아니에요. 그냥 좀 쉬고 싶어요."
"소설에 자살하는 인물을 넣으려는데 어떻게 그릴까요"
"시험 망해서 죽고싶다 ㅋㅋ"
```

**전부 HIGH 키워드에 걸립니다.** 즉시 판정하면 이들에게 109 긴급 상담
화면이 뜹니다.

**요건의 전제가 실측과 다릅니다.** 「명백한 위기 표현」이라는 말이 HIGH
키워드 사전이 실제로 잡는 것과 일치하지 않습니다.

### 선택지

| 안 | 내용 | 대가 |
|---|---|---|
| A | 현행 유지 — 항상 LLM 대기 | `NFR-TS-001` 미달 유지 |
| B | HIGH 키워드 즉시 판정 | 3초 통과. **오탐 50%** — 위기 아닌 사람에게 109 화면 |
| C | HIGH 사전을 정밀도가 높은 표현만 남기게 좁힘 | 재현율이 더 떨어짐(이미 0.097) |
| D | 요건 문구를 실측에 맞게 개정 | 문서 개정 1건 |

**B 는 권하지 않습니다.** 정신건강 앱에서 오탐 109 화면은 불안을 키우고
회피를 유발합니다 — 화면 설계에서 이미 같은 이유로 경고색을 뺐습니다
(`SD-A⑤`).

## `_decide()` 를 두 번 고쳤습니다 — 두 번째가 정정입니다

**1차(과함)** — HIGH 키워드를 무조건 CRITICAL 바닥값으로 두었습니다.
`bench` 에서 「죽고 싶다」 발화가 `['CONTENT', 'EMERGENCY']` 로 갈리는 회귀를
잡으려던 것인데, **LLM 의 거부권까지 없앴습니다.** 위 오탐 5건이 전부
109 로 갔을 것입니다.

**2차(정정)** — 문맥을 볼 수 있을 때는 LLM 을 신뢰합니다.

```
severity == HIGH                          -> CRITICAL
is_crisis  + (HIGH 키워드 | severity 불명) -> CRITICAL
is_crisis                                 -> CAUTION
LLM 이 위기 아님 + 키워드 있음              -> CAUTION   (109 아님)
LLM 없음(장애) + HIGH 키워드               -> CRITICAL  (NFR-DV-003)
```

**오탐을 감수하는 것은 문맥을 볼 수 없을 때의 정책**이지 상시 규칙이
아닙니다. `LLM-005` 가 「그만두고 싶」을 HIGH 에 넣지 않은 것과 같은 판단입니다.

회귀 방지 — `backend/tests/test_risk_policy_drift.py` 에 두 건 추가.
백엔드 전체 **71건 통과**.

## 구조적 원인 두 가지

**① OpenAI 는 네 작업이 한 모델을 씁니다**

`model_for()` 가 Gemini 는 작업별로 갈라놓았지만(`reply`·`crisis`·`summary`·
`daily`) OpenAI 는 `openai_model` 하나입니다. 주석에 "정확도 기준선이라 같은
모델을 써야 Gemini 와 비교가 의미를 갖는다"는 근거가 있어 **의도된 설계**입니다.

다만 `gpt-5.6` 은 응답 생성용으로는 무겁습니다. 지연이 문제라면 `reply` 만
가벼운 모델로 빼는 선택지가 있고, 그때는 위 주석의 전제를 함께 고쳐야 합니다.

**② `llm_timeout_seconds = 8.0`**

3초 예산의 2.7배입니다. **예산을 넘겨도 실패로 잡히지 않습니다.** 이 값은
"무료 티어 503 이 3초 예산을 통째로 먹는 것"을 막으려고 정한 것이라
(`LLM-004`, 실측 13.95초) 근거가 있지만, OpenAI 경로에서는 예산과
어긋납니다.

# ✅ 해결 — E안 적용 후 두 요건 모두 통과 (같은 날 후속)

**「위기가 확정되면 응답 생성을 기다리지 않는다」** 를 구현했습니다.

| 요건 | 개선 전 | 개선 후 | 예산 |
|---|---|---|---|
| `NFR-DV-001` | 2134.6 / 3216.1ms ❌ | **2483.6 / 2899.1ms** ✅ | 3000ms |
| `NFR-TS-001` | 4964.5 / 6608.3ms ❌ | **2058.9 / 2881.1ms** ✅ | 3000ms |

## 근거 — 어느 호출이 긴 쪽인지 직접 쟀습니다

n=5, `LLM_PROVIDER=openai`, 두 함수를 따로 호출.

| | `detect_crisis` | `generate_reply` |
|---|---|---|
| 위기 발화 | 1920.0 / 4007.5ms | **5151.5 / 6379.9ms** |
| 일반 발화 | 1347.7 / 2623.4ms | 2496.1 / 2936.9ms |

**응답 생성이 위기 판정보다 2.7배 깁니다.** 병렬 호출의 전체 시간은
`max(둘)` 이므로 위기 경로는 사실상 응답 생성 시간이었고, **그 응답은
CRITICAL 이면 버려집니다.** 버릴 것을 기다리고 있었습니다.

개선 후 `NFR-TS-001` 중앙값 2058.9ms 는 `detect_crisis` 단독 실측
1920.0ms 와 거의 같습니다 — **의도한 메커니즘대로 동작합니다.**

## ⚠ 처음 구현은 효과가 없었습니다

`severity == "HIGH"` 일 때만 취소하도록 만들었더니 **재측정에서 오히려
나빠졌습니다**(4964 → 6797ms).

원인은 「죽고 싶다」 발화에 **LLM 이 MEDIUM 을 주는 일이 잦다**는 것입니다.
프롬프트가 "실행 의도가 드러나지 않으면 MEDIUM" 을 지시하기 때문입니다.
최종 CRITICAL 은 **HIGH 키워드가 함께 있어서** 나오는데,
`analyze_and_reply` 는 키워드 결과를 받지 않아 그걸 알 수 없었습니다.

> **판정 규칙이 두 곳에 있으면 이런 일이 납니다.** `chat.py` 의 `_decide()`
> 안에만 규칙이 있어서, 성능 최적화 쪽이 조건을 **따로 적었고 그게 틀렸습니다.**
>
> 규칙을 `risk_policy.level_for()` 한 곳으로 올리고, 양쪽이 같은 함수를
> 쓰게 했습니다. `analyze_and_reply` 는 `will_discard_reply()` 로 묻습니다.

## ⚠ 측정 변동이 큽니다

같은 코드로 두 번 잰 값이 이만큼 다릅니다.

```
1차  NFR-DV-001  2134.6 / 3216.1ms
2차  NFR-DV-001  2594.6 / 5956.2ms   ← 코드는 그대로, API 변동
```

**n=10 으로는 작은 개선을 구분할 수 없습니다.** 위 E안의 효과가 확실하다고
보는 이유는 (1) 위기 경로가 3.3배 줄었고 (2) 그 값이 `detect_crisis` 단독
실측과 일치하기 때문입니다. **일반 경로의 변화는 변동으로 봐야 합니다.**

## 선택지 A~D 는 어떻게 됐나

| 안 | 결과 |

| A 현행 유지 | 불필요 — E 로 해결 |
