# LLM 참고자료 사용 이력

LLM·프롬프트·OpenAI API 관련 작업을 시작할 때 최신 관련 항목을 먼저 검색합니다. 새 기록은
맨 위에 추가합니다. 단순 열람은 기록하지 않고, 구현이나 설계 판단에 영향을 준 자료만 남깁니다.

## 기록 양식

```markdown
## YYYY-MM-DD · LLM-XXX · 작업명

- 작업 범위:
- 조회한 자료:
- 채택한 방법:
- 채택하지 않은 방법과 이유:
- 성공 조건·평가 사례:
- 검증 결과:
- 반영 파일:
```

## 2026-08-22 · LLM-020 · 위기 판정을 처음으로 DB 에 남깁니다 — 프롬프트는 건드리지 않았습니다

- **작업 범위**: `MLCM_320` 7단계 미구현(구현_갭 갭 9) — 대화 위기 판정의 DB 적재
- **조회한 자료**: `PROMPT_REFERENCE.md` 적용 원칙 · 요구사항정의서 `MLCM_320`·`MLCM_501` 원문 ·
  `risk_policy.level_for()` 주석(키워드 정밀도 실측) · `db/schema.sql`
- **결론**: 채택. 프롬프트·모델·API 계약은 **한 줄도 안 바꿨습니다.**

### 왜 LLM 작업으로 기록하는가

프롬프트를 안 고쳤는데도 남깁니다. CLAUDE.md 절차의 적용 범위가 「위기 탐지,
안전장치」이고, **이건 위기 판정 결과의 처리 경로**이기 때문입니다.
판정 품질은 그대로인데 **그 판정이 아무에게도 닿지 않던 것**을 고쳤습니다.

### 무엇이 비어 있었는가

`chat.py` 는 `EMERGENCY` 판정에서 응답을 버리고(맞습니다) 사용자를 긴급
화면으로 보낸 뒤 **끝났습니다.** 판정 결과가 어디에도 안 남아, 관리자 관제의
위기 사건 이력에 아무 일도 일어나지 않았습니다.

> **수면·걸음이 무너진 사람은 보이는데, 직접 「죽고 싶다」고 말한 사람은
> 안 보였습니다.**

`MLCM_320` 7단계와 종료조건이 둘 다 이걸 요구합니다.

### 채택 — `EMOTION_RISK_SCORES` 적재 (A안)

관제가 읽는 테이블에 그대로 넣습니다. **스키마 변경 0, 관제 조회 코드 변경 0.**

| | 값 |
|---|---|
| `risk_level` | `CRITICAL` |
| `emotion_id` | `CRISIS` (감정 마스터 9종 중) |
| `model_version` | `chat-crisis-llm-v1` / `chat-crisis-kw-v1` |
| `emotion_score`·`risk_score` | `100.00` — **정책 상수, 측정값 아님** |

**판정 근거를 버전 문자열에 적은 것이 이번 설계의 핵심입니다.**
키워드 단독 판정은 **정밀도 0.500**(평가셋 200건 · TP 10 / FP 10). 같은
`CRITICAL` 이라도 근거가 다르다는 것이 관리자에게 보여야, 오탐에 개입하느라
진짜를 놓치지 않습니다. 관리자 화면의 「모델」 칸에 그대로 노출됩니다.

### 거부한 대안

| 안 | 왜 안 썼나 |
|---|---|
| `CHAT_SESSIONS` 에 위험 상태 컬럼 | 요구사항 문구(「세션을 고위험 상태로 전환」)에는 더 맞지만 **관제가 그 테이블을 안 읽습니다.** 조회 코드까지 고쳐야 하고, 스키마도 바뀝니다 |
| 위험 탐지 로그 테이블 신설 | 데이터베이스요구사항분석서·테이블명세서가 **제출 완료**. 10번째 테이블이 생기면 문서와 어긋납니다 |
| 점수를 `severity` 로 환산 | `severity` 는 LLM 이 채우는 **자유 문자열**입니다("High"·"위험" 등이 옵니다). 정규화해 봐야 3단계뿐이라 0~100 척도를 만들 근거가 없습니다. 있는 척하면 리포트 차트에서 **측정값처럼 보입니다** |
| 매 발화마다 적재 | 위기 상태의 사람은 연달아 말합니다. 관제 목록 첫 페이지를 혼자 채워 **다른 위험군을 화면 밖으로 밀어냅니다** → 세션당 1건으로 제한 |
| 키워드 단독 건 제외 | `NFR-DV-003` 이 장애 중 키워드 단독 동작을 요구합니다. **시스템이 가장 약할 때 감시까지 꺼집니다** |

### 성공 조건과 결과

구현 전에 정하고, 구현 후 같은 항목으로 검증했습니다
(`backend/tests/test_crisis_log.py`, 9건 신설).

| 조건 | 결과 |
|---|---|
| 위기 발화(LLM 확정) → `CRITICAL` 1행 · `chat-crisis-llm-v1` · `CRISIS` | ✅ |
| 외부 API 장애 + HIGH 키워드 → `chat-crisis-kw-v1` | ✅ |
| 같은 세션 위기 3회 → 행 1개, 발화 3개는 보존 | ✅ |
| 세션이 다르면 따로 적재 | ✅ |
| 일반 발화·CAUTION → 0행 | ✅ |
| 감정 마스터에 `CRISIS` 가 없어도 긴급 전환은 정상(500 안 남) | ✅ |
| 적재 중 예외가 나도 대화는 저장 | ✅ |
| 관리자 위기 사건 이력에 노출 | ✅ |
| 기존 회귀 109건 | ✅ 전부 통과 (총 118건) |

실서버에서도 위기 발화 → 관제 목록에 `chat-crisis-llm-v1` 행이 뜨는 것을
확인했습니다.

### 곁가지로 함께 닫힌 것

홈 화면은 최신 판정으로 `action` 을 정합니다. 이 적재가 들어가면서
**`MLCM_510` 2단계(콘텐츠 추천 중단)가 응답 한 번을 넘어 지속**됩니다.
전에는 위기 발화 직후에도 홈이 힐링 콘텐츠를 계속 추천했습니다.

### ⚠ 첫 검증이 거짓이었습니다

백엔드를 `--reload` 없이 띄워 둔 채 재시작했는데 **포트가 안 풀려 옛 코드가
요청을 처리**했습니다. 「구현했는데 안 나온다」로 30분을 쓸 뻔했습니다.
로그의 `bind on address ... already in use` 가 유일한 단서였습니다.

**재기동 뒤에는 로그에 bind 오류가 없는지 먼저 보세요.** 응답이 200 이라고
새 코드가 도는 것이 아닙니다.

## 2026-08-12 · LLM-019 · 선제 접촉 페르소나 구분 — 이미 해결돼 있었고, 평가 도구가 고장나 있었습니다

- **작업 범위**: `OUTREACH_SYSTEM` 페르소나 구분 검토 (SESSION-HANDOFF 잔여 3건 중 ③)
- **조회한 자료**: 요구사항정의서 `MLCM_220`·`MLCM_300`·`MLCM_310` 원문 · `tools/eval_outreach.py`

### 먼저 — 요건상 필수가 아닙니다

`MLCM_220` 3단계는 「**관찰된 이탈 지표를 근거로** 챗봇 첫 발화를 생성한다」
까지만 규정합니다. **페르소나 반영은 안 적혀 있습니다.** 페르소나를 명시적으로
요구하는 것은 `MLCM_300`(주입 가능한 상태) · `MLCM_310`(사용자 입력에 대한
답변)이고, 선제 접촉 첫 마디는 `MLCM_310` 소관이 아닙니다.

**즉 요건 미충족이 아니라 완성도 문제입니다.** 검사기도 잡지 않습니다.

### 성공 조건 (측정 전에 정함)

| 항목 | 이전 기록 | 목표 |
|---|---|---|
| 페르소나 간 유사도 평균 | 0.76 | < 0.60 |
| 유사도 최대 | 0.97 | < 0.85 |
| 닫는 문장 동일 | 10/12 | ≤ 3/12 |
| 기계 검사 위반 | — | 0건 유지 |

### ⚠ 평가 도구가 운영과 다른 것을 재고 있었습니다

측정하려다 `tools/eval_outreach.py` 의 결함 셋을 먼저 잡았습니다. **`LLM-016`
이 응답 모델을 `openai_model_reply` 로 가른 뒤 이 도구가 따라오지 않은
것**이 공통 원인입니다.

| 결함 | 증상 |
|---|---|
| `--model` 이 생성에 안 먹음 | `gen()` 이 `outreach_opener()` 를 인자 없이 불러 **헤더에만 찍히고 실제 호출은 안 바뀜.** 대조군 비교용 옵션이 비교를 안 함 |
| 캐시 키에 모델 없음 | 모델을 바꿔도 **호출 0건**으로 옛 발화를 다시 채점 |
| 기본 모델이 판정용 | `resolve_model()` 기본값이 `openai_model`(`gpt-5.4`)인데 선제 접촉은 `model_for('reply')`(`gpt-5.4-mini`) 사용 |

셋째가 특히 위험합니다 — **헤더에 `gpt-5.4` 를 찍으면서 실제로는
`gpt-5.4-mini` 로 생성**하고 있었습니다. 수치는 맞는데 이름이 틀린 상태라
「어느 모델의 성적인가」를 문서에 잘못 적기 딱 좋습니다.

### 검증 결과 — 목표 전부 통과, 프롬프트 수정 불필요

`gpt-5.4-mini`(운영과 동일) · 6사례 × 2페르소나 = 12건

| 항목 | 이전(`gpt-5.6` 시절) | 목표 | **현재** |
|---|---|---|---|
| 유사도 평균 | 0.76 | < 0.60 | **0.50** ✔ |
| 유사도 최대 | 0.97 | < 0.85 | **0.71** ✔ |
| 닫는 문장 동일 | 10/12 | ≤ 3/12 | **0/12**(12종 전부 다름) ✔ |
| 기계 검사 위반 | — | 0건 | **0/12** ✔ |
| 말투 일관성 | — | 유지 | FRIEND·COUNSELOR 모두 존댓말 ✔ |

**`LLM-017` 의 모델 교체가 이것도 같이 고쳤고, 아무도 다시 안 재봤습니다.**
문장을 읽어도 갈림이 분명합니다 — FRIEND 는 감정을 받고("은근히 지치실 수
있는데", "괜히 마음이 쓰입니다"), COUNSELOR 는 패턴 확인으로 갑니다("최근에
잠들기 전 패턴이 달라진 점이 있었는지", "함께 살펴보셔도 좋습니다").

- **채택한 방법**: 프롬프트 **수정하지 않음.** 평가 도구만 고침
- **채택하지 않은 방법과 이유**: `OUTREACH_SYSTEM` 에 페르소나별 문 여는 방식을
  명시하는 안. **목표를 이미 통과한 상태라 고칠 이유가 없고**, 손대면 지금
  통과하는 구분이 되레 무너질 수 있습니다
- **반영 파일**: `tools/eval_outreach.py` · `backend/app/services/llm.py`
  (`outreach_opener` 에 평가용 `model` 인자 추가 — 운영은 안 넘기므로 동작 불변)

### 사람이 읽어야 잡히는 것 — 판단 대기 2건

기계 검사는 12건 전부 통과했습니다. 읽어서 걸린 것만 남깁니다.

1. **COUNSELOR 가 지속일수를 그대로 말합니다** — 3/12건. 「최근 **5일 동안**
   밤중에 깨는 횟수가…」 · 「2주째 보여서」 · 「최근 3일 동안」. FRIEND 는 0건.
   `OUTREACH_SYSTEM` 은 「수치를 그대로 읽어주지 말고」 · 「감시당한다는 느낌을
   주지 않는다」를 규정합니다. **며칠째인지 세고 있었다는 것이 드러납니다.**
   다만 근거를 구체적으로 대 신뢰를 준다고 볼 여지도 있어 판단이 필요합니다
2. **세미콜론** — FRIEND/수면 둘 장기 1건. 「많이 신경 쓰이셨을 수 있어요**;**
   괜찮으시면…」. 한국어 채팅 말풍선에 어울리지 않습니다

## 2026-08-12 · LLM-018 · UNCLEAR 반쪽 구현 기각 — 세 지표가 전부 내려갔습니다

- **작업 범위**: 요구사항정의서 `MLCM_320` 4-1·4-2 의 「판별 불가」 상태 구현
- **조회한 자료**: `MLCM_320` 4-1·4-2 원문 · `LLM-017` 의 0.946 기준선

### 무엇을 했나

`severity` 에 `UNCLEAR` 값을 추가하고(프롬프트 + 스키마 설명), `risk_policy.level_for()`
에서 `UNCLEAR → CAUTION`(단 키워드 HIGH 면 CRITICAL)으로 매핑했습니다. 채점기도
판별 불가 건수를 세도록 고쳤습니다.

### 검증 결과 — 기각

  아주 흔해서, 외부 API 장애 중에 멀쩡한 사용자에게 긴급 상담 화면이 뜹니다.
  미탐을 줄이려 오탐을 감수하는 것은 **문맥을 볼 수 없을 때의 정책**이지 일상 표현을
  고위험으로 분류하라는 뜻이 아닙니다
- **성공 조건·평가 사례**:
  - `다 그만두고 싶어요` → MEDIUM
  - `회사를 그만두고 싶어요` → MEDIUM (**HIGH 아님**)
  - `배고파 죽겠다`·`이 회의는 의미가 없어요` → NONE (기존 오탐 방어 유지)
- **검증 결과**: `test_lifelog_chat.py` 13건 통과. 백엔드 전체 48건 통과

## 2026-07-31 · LLM-002 · 챗봇 라우터 구현 (페르소나 응답·위기 판정·세션 요약)

  - 키워드 사전을 `app/data/crisis_keywords.json` 으로 분리(03-B "운영 중 갱신 가능")
