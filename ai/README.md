# AI — 라이프로그 분석 모델

> **담당** 김건영 · **최종 내용 갱신** 2026.07.29 · **현행성 점검** 2026.07.31
>
> 2026.07.31 기준 아래 상태는 그대로입니다. 전체 학습 완료가 아니라 PMData `p01`과
> GLOBEM 샘플 1개로 전처리 파이프라인을 검증한 단계입니다.

라이프로그 시계열에서 정서 위험도를 산출하는 2단계 모델입니다.

```
1차  LSTM Autoencoder   정상 패턴 학습 → 재구성 오차 = anomaly_score
2차  LightGBM           anomaly_score + 라이프로그 피처 → 감정 9종 · risk_score
```

위기 대화 탐지는 **별도 학습 모델이 아닙니다.** 키워드 규칙 + OpenAI 프롬프트 2단계로 구현합니다. (안건 3 확정)

> ### 모델을 어디에 끼우나 — [`server/`](server/README.md) (2026.08.01 추가)
>
> 비즈니스 서버가 호출하는 추론 서버가 `ai/server/` 에 있습니다. **`main.py` 의
> `_predict()` 하나만 위 2단계 모델로 바꾸면** 앱까지 전 구간이 연결됩니다.
>
> 지금은 규칙 기반 임시 판정이라 `model_version` 이 `rule-placeholder-v0` 입니다.
> 반환 6필드의 이름·타입은 비즈니스 서버와의 계약이므로 바꾸지 마세요.

## ⚠ 문서 작성 시 주의할 점

### 1. `hrv_sdnn` 은 진짜 SDNN 이 아닙니다

`process_pmdata.py` 는 **일별 BPM 의 표준편차**를 HRV 프록시로 씁니다.

```python
hrv_sdnn=('bpm', 'std')  # 심박수 표준편차 = HRV 프록시 지표
```

표준 SDNN 은 RR 간격(NN interval)의 표준편차인데, PMData 의 Fitbit 데이터에 RR 간격이 없어 대체한 것입니다. 합리적인 선택이지만 **산출물 문서에 그냥 "HRV"라고 쓰면 정확하지 않습니다.**

- **실서비스** — Health Connect 가 제공하는 HRV 를 그대로 수집
- **학습 데이터** — PMData 의 BPM 표준편차 프록시

두 값의 성격이 달라 **도메인 갭이 존재**합니다. 문서에 이 차이를 적어두면 "학습 데이터의 HRV 와 실제 수집하는 HRV 가 같은 건가요"라는 질문에 답할 수 있습니다.

### 2. GLOBEM 의 스크린타임 피처는 쓰지 않습니다 *(2026.07.29 제외)*

`process_globem.py` 가 원래 `screen.csv`(스크린타임·화면 잠금해제)를 병합하고 있었으나 **제거했습니다.**

**서비스가 만들 수 없는 피처로 학습하면 배포 시 그 자리가 비어 성능이 나오지 않습니다.**

- `LIFELOG_METRICS` 에 스크린타임 컬럼이 없습니다 (`db/schema.sql`)
- **Health Connect 는 스크린타임을 제공하지 않습니다.** 안드로이드에서 폰 사용량은 `UsageStatsManager` 영역이라 별도 권한이 필요하고, 현재 수집 범위·동의 항목 어디에도 없습니다

결과적으로 GLOBEM 피처 매트릭스는 **수면 4 + 걸음 4 + BDI-II 라벨 = 12컬럼**입니다. (이전 15컬럼)

> 폰 사용량을 정식 수집 항목으로 추가하기로 결정한다면, **스키마·요구사항정의서·동의 항목을 먼저 고친 뒤** 되살리세요. 순서를 바꾸면 "동의도 안 받은 데이터로 학습했다"가 됩니다.

### 3. 다른 공개 데이터셋을 검토했으나 추가하지 않았습니다

| 데이터셋 | 검토 결과 |
|---|---|
| **Depresjon** | **부적합.** 분 단위 활동량 하나뿐이라 수면·심박·HRV 와 겹치는 신호가 없습니다. MADRS 임상 라벨은 매력적이지만 신호가 없으면 쓸 수 없습니다 |
| **LifeSnaps** | **여유가 생기면 재검토.** Fitbit Sense 기반이라 GLOBEM 의 약점(심박·HRV 없음)을 메웁니다. 라벨이 PANAS(정서)·STAI(불안)이라 우울 척도보다 오히려 감정 9종 분류에 가깝습니다. 다만 실제 컬럼 구성 확인이 필요하고, 4주차 이후에나 볼 일입니다 |

**데이터셋을 하나로 합치는 것은 권장하지 않습니다.** 집계 단위(일별 vs 14일), 기기 모델, 라벨 척도(BDI-II·MADRS·PANAS 는 상호 변환 불가), 인구집단이 모두 달라 도메인 시프트가 큽니다. **지금처럼 역할을 나누는 구조**(PMData=비지도 1차, GLOBEM=지도 2차)가 맞습니다.

### 4. 현재는 전체 학습이 아니라 파이프라인 검증 단계입니다

| 스크립트 | 처리 범위 |
|---|---|
| `process_pmdata.py` | **참가자 `p01` 한 명** |
| `process_globem.py` | **`INS-W-sample_1` 샘플 1개** |

"전처리 완료"가 아니라 **"파이프라인 동작 확인 완료"** 입니다. 문서에 학습 규모를 쓸 때 과장하지 마세요.

## 기업(라라랩스) 제공 데이터 — 2026.07.29 메타데이터 수령

멘토가 전달한 [`라이프로그데이터_메타데이터`](../docs/extracted/라이프로그데이터_메타데이터.txt) 로 기존 질문 3건이 모두 해소되었습니다.

| 질문 | 답 |
|---|---|
| 항목과 단위 (초/분 원본 vs 일 통계) | **일(日) 단위 집계.** 날짜 `YYYY.MM.DD`, 수면 `min`, 걸음 `count`. **추가 전처리 불필요** |
| 정답(라벨) 데이터 유무 | ⚠ **없음.** 아래 참조 |
| 워치 미착용 구간 결측 처리 | 수면·깊은잠·얕은잠·REM 이 **기록되지 않은 행은 삭제**한 정제본 제공 |

### 제공 항목

- **라이프로그(13)** — 날짜, 깊은잠·얕은잠·각성·REM(min), 수면 시작·종료 시각, 활동 날짜·시작·종료 시각, 거리(m), 걸음 수, 칼로리
- **체성분(12)** — 회원번호, 나이, 성별, 키, 체중, 체수분, 체지방, 근육량 및 표준범위 상·하한, 골격근량, 기초대사량
- **집계(23)** — 위 항목에 총 수면시간·각성·입면 시간·수면 효율(%)·총 활동시간/거리/걸음수/칼로리 추가

### ⚠ "라벨링데이터" 에 정답이 없습니다

표 이름은 `라벨링데이터 항목` 이지만 **23개 항목이 전부 수면·활동·체성분 수치**입니다. 정서 상태나 위험도 라벨이 하나도 없습니다. **이름만 라벨링이고 실제로는 일별 집계 피처입니다.**

→ **2차 LightGBM 의 지도학습 정답은 GLOBEM 의 BDI-II 가 유일한 임상 라벨 소스입니다.** 기업 데이터로는 자체 위험도 점수를 산출해야 합니다(라이프로그 수치 가중치 방식).

### ⚠ 심박수·HRV 가 없습니다

기업 데이터 어디에도 심박수·HRV 가 없습니다. 출처별로 확보 수준이 다릅니다.

| 출처 | 심박수 | HRV |
|---|---|---|
| 기업 제공 데이터 | ❌ | ❌ |
| PMData | ✅ 분 단위 | △ 일별 표준편차 **프록시** |
| 실서비스 (Health Connect) | ✅ | ✅ |

→ **1차 모델은 수면·활동을 공통 피처로 쓰고, 심박·HRV 는 확보 가능한 구간의 보조 피처로 다룹니다.** 문서 반영은 체크리스트 `03-E`.

### 스키마 대조 결과

| 구분 | 결과 |
|---|---|
| **체성분 8항목** | ✅ `BODY_COMPOSITION_METRICS` 와 **완전 일치** |
| 수면 8항목 · 걸음·거리·칼로리 | ✅ `LIFELOG_METRICS` 와 일치 |
| 나이·성별·키 | ✅ `USERS` 와 일치 |
| **활동 시작·종료 시각, 총 활동시간** | ⚠ **스키마에 없음** → 수용 여부 판단 필요 (`05-E`) |

**체성분이 8항목 그대로 맞는 건 강점입니다.** 발표에서 "기업 제공 데이터 구조에 맞춰 스키마를 설계했다"고 말할 수 있습니다.
